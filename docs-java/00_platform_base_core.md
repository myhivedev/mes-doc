# Спецификация требований на базовое ядро платформы

**Редакция**: 1.0.4.1

---
# 1. Введение

## 1.1. Назначение

Настоящая спецификация требований определяет полные, атомарные технические требования к проектированию, разработке и конфигурированию **базового ядра цифровой производственной платформы DMP СИГМА.MES+** (далее — Продукт или Ядро). Документ служит техническим заданием для инженеров-разработчиков и системных архитекторов.

Документ фиксирует структуру многомодульного проекта, стек технологий с указанием версий, а также архитектурные ограничения и базовые примитивы управления вычислительными ресурсами.

## 1.2. Область действия

Реализация общих базовых технических компонентов Ядра платформы охватывает:

* Контексты получения параметров запуска, сборки и применения конфигурации, включая решение задачи безопасного разделения и сквозной подачи секретов.
* Базовую модель разделения на архитектурные слои в соответствии с принципами чистой гексагональной архитектуры.
* Размещение, конфигурацию и низкоуровневое подключение платформенных ресурсов: PostgreSQL (Patroni Cluster), ClickHouse (LZ4), Apache Kafka (и Kafka Lite).
* Внедрение отказоустойчивого встроенного LSM-хранилища для Edge-слоя и примитивов Backpressure.
* Набор базовых типов, глобальных идентификаторов и видов доменных/инфраструктурных ошибок.
* Развертывание и автоматическую генерацию спецификаций OpenAPI (Swagger).
* Базовую модель, конфигурацию и базовые инструменты асинхронного структурированного журналирования.
* Заготовки и шаблоны автоматизированного тестирования для каждого макро-слоя.

Ядро представляет собой готовый к промышленной эксплуатации программный каркас на базе Spring Boot 4.x и Java 25, изолирующий чистое бизнес-ядро от сред исполнения и внешних инфраструктурных технологий.

## 1.3. Термины, определения и сокращения

| Термин | Определение |
|---|---|
| Ядро (Базовое ядро) | Программный каркас, задающий стандарты разработки, общие технические компоненты и инвариантные примитивы платформы. |
| Функциональное программирование (ФП) | Это парадигма разработки программного обеспечения, при которой программа рассматривается как набор вычислений, производимых с использованием чистых функций над неизменяемыми данными с явным разделением и управлением эффектами (ошибки, операции ввода-вывода, существование-отсутствие и так далее) отдельно от основных вычислений.<br><br>Используется при описании прикладных (доменных) моделей. |
| Чистая функция (в рамках ФП) | Функция, результат которой зависит только от входных параметров, не изменяющая глобальное состояние и не производящая побочных эффектов. |
| Побочные эффекты (Side Effects) | Операции ввода-вывода (запись в БД, отправка в Kafka), логирование и обработка ошибок, вынесенные за пределы (не относящиеся к) бизнес-логики. |
| Java Virtual Threads | Легковесная модель многопоточности (Project Loom), обеспечивающая масштабируемость I/O-bound задач без исчерпания пула системных потоков ОС. |
| OpenAPI | Международный машиночитаемый стандарт описания REST API для обеспечения структурно-функциональной совместимости технических решений. |
| JPA | Jakarta Persistence API — спецификация платформы Jakarta EE, предназначенный для объектно-реляционного отображения (ORM) в экосистеме Java. |
| Гексагональная архитектура | Подход к проектированию («Порты и Адаптеры»), изолирующий доменную бизнес-логику от фреймворков, баз данных, очередей сообщений и интерфейсов ввода-вывода. |
| LSM-Tree Storage (RocksDB) | Встраиваемая высокопроизводительная СУБД на базе лог-структурированного дерева слияния, устойчивая к внезапным сбоям электропитания (Power Fails). |
| Backpressure (Обратное давление) | Механизм регулирования интенсивности потока данных, предотвращающий переполнение очередей и неконтролируемый рост потребления памяти (OOM). |

# 2. Общее описание

## 2.1. Контекст продукта

Продукт является технологическим фундаментом для построения распределенной КИИ-совместимой системы СИГМА.MES+. Он не содержит конечной бизнес-логики, а предоставляет внутренние технические сервисы, интерцепторы, примитивы сглаживания потоков и инфраструктурные контракты для команд разработки прикладных MES-модулей.

## 2.2. Архитектурный стек и версии

Приложение разрабатывается как MVC-приложение с использованием блокирующего ввода-вывода, оптимизированного за счет пула виртуальных потоков Java.

| Компонент / Слой | Технология | Версия | Особенности конфигурации |
|---|---|---|---|
| Базовая платформа | Java (JDK) | 25 | Стандартизация под Project Loom и ScopedValues. |
| Фреймворк | Spring Boot | 4.x | Актуальная стабильная ветка на базе Jakarta EE. |
| Автодокументирование | springdoc-openapi-jakarta | 2.6.x | Автогенерация из слоя портов/контроллеров. |
| Реляционная БД | PostgreSQL (Драйвер) | 42.7.x | Конфигурация под Patroni Cluster. |
| ORM Спецификация | Hibernate ORM / Spring Data | 6.6.x | Запрещен в `:domain:abstraction`. |
| Аналитическая БД | ClickHouse JDBC Driver | 0.6.x | Сжатие LZ4,ReplacingMergeTree. |
| Встраиваемый LSM-буфер | RocksDB (JNI-драйвер) | 8.x.x | WAL-режим для Edge-слоя (POS=EDG). |
| Брокер сообщений | Spring for Apache Kafka | 3.2.x | Поддержка Kafka Lite на узлах. |
| Безопасность | Spring Security | 6.3.x | OAuth2 Resource Server. |
| Контейнеризация тестов | Testcontainers | 1.20.x | Изолированное тестирование ресурсов. |

# 3. Конкретные требования

## 3.1. Требования к структуре проекта

Продукт должен быть реализован в виде многомодульного Gradle-проекта (Kotlin DSL). Код строго разделяется на три макро-группы и соответствующие им подмодули:

### А. Группа доменной логики (`domain`)

Бизнес-код пишется в парадигме функционального программирования. Данные должны быть неизменяемыми (immutable Java Records), а логика — состоять из чистых функций.

- **Слой абстракций (`:domain:abstraction`)**:

    - Содержит доменные модели, интерфейсы, типы данных и чистые функции. Категорически запрещено использование аннотаций JPA (@Entity), зависимостей фреймворков и библиотек ввода-вывода.

- **Слой контрактов (`:domain:ports`)**:

    - Содержит интерфейсы входящих и исходящих портов доступа. Включает обобщенные типы данных и контракты сглаживания MultiTemporalDataPort.

- **Слой встраиваемых модулей (`:domain:plugins`)**:

    - Реализация адаптеров для бизнес-логики и изолированные прикладные модули. Функционирует по аналогии с сервисами MCP (Model Context Protocol) для изоляции эффектов.
    - Обеспечивает обработку побочных эффектов доменной логики.

### Б. Группа исполнения и управления вычислениями (`runtime`)

- **Слой исполнения (`:runtime:execution`)**:

    - Конфигурация пула виртуальных потоков Java (Java Virtual Threads). Все входящие/исходящие задачи обрабатываются без блокировки потоков ОС. Включает процессор контекстов на базе ScopedValues (JDK 25).

- **Слой маршрутизации (`:runtime:routing`)**:

    - Компоненты распределения, балансировки вычислительной нагрузки и иерархического применения конфигураций (Configuration Delivery Engine).

- **Слой интеграции (`:runtime:integration`)**:

    - Реализация связующих сервисов и адаптеров для выноса побочных эффектов из доменной логики.

- **Слой управления доступом (`:runtime:auth`)**:

    - Интеграция со Spring Security 6.3.x. Режим Resource Server для JWT Keycloak и локальных кодов OAT с поддержкой эшелонирования КИИ-топологии (CTR, LOC, BLD, EDG).

### В. Инфраструктурно-ресурсная группа (`infrastructure`)

- **Инфраструктурный слой (`:infrastructure:core`)**:

    - Настройка сквозного логирования и глобальный обработчик ошибок (@ControllerAdvice) с маппингом внутренних типов ошибок ядра в REST-ответы (401, 403, 409).

- **Ресурсный слой (`:infrastructure:resources`)**:

    - Прямые низкоуровневые подключения к хранилищам данных и брокерам.
    - Содержит технические сущности (Entity) баз данных, отличные от доменных моделей, а также реализации RocksDB-буферов (контура Edge).

## 3.2. Функциональные требования

### Управление конфигурацией и секретами

- **REQ-F-001**: Ядро должно собирать конфигурацию из переменных окружения (ENV) и иерархических файлов application.yml с поддержкой горячей перезагрузки через ScopedValues.

- **REQ-F-002**: Реализовать строгое и безопасное разделение секретов. Хранение парольных пар, API-ключей и URI в открытом виде в Git-репозитории запрещено. Их внедрение должно происходить на этапе старта контейнера через защищенные переменные среды.

### Взаимодействие с базами данных и брокерами сообщений

- **REQ-F-003 (PostgreSQL)**: Конфигурация пула HikariCP к отказоустойчивым кластерам PostgreSQL под управлением Patroni. Реализация паттерна Transactional Outbox для межузлового асинхронного обмена.

- **REQ-F-004 (ClickHouse)**: Настройка подключения через официальный JDBC-драйвер ClickHouse с обязательным сжатием блоков данных по алгоритму LZ4 и движками семейства ReplacingMergeTree.

- **REQ-F-005 (Синхронизация данных)**: Использование движка MaterializedPostgreSQL на стороне ClickHouse для автоматической репликации витрин в реальном времени в штатном режиме работы сети узлов Платформы.

- **REQ-F-006 (Kafka)**: Конфигурация базовых инстансов KafkaTemplate (acks=all) и фабрик слушателей для штатного (Apache Kafka) и автономного внутризаводского (Kafka Lite) контуров.

### Документирование API (OpenAPI)

- **REQ-F-007**: Автоматическая генерация UI-спецификации Swagger по адресу /swagger-ui.html на основе аннотаций в слое контрактов/контроллеров. Спецификация должна явно разграничивать доступ по типам токенов (JWT / OAT).

### Журналирование и обработка ошибок

- **REQ-F-008**: Каждая запись в асинхронном JSON-логе должна содержать: Timestamp, Thread-ID (с флагом виртуального потока), LogLevel, Trace-ID и Client-ID узла КИИ-топологии.

- **REQ-F-009**: Базовый перечень исключений Ядра должен транслироваться глобальным обработчиком в REST-ответы:
   - AuthenticationException / BadCredentialsException → HTTP 401.
     - PolicyViolationException / AccessDeniedException → HTTP 403.
     - ConcurrentResourceSessionException → HTTP 409.
     - и другие.

### Отказоустойчивость Edge-слоя и примитив Backpressure

- **REQ-F-010 (LSM-буферизация на Edge)**: На эшелоне цеха (POS=EDG) Ядро обязано использовать встроенную СУБД RocksDB с LSM-структурой для локальной тритемпоральной буферизации. Использование реляционных файловых баз данных (включая SQLite) запрещено из-за низкого уровня отказоустойчивости при сбоях питания (Power Fails).

- **REQ-F-011 (Регулирование обратного давления)**: Порт MultiTemporalDataPort должен реализовывать стратегию Backpressure Buffer-or-Block. При превышении емкости In-Memory RingBuffer или задержках записи в PostgreSQL Patroni, Ядро обязано атомарно сбрасывать входящий поток данных (до 100 000 сигналов/сек на ноду) в локальный WAL RocksDB без генерации OOM и блокировки системных потоков ОС.

## 3.3. Нефункциональные требования

### Производительность, масштабируемость и надежность

- **REQ-NF-001**: Использование Java Virtual Threads должно обеспечивать обработку высокочастотных I/O-bound задач (до 100 000 IoT-сигналов в секунду на цеховой узел) без деградации памяти. Добавочная задержка (overhead) на перехват и обогащение контекста не должна превышать 0.2 миллисекунды.

- **REQ-NF-002**: Скорость декомпрессии и глубина аналитического хранения в ClickHouse на эшелонах LOC и CTR оптимизируются за счет LZ4-кодеков и упорядочивания по темпоральному кортежу.

- **REQ-NF-005 (Надежность буфера RocksDB)**: Локальный LSM-буфер RocksDB на Edge-ноде должен гарантировать сохранность транзакционных данных MES в условиях полной деградации сети с глубиной удержания не менее 168 часов (7 суток).

### Безопасность и изоляция КИИ


- **REQ-NF-003**: Все запросы к защищенным REST API портам ядра должны проходить валидацию через Keycloak (проверка подписи JWT, срока действия, областей видимости скоупов).

- **REQ-NF-006**: Ядро обязано осуществлять сквозную изоляцию `SecurityContext` и `DistributedEvaluationContext` строго с использованием иммутабельных контейнеров `ScopedValues` (JDK 25) в пуле Java Virtual Threads. Использование любых модификаций ThreadLocal для передачи контекста безопасности и топологии КИИ в виртуальных потоках выполнения категорически запрещено.".

- **REQ-NF-007**: Прямые синхронные SQL-транзакции между узлами КИИ-топологии категорически запрещены. Все межузловые операции фиксируются локально и изолированно на уровне конкретных Patroni PostgreSQL кластеров предприятий/корпусов.

### Требования к тестированию

- **REQ-NF-004**: Архитектурные слои должны быть покрыты заготовками тестов:
   - Доменный слой: Чистые модульные тесты (JUnit 5, AssertJ) без поднятия Spring-контекста.
     - Слой исполнения: MockMvc-тесты контрактов API с использованием jwt() утилит Spring Security Test.
     - Ресурсный слой: Интеграционные тесты с использованием Testcontainers для RocksDB, PostgreSQL Patroni, ClickHouse и Kafka.

# 4. Структура проекта

Многомодульный Gradle-проект (Kotlin DSL) имеет строго фиксированную иерархию папок, исключающую нарушение гексагональных границ:

```
dmp-sigma-mes-core/
├── build.gradle.kts          // Корневой скрипт сборки Gradle (Kotlin DSL)
├── settings.gradle.kts       // Подключение всех модулей платформы (include)
├── domain/                   // МАКРО-ГРУППА ДОМЕННОЙ ЛОГИКИ
│   ├── abstraction/          // Неизменяемые модели данных (Java Records) и типы
│   ├── ports/                // Интерфейсы входящих/исходящих портов (Backpressure порты)
│   └── plugins/              // Изолированные MCP-компоненты, адаптеры бизнес-логики
├── runtime/                  // МАКРО-ГРУППА ИСПОЛНЕНИЯ И ВЫЧИСЛЕНИЙ
│   ├── execution/            // Конфигурация Virtual Threads и ScopedValues процессоров
│   ├── routing/              // Подсистема распределения задач и Configuration Delivery Engine
│   ├── integration/          // Связующие сервисы выноса побочных эффектов
│   └── auth/                 // Контур Spring Security (Валидаторы OAT/JWT, OPA PDP)
└── infrastructure/           // МАКРО-ГРУППА ИНФРАСТРУКТУРЫ И РЕСУРСОВ
    ├── core/                 // Глобальный ExceptionHandler, логирование, SwaggerConfig
    └── resources/            // Низкоуровневые DataSource адаптеры (PostgreSQL Patroni,
                              // ClickHouse LZ4, RocksDB JNI, Kafka Lite)
```
