## 4. Сущности исходных требований и целевая модель

| Сущность исходных требований | Целевое решение | Статус | Документ |
|---|---|---|---|
| Документ (`Document`) | самостоятельная запись каждой версии документа | принято | `02`, `04` |
| Каталог документов (`DocumentFolder`) | иерархический классификатор модуля | принято | `02`, `03`, `06` |
| Тип документа (`DocumentType`) | классификатор с обязательным хранилищем и ограничениями файлов | принято | `02`, `05`, `16` |
| Файл (`File`) | заменён объектом «Содержимое документа» (`DocumentContent`) для файла, ссылки и текста | переименование | `02`, `05`, `06` |
| Связь документа с файлом (`DocumentFileLink`) | заменена связью документа с содержимым (`DocumentContentLink`) | переименование | `02`, `03` |
| Связь документа с бизнес-объектом (`DocumentObjectLink`) | универсальная ссылка без физического внешнего ключа | принято | `02`, `03`, `05` |
| Хранилище документов (`DocumentStorage`) | минимальная системная запись «База данных»; пользовательские хранилища после MVP | принято для MVP; расширение `DM-Q-024` отложено | `02`, `03`, `06`, `15` |
| Настройки управления документацией (`DocumentManagementSettings`) | отдельный доменный объект не создаётся; используются настройки платформы | отклонено как объект | `01`, `16` |

## 5. Принятые уточнения исходных требований

- официальное название модуля — «Управление документацией»;
- «Содержимое документа» (`DocumentContent`) заменяет прежний объект файла; виды — «Файл», «Ссылка», «Текст»;
- поле «Ответственное подразделение» (`ProductionUnitResponsible`) ссылается на производственную единицу (`ProductionUnit`);
- поле «Ответственный» (`ResponsibleEmployeeId`) ссылается на объект «Сотрудник» (`Personnel`) модуля «Управление ресурсами» по ПР04;
- номер документа обязателен и формируется автоматически, но может быть изменён вручную;
- восстановление переводит документ из архива в черновик;
- новая версия сохраняет номер и ссылается на первую версию;
- после удаления последней связи содержимое сразу мягко удаляется;
- отдельный объект настроек не создаётся;
- роль «Администратор модуля „Управление документацией“» включает роль «Работа с документами», а роль «Работа с документами» включает роль «Просмотр документов»;
- пункт «Документы связанного объекта» исключён.

## 6. Решения и отложенные вопросы

| ID | Решение | Статус |
|---|---|---|
| `DM-Q-008` | Целевая дочерняя коллекция `DocumentTypeRequiredField` у `DocumentType`; реализация после MVP. | отложен после MVP |
| `DM-Q-024` | В MVP только системное хранилище «База данных» без пользовательского управления; полный контракт после MVP. | частично закрыт, расширение отложено |
| `DM-Q-025` | В MVP используется `ContentRef` и системный DB-backed provider платформы; внешние providers и расширенная настройка размещения после MVP. | закрыт для MVP, расширение отложено |
| `DM-Q-026` | Скачивание файла и открытие URL пишутся модулем через `IAuditHistoryWriter`. | закрыт |
| `DM-Q-027` | Используется стандартный `ConcurrencyToken` Object Runtime. | закрыт |

Принятый вопрос `DM-Q-023` не является открытым: после удаления последней связи содержимое немедленно мягко удаляется одной целостной операцией.

## 7. Платформенные зависимости

Платформенные зависимости не изменяют предметную модель модуля и не считаются его незакрытыми функциональными требованиями. Все предлагаемые изменения планов работ платформы требуют решения Главного архитектора. До согласования новые задачи в `plans` не создаются.

### 7.1. Требуют решения Главного архитектора

### 7.1.1. Универсальная проверка связанной записи (`DM-PD-001`)

- Решение модуля: «Связь документа с бизнес-объектом» (`DocumentObjectLink`) хранит тип и идентификатор связанной записи.
- Требование к платформе: среда выполнения объектов (`Object Runtime`) проверяет регистрацию типа, существование записи, предприятие и право просмотра, не раскрывая недоступные данные.
- Существующий план: «Бэклог базовой реализации среды выполнения объектов» (`018_object_runtime_foundation_backlog.md`) покрывает общие операции, но не фиксирует универсальную проверку такой связи.
- Предлагаемое действие: дополнить существующий план общим контрактом проверки связанной записи.
- Статус: требует решения Главного архитектора.

### 7.1.2. Иерархические бизнес-объекты (`DM-PD-002`)

- Решение модуля: «Каталог документов» (`DocumentFolder`) образует иерархию без циклов.
- Требование к платформе: общий контракт поддерживает чтение дерева, выбор родителя и перемещение; предметную проверку циклов выполняет модуль.
- Существующие планы: «Бэклог базовой реализации среды выполнения объектов» (`018_object_runtime_foundation_backlog.md`) и «План редактора артефактов и свойств» (`008_artefact_and_property_editor.md`) покрывают только часть поведения.
- Предлагаемое действие: дополнить план среды выполнения объектов поддержкой иерархических бизнес-объектов.
- Статус: требует решения Главного архитектора.

### 7.1.3. Ссылочная настройка предприятия (`DM-PD-003`)

- Решение MVP: отдельная ссылочная настройка `DocumentManagement.DefaultStorageId` не используется; системное хранилище «База данных» назначается начальными данными модуля.
- Расширение: если после MVP потребуется выбор хранилища пользователем, потребуется ссылочный тип настройки и ограничение области предприятием.
- Статус: отложено после MVP; текущий выпуск дополнительной платформенной задачи не требует.

### 7.1.4. Состояние списка пользователя (`DM-PD-004`)

- Решение модуля: для пользователя сохраняются выбранное представление документов, поиск, фильтры и сортировка.
- Требование к платформе: пользовательские предпочтения (`User Preferences`) сохраняют и восстанавливают состояние конкретного списка.
- Существующий план: «Бэклог настроек времени выполнения модулей и пользовательских предпочтений» (`012_runtime_settings_backlog.md`) содержит общее хранилище, но не перечисляет состояние списков.
- Предлагаемое действие: дополнить существующий план кодами предпочтений и интеграцией со списками среды выполнения.
- Статус: требует решения Главного архитектора.

### 7.1.5. Платформенная нумерация (`DM-PD-005`)

- Решение модуля: поля «Код типа документа» (`DocumentType.Code`) и «Номер документа» (`Document.Number`) автоматически формируются по опубликованным правилам.
- Требование к платформе: платформенная нумерация (`Platform Numbering`) обеспечивает правила, атомарные счётчики, разделение по предприятию и типу документа, ручной ввод и вызов при создании.
- Существующий план: проектная документация платформы существует; отдельная задача реализации в `plans` отсутствует.
- Предлагаемое действие: согласовать создание отдельного плана реализации платформенной нумерации.
- Статус: требует решения Главного архитектора.

### 7.1.6. Защищённая конфигурация провайдеров хранения (`DM-PD-006`)

- Решение модуля: «Хранилище документов» (`DocumentStorage`) ссылается на зарегистрированного провайдера; адреса подключения и секреты не входят в предметный объект.
- Требование к платформе: защищённая конфигурация регистрирует провайдеры хранения и хранит секреты без возврата пользователю.
- Существующий план: подходящая задача в `plans` не найдена.
- Предлагаемое действие: согласовать отдельную платформенную задачу по реестру провайдеров и защищённому хранению секретов.
- Статус: отложено после MVP вместе с внешним хранением (`DM-Q-025`).

### 7.1.7. Единое правило обязательности полей (`DM-PD-007`)

- Решение модуля: в целевой версии тип документа задаёт дополнительные обязательные поля через дочернюю коллекцию `DocumentTypeRequiredField`; реализация после MVP (`DM-Q-008`).
- Требование к платформе: один опубликованный источник правила управляет обязательностью в интерфейсе и серверной проверкой при сохранении.
- Существующие планы: «План заморозки и переработки контрактов конфигурационных артефактов» (`015_artifact_contract_freeze_and_refactor_backlog.md`) и план среды выполнения объектов покрывают отдельные части.
- Предлагаемое действие: после включения функции в выпуск согласовать границу общей платформенной реализации и дополнение соответствующего плана.
- Статус: отложено после MVP; в текущем выпуске новая задача не требуется.

### 7.1.8. Аудит чтения содержимого (`DM-PD-008`)

- Решение модуля: скачивание файла и открытие ссылки подлежат аудиту и записываются через существующий `IAuditHistoryWriter` (`DM-Q-026`).
- Требование к платформе: общий аудит принимает и хранит стандартный `AuditRecord` с action code, предприятием, пользователем, временем, корреляцией и деталями.
- Предлагаемое действие: отдельная платформенная задача для MVP не требуется.
- Статус: покрыто существующим контрактом; вопрос `DM-Q-026` закрыт.

| Защита от одновременного изменения | «Активный план среды выполнения» (`009_runtime_active_backlog.md`) содержит контракт метки конкурентного изменения. | Новая задача не предлагается; вопрос `DM-Q-027` закрыт применением `ConcurrencyToken`. |

У объектов модуля есть поле «Предприятие» (`TenantId`), но нет поля «Площадка» (`SiteId`). Поэтому права, фильтрация и настройки модуля не становятся площадочными без отдельного предметного и архитектурного решения.
