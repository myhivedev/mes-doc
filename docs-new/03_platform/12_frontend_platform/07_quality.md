## 1. Назначение документа

Документ фиксирует подтверждённые проверки фронтенд-платформы, наблюдаемые
состояния, эксплуатационные пределы и пробелы, которые нельзя выдавать за
готовые гарантии.

## 2. Надёжность

В `src/Frontend/package.json` определены следующие скрипты проверок:

| Скрипт | Назначение |
| --- | --- |
| `lint` | ESLint для рабочей области. |
| `lint:all` | ESLint для приложений и пакетов. |
| `i18n:check` | Проверка словарей локализации фронтенда. |
| `typecheck` | Проверка проектов TypeScript. |
| `build` | Сборка приложений и пакетов. |
| `test` | Модульные/компонентные тесты через Vitest. |
| `test:e2e` | E2E-тесты через Playwright. |
| `test:e2e:ui` | Режим UI для Playwright. |
| `test:e2e:report` | Формирование отчёта Playwright. |

([пакет фронтенда][frontend-package])

| Отказ | Гарантия | Предел | Восстановление | Проверка |
| --- | --- | --- | --- | --- |

## 3. Наблюдаемость

Код подтверждает пользовательские состояния входа, проверки сессии, стартовой
страницы runtime и ошибки загрузки. Производственная телеметрия, политика
корреляции и классификация клиентских логов не подтверждены.

| Сигнал | Источник | Корреляция | Потребитель | Диагностический пробел |
| --- | --- | --- | --- | --- |
| Ошибка проверки сессии | Запуск приложений | Сессия и результат HTTP-запроса | Пользователь и приложение | Нет общей производственной классификации |
| Ошибка точки входа runtime | Приложение Runtime | Запрос runtime | Приложение Runtime | Нет утверждённой политики телеметрии и хранения |

## 4. Производительность

Текущий код содержит элементы управления списком и grid, но измеренный предел размера списка и
SLO для рендеринга не зафиксированы.

| Сценарий нагрузки | Предел или SLO | Метод | Результат |
| --- | --- | --- | --- |
| Большой настроенный список | Не определён | Отдельный тест производительности | Не подтверждено; `FE-DEC-05 — полнота разметки списка runtime` |
| Общая оболочка приложения | Не определён | e2e на уровне браузера и визуальный эталон | Частично подтверждено e2e; визуальный эталон отсутствует |

### 5.2. Пределы покрытия

Текущие тесты подтверждают многие механизмы фронтенда, но этот драфт не заявляет
полного покрытия для следующих случаев:

- всех сочетаний профилей приложений;
- всех вариантов поведения опубликованного `Menu.TargetType`;
- полной матрицы совместимости контрактов серверной части и фронтенда;
- аудита доступности всех компонентов;
- классификации безопасности хранилища браузера;
- ограничений производительности для больших настроенных списков;
- покрытия визуальными регрессионными проверками разметки оболочки/списков/форм.

Эти ограничения направлены в `90_traceability.md` как будущие решения или
предложения для backlog, если они затрагивают архитектуру.

## 6. Неподтверждённые свойства

### 6.1. Документационные проверки

Для этой области ожидаются следующие проверки документации:

- отсутствие ссылок на импортированные старые каталоги источников в нормативных документах;
- отсутствие неразрешённых маркеров-заполнителей;
- отсутствие неоднозначных маркеров перевода UI;
- `git diff --check`;
- корректность локальных ссылок на Markdown и исходные файлы.

### 6.2. Неподтверждённые приёмочные требования из старых материалов

Следующие проверки нужны для целевого состояния, но не должны описываться как
уже выполненные на основании текущего набора тестов:

- одинаковое поведение `WorkspaceTemplate`, `SplitExplorerTemplate` и
  `TreeInspectorTemplate` при реальной разметке режимов `split`, `tree` и `workspace`;
- переходы `Context Bar` между Scope, Version и Mode с защитой несохранённых
  изменений;
- сохранение изменений редактора между несколькими узлами, `SaveAll/Validate/Discard`
  и предсказуемая обработка конфликта конкуренции;
- единая индикация изменений в дереве, списке, редакторе свойств и предварительном просмотре;
- пользовательский слой runtime Workflow: индикатор состояния, сводная причина, команда для одного
  объекта и политика групповых операций с учётом выбора;
 - клавиатура/доступность, адаптивная разметка и визуальная регрессия для
  оболочки, списка, формы и шаблонов редактора;
 - эталон производительности для больших настроенных списков и политика
  хранилища браузера/диагностики.

До появления соответствующих тестов и решений эти пункты имеют статус
`будущая проверка` или `открытое решение`, а не `подтверждено кодом`.

## 7. Проверки UI для файлов

Component/smoke-проверки UI должны разделять два паттерна:

- `FileField`: один файл в карточке `View`/`Edit`, списке `View`/`Inline Edit`,
  выбор, замена, очистка, открытие, пустое состояние и длинное имя;
- `FileUploadParameter`: параметр `File` с `Multiple=false/true`, drop-зона,
  системный picker, добавление нескольких файлов, ограничения политики, ошибка отдельного файла,
  повторная попытка и блокировка основной кнопки диалога до успешной проверки.

Для обоих паттернов проверяются `Disabled` и `ReadOnly`, доступность имени файла
как ссылки и отсутствие изменения высоты inline-строки. Серверная ошибка должна
отображаться без потери уже успешных результатов; клиентская предварительная
проверка не заменяет серверную валидацию. Браузерный визуальный тест полного
пользовательского пути остаётся отдельной проверкой runtime-приложения.
