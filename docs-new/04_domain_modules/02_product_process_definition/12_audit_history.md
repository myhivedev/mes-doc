# Аудит и история - 02 Составы и технологии

## 1. Назначение документа

Документ фиксирует, какие изменения объектов модуля `02 Product & Process Definition` должны быть видны в аудите и истории, и где проходит граница между предметной историей модуля и платформенными механизмами.

## 2. Базовое решение

Модуль использует стандартные механизмы Common, Object Runtime, Workflow и Audit History.

Модуль не вводит отдельный журнал изменений для стандартных create/update/archive/delete. Предметная история важна для ревизий и расчета состава.

## 3. События, которые должны попадать в аудит

| Событие | Источник |
|---|---|
| Создание спецификации, технологии, схемы кооперации | Object Runtime Create |
| Изменение рабочих полей и строк коллекций | Object Runtime Update |
| Создание новой ревизии | Предметная операция `CreateNewRevision` |
| Создание копии технологии | Предметная операция копирования |
| Workflow-переходы | Workflow Runtime |
| Заполнение или корректировка дат отправки и утверждения ревизии | Workflow Runtime или Object Runtime Update по workflow-policy |
| Архивирование и восстановление | Workflow Runtime или Common по типу объекта |
| Создание анализа состава | Предметная операция анализа |
| Перерасчет анализа состава | Предметная операция `RunProductCompositionAnalysis` |
| Завершение анализа состава с ошибками или предупреждениями | Предметная операция `RunProductCompositionAnalysis` |
| Изменение условий применимости | Object Runtime Update владельца и строки условия |
| Изменение правила замены номенклатуры | Object Runtime Update `NomenclatureSubstitution` |

## 4. Ревизионная история

Для `ManufacturingBill`, `ProcessDefinition`, `CooperationScheme` в истории должны быть видны:

- исходная ревизия, на основании которой создана новая;
- новая ревизия;
- пользователь и время создания;
- скопированные коллекции;
- измененные при создании параметры;
- состояние lifecycle новой ревизии.

Изменение `SubmittedForApprovalAt` и `ApprovedAt` должно быть видно в истории ревизии независимо от того, выполнено оно workflow-переходом или разрешенной ручной корректировкой.

Если новая ревизия или копия `ProcessDefinition` создает новую связанную индивидуальную спецификацию ТО, история должна показывать обе созданные ревизии и связь между новой технологией и новой спецификацией.

## 5. История продуктивной применимости

Изменение областей использования:

- `UseInPlanning`;
- `UseInProduction`;
- `UseInCosting`;
- `AllowNewOperationalSelection`;
- `ValidFrom`;
- `ValidTo`;
- строки `UseConditions` и их `ParameterValues`;

должно попадать в историю изменений ревизии, потому что эти поля влияют на планирование, производство и калькуляцию.

Изменение `NomenclatureSubstitution`, его периода действия и условий применения должно попадать в историю изменений правила замены, потому что эти данные влияют на разузлование, расчет потребностей и последующую комплектацию.

## 6. Анализ состава

Для `ProductComposition` сохраняются:

- параметры расчета;
- дата норм;
- исходные спецификация, технология и схема кооперации, если они были заданы;
- аналитика условий применимости и значения реквизитов расчетного контекста;
- статус и дата расчета;
- счетчики строк, предупреждений и ошибок;
- сообщения расчета.

Перерасчет существующего `ProductComposition` обновляет текущий расчетный результат: прежние строки результата заменяются новыми строками, а событие перерасчета фиксируется в Audit History.

Если требуется сохранить сравнимую историю старого результата, новый расчет создается как новый `ProductComposition` с теми же параметрами. В этом случае старый результат не изменяется.
