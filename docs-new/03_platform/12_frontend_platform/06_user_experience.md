## 1. Назначение документа

Документ описывает общий пользовательский слой фронтенд-платформы: оболочку
приложения, навигацию, разметку страниц, общие UI-компоненты, отображение
и локализацию, а также разделение профилей приложений `Admin`, `Runtime`, `Studio`.

Документ не дублирует предметную семантику экранов. Каталог ниже показывает,
какие экранные сценарии подтверждены в приложениях и где находится их
функциональный владелец. Для каждого такого сценария здесь фиксируется общий
механизм подключения и отображения, а детали данных, прав и действий остаются
в документе владельца.

### 1.1. Каталог экранов и владельцев

| Раздел или сценарий | Представление или пакет | API | Право | Статус реализации |
| --- | --- | --- | --- | --- |
| Admin: предприятия, пользователи, роли, права и назначения | Провайдеры функций Admin | Tenant Security API | Права сессии | Подтверждено кодом; предметный владелец — Tenant Security |
| Admin: оболочка и общий маршрут | Оболочка Admin и реестр маршрутов | Запуск приложения | Состояние сессии | Подтверждено кодом; владелец общего механизма — фронтенд-платформа |
| Studio: управление контекстом и версиями, Configuration Explorer и Artifact Editor | Настроенные провайдеры функций Studio | Configuration API | Права Configuration | Подтверждено кодом; предметный владелец — Configuration |
| Studio: редактор данных Value Sets | `StudioValueSetDataEditor` | Value Sets API | Права Value Sets | Подтверждено кодом; предметный владелец — Value Sets |
| Studio: каталог и редактор Settings | `settingsFeatureProviderDefinition` | Settings API | Права Settings | Подтверждено кодом; предметный владелец — Settings |
| Runtime: стартовая страница, маршрут runtime и настроенное представление | `RuntimeResolvedRouteHost` и провайдеры runtime | API разрешения и данных runtime | Состояние, переданное сервером/runtime | Частично подтверждено; состав экрана задаётся runtime-контрактом |
| Admin, Runtime, Studio: состояния загрузки, ошибки, пустого результата, сессии и защиты навигации | Общие UI-компоненты и пакеты runtime | Контракты приложения/runtime | Состояние сессии и действия | Подтверждено общими компонентами |

`View` в этой таблице означает конфигурационный контракт Configuration, а не
 самостоятельный экран. Видимый runtime-экран формируется хостом, рендерером,
данными и действиями по контрактам нескольких областей.

## 2. Контракты фронтенда

| Элемент интерфейса | Техническое имя | Ответственность |

| Пользовательский слой объекта | `ObjectViewLayout`, `ObjectTabs`, `ObjectHeaderTitle`, настроенные рендереры | Отображение списка, формы, карточки и рабочего места по разрешённой/настроенной модели. |

## 3. Разделы интерфейса и сценарии

| Профиль приложения | Роль интерфейса | Что описывает фронтенд-платформа |
| --- | --- | --- |
| Admin | Администрирование платформы | Вход/запуск, оболочка, граница навигации Admin, подключение функций и различие удалённой/локальной навигации. |
| Runtime | Рабочее место опубликованного runtime | Стартовая страница, переход от точки входа, маршрут runtime, хост разрешённого представления, навигация runtime и отображение списка/формы/действия. |
| Studio | Авторинг конфигурации | Вход/запуск, оболочка, интеграция контекста Configuration, граница навигации Studio и настроенные провайдеры функций. |

Предметные сценарии внутри профилей остаются у владельцев: Tenant Security
документирует роли/права/пользователей; Configuration — Explorer/редактор;
Value Sets — редактор данных и провайдер функции. ([Tenant Security UX][tenant-security-ux];
[Configuration UX][configuration-ux]; [Value Sets UX][value-sets-ux])

### 3.1. Рабочее место Runtime

Приложение Runtime отображает нейтральную стартовую страницу, если точка входа
runtime не разрешена. Когда серверная часть возвращает коды точки входа, приложение
переходит на
`/runtime/:moduleCode/:objectTypeCode/:viewCode` и отображает
`RuntimeResolvedRouteHost`. Заголовок оболочки, действия заголовка страницы,
группы навигации и защита от потери несохранённых изменений обновляются по разрешённой
модели и состоянию runtime. ([Runtime app][runtime-app])

## 4. Навигация и оболочка приложений

Навигация интерфейса имеет три источника:

| Пункт навигации | Родитель | Цель | Право | Порядок | Источник |
| --- | --- | --- | --- | --- | --- |
| Локальный пункт приложения | Группа реестра функций | Маршрут Admin или Studio | Право сессии, если оно задано сценарием функции | Порядок в реестре | Реестр навигации Admin/Studio |
| Пункт меню runtime | Группа из разрешённого меню | Маршрут runtime или настроенная цель | Состояние, переданное сервером/runtime | Порядок разрешённой модели | Адаптеры `@dmp/runtime-react` |
| Удалённый/эффективный пункт | Группа удалённой/эффективной навигации | Опубликованный путь Admin | Навигация, переданная сервером | Порядок ответа API | `VITE_ADMIN_REMOTE_NAVIGATION_ENABLED`; `FE-DEC-03` |

Обработка целей меню `ExternalUrl` и `Action` в этом драфте не завершена.
Открытое решение отслеживается в `90_traceability.md`.

### 4.1. Общая композиция оболочки

Все три приложения используют общий набор компонентов оболочки и разные
профили навигации. Различия профилей являются частью фронтенд-контракта и не
должны скрываться за одинаковым визуальным представлением.

| Элемент | `Admin` | `Runtime` | `Studio` | Общее требование |
| --- | --- | --- | --- | --- |
| Оболочка | `AppShell`, `TopBar`, `Sidebar`, `PageLayout` | Те же компоненты | Те же компоненты | Структура страницы и жизненный цикл оболочки задаются общими UI-компонентами. |
| Представление меню | Группы | Дерево, включая вложенные пункты | Группы | Представление выбирается профилем и моделью меню; нельзя предполагать один вид для всех приложений. |
| Источник пунктов | Локальная конфигурация, при включённом режиме также эффективная/удалённая навигация | Меню из разрешённого runtime-ответа | Локальный реестр настроенных экранов | Источник должен быть явно определён до построения `Sidebar`. |
| Верхняя панель | Заголовок, пользовательское меню | Заголовок разрешённого представления, пользовательское меню | Заголовок, контекстные элементы, пользовательское меню | Общие элементы используют единые компоненты и локализацию. |
| Состояние боковой панели | `dmp.admin.navigation.<userId>` | `dmp.runtime.navigation.<userId>` | `dmp.studio.navigation.<userId>` | Состояние разделяется по приложению и пользователю. Политика хранения и очистки отслеживается в `90_traceability.md`. |
| Несохранённые изменения | Защита перехода в отдельных потоках | Защита перехода из рабочего места | Состояние редактора и защита перехода в потоках Studio | Переход, который может потерять изменения, должен проходить через общий механизм подтверждения. |

Текущая реализация оболочки подтверждена исходниками приложений и пакета
`@dmp/ui`; состав конкретного предметного экрана в этот общий контракт не
входит. ([Admin app][admin-app]; [Runtime app][runtime-app]; [Studio app][studio-app])

### 4.2. Меню `Admin`

Каноническим локальным описанием меню `Admin` является функция
`createAdminRuntimeMenu`. Представленные ниже маршруты верхнего уровня и их
связи с `viewCode` подтверждены исходниками. ([Admin navigation][admin-navigation];
[Admin routes][admin-routes]; [Admin UI config][admin-ui-config])

| Группа | Пункт | Код пункта | Маршрут | `targetType` | `viewCode` | Правило видимости | Статус |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Основное | Панель | `Admin.Nav.Dashboard` | `/admin/dashboard` | `View` | `Admin.Dashboard` | Видим в локальном меню | Реализовано |
| Основное | Предприятия | `Admin.Nav.Tenants` | `/admin/tenants` | `View` | `Admin.Tenants.List` | Требует `tenantPermissionCodes.read` при построении оболочки | Реализовано |
| Безопасность | Пользователи | `Admin.Nav.Users` | `/admin/users` | `View` | `Admin.Users.List` | Требует `userPermissionCodes.read` при построении оболочки | Реализовано |
| Безопасность | Роли | `Admin.Nav.Roles` | `/admin/roles` | `View` | `Admin.Roles.List` | Требует `rolePermissionCodes.read` при построении оболочки | Реализовано |

Технические свойства локального меню:

| Свойство | Подтверждённое значение |
| --- | --- |
| `menuCode` | `Admin.MainMenu` |
| `moduleCode` | `TenantSecurity` |
| Порядок групп | `Main` — 10, `Security` — 30 |
| Порядок пунктов | Панель — 10, Предприятия — 20, Пользователи — 30, Роли — 40 |
| Режим панели | `persistent` |
| Закрытие после выбора | `closeOnSelect = false` |
| Представление `Sidebar` | Группы, поиск и быстрый доступ выключены |
| Источник локальной проекции | `createAdminNavigationRegistry` и `getAdminNavigationGroups` |

Маршруты деталей, создания и редактирования предприятий, пользователей и
ролей являются вложенными маршрутами предметных функций. Они не являются
отдельными пунктами верхнего уровня меню. Правила доступа к данным и действиям
описываются владельцем Tenant Security; фронтенд-платформа фиксирует только
связь пункта меню с маршрутом и проверкой видимости. Использование
Эффективная/удалённая навигация управляется `VITE_ADMIN_REMOTE_NAVIGATION_ENABLED`;
источник такой навигации остаётся открытым решением `FE-DEC-03`.

### 4.4. Меню `Runtime`

В `Runtime` нет фиксированного списка предметных пунктов меню во фронтенд-коде.
Приложение получает точку входа, затем разрешённое представление вместе с
проекцией меню и строит `Sidebar` адаптером runtime. ([Приложение Runtime][runtime-app];
[Адаптер навигации Runtime][runtime-nav-adapter])

| Источник или этап | Подтверждённое поведение |
| --- | --- |
| `/api/runtime/entry-point` | Возвращает `moduleCode`, `objectTypeCode`, `viewCode` и необязательный `menuCode`; из них строится маршрут `/runtime/{moduleCode}/{objectTypeCode}/{viewCode}`. |
| Разрешение runtime | `RuntimeResolvedRouteHost` получает `RuntimeViewResolveResponse`; его `menu` используется как источник навигации разрешённого представления. |
| Построение групп | `buildRuntimeNavigationGroups` отбирает видимые узлы, сортирует их по `order`, строит группы и вложенные пункты, добавляет `operationMode` и `menuCode` к маршрутам. |
| Представление | `Sidebar` работает в режиме дерева; режим панели и закрытие после выбора берутся из `menu`, с резервными значениями `overlay` и `true`. |
| Нет разрешённого меню | После разрешения представления используется резервная группа «Справочники» и пункт «Номенклатура»; до разрешения меню группы не показываются. |
| Состояние | Используется `dmp.runtime.navigation.<userId>`; переход контролируется защитой от потери несохранённых изменений. |

Следовательно, нормативный документ фронтенд-платформы описывает алгоритм
построения и отображения меню `Runtime`, а не перечисляет предметные пункты.
Состав меню и доступность пунктов приходят в runtime-контракте от сервера;
семантика артефактов, объектов, представлений и действий остаётся у владельцев
соответствующих контрактов.

### 4.5. Требования к UX/UI меню и оболочке

| ID | Требование | Подтверждение текущим кодом | Статус для черновика |
| --- | --- | --- | --- |
| FE-UX-01 | Стабильные `menuCode`, коды пунктов, маршруты и связь с `viewCode` должны использоваться для построения меню и заголовка текущего маршрута. | Подтверждено реестрами `Admin` и `Studio`, а также адаптером `Runtime`. | Текущее требование |
| FE-UX-02 | Скрытый пункт меню не является заменой проверки права; серверная часть должна повторно проверять доступ к операции и данным. | Фильтрация пунктов по сессии есть в `Admin`; runtime использует `visible` из разрешённого ответа. | Текущее требование; детали права у владельца Security. |
| FE-UX-03 | Активный маршрут и выбор пункта должны быть согласованы с фактическим URL, включая параметры runtime. | Подтверждено `activePath` и картой путей адаптера runtime. | Текущее требование |
| FE-UX-04 | Состояние боковой панели должно храниться раздельно для приложения и пользователя. | Подтверждено ключами `dmp.*.navigation.<userId>`. | Текущее требование; политика хранения открыта в `FE-DEC-06`. |
| FE-UX-05 | Переход из изменённого экрана должен предупреждать о возможной потере изменений. | Подтверждено защитой перехода в Runtime и отдельными потоками Studio. | Текущее требование; единая сессия редактора (`editor session`) открыта в `FE-DEC-10`. |
| FE-UX-06 | `ExternalUrl` и `Action` должны иметь определённое поведение, прежде чем станут гарантированными целями меню. | Для `Action` адаптер не создаёт кликабельный пункт; полная семантика не закреплена. | Открыто, `FE-DEC-02`; не считать частью гарантии MVP. |
| FE-UX-07 | Поиск и быстрый доступ должны иметь единый контракт, если будут включены. | В `Admin` и `Studio` явно выключены. | Будущая доработка, отдельное решение. |
| FE-UX-08 | Адаптивность, клавиатурная навигация, доступность и визуальный эталон должны иметь проверяемые критерии. | Отдельные UI-проверки есть, общего эталона для трёх приложений нет. | Открыто, `FE-DEC-07` и `FE-DEC-16`. |
| FE-UX-09 | Локальные конфигурации `Admin` и `Studio` следует по возможности приводить к канонической модели артефактов и runtime, добавляя фронтенд-расширения только для сложных форм, которые общий runtime пока не поддерживает. | Общая модель runtime и локальные реестры уже существуют, но полного равенства моделей нет. | Открыто, `FE-DEC-14`; не формулировать как требование получать конфигурацию этих приложений с сервера. |
| FE-UX-10 | Узел-заполнитель (`placeholder`) должен быть явно отличим от готового предметного сценария. | Тип узла хранится в реестре `Studio`; часть пунктов ведёт на заглушки. | Текущее требование |

## 5. Локализация

Фронтенд-платформа использует словари `ru-RU` и `en-US` через `@dmp/shared`.
Локаль фронтенда определяется из кандидатов пользователя, tenant и браузера и
хранится в локальном хранилище браузера (`local storage`). Тексты приложения и
конкретных функций берутся из словарей фронтенда или настроенных значений
`ConfigText`. Предметные значения, локализованные серверной частью, остаются у
области, которая их
возвращает.

| Ресурс | Ключ | Язык | Резервное значение | Владелец | Покрытие |
| --- | --- | --- | --- | --- | --- |
| Словарь приложения | Ключ словаря | `ru-RU`, `en-US` | Резервное значение из `@dmp/shared` | Фронтенд-платформа / приложение | Подтверждено словарями и `resolveI18nLocale` |
| Настроенный текст | `ConfigText` | Язык разрешённой модели | Резервное значение по контракту Configuration | Configuration | Используется в настроенном пользовательском слое |
| Предметное значение | Поле, переданное серверной частью | Язык контекста серверной части | Определяется серверной частью | Область-владелец данных | Не синтезируется фронтендом |

## 6. Ограничения

Фронтенд-платформа должна соблюдать следующие ограничения:

- не выводить право из того, что элемент UI скрыт;
- не создавать подписи для значений ссылок и области (`reference`/`scope`), если API не вернул их
  отображаемые значения;
- не угадывать фильтры и операторы списка вне контрактов runtime и настроенной модели;
- не создавать локальную постоянную семантику схемы для `View`, `Action` или `Menu`;
- не переносить сценарии конкретных функций из документов владельцев в этот документ.

### 6.1. Требования из старых UI-материалов, не являющиеся текущей гарантией

Старые материалы описывают более широкий целевой UX, чем подтверждено текущим
кодом. Для фронтенд-платформы сохраняются следующие общие требования и границы:

| Требование | Что подтверждено сейчас | Что нужно зафиксировать отдельно |
| --- | --- | --- |
| Единый runtime для Admin и Studio | Общие `@dmp/runtime-contracts`, `@dmp/runtime-react`, `@dmp/ui` и реестр шаблонов существуют. | Проверить, что каждый шаблон имеет самостоятельную семантику разметки и одинаковые критерии приёмки для всех профилей приложений. |
| `Context Bar` для Studio | `ContextBar` и состояние контекста Configuration в Studio присутствуют. | Зафиксировать полный контракт Scope/Version/Base/Mode, переходы между режимами и поведение при несохранённых изменениях. |
| Общая сессия редактора | Есть состояние несохранённых изменений Studio, `SaveAll`, `Validate`, `Discard` и защита навигации в отдельных потоках. | Проверить единое хранилище сессии, сохранение изменений между узлами, конфликт конкуренции и политику `Reload/Merge`; автоматическое сохранение остаётся будущим расширением. |
| Единое отображение изменений | В Studio есть проекции проблем и состояний отображения. | Нет общего эталона приёмки для приложений по `Changed`, `Added`, `Deleted`, `Inherited`, `Override`, `Conflict` в списке, дереве, редакторе и предварительном просмотре. |
| Сложные шаблоны разметки редактора | Есть переиспользуемые `TreeView`, `ListViewLayout` и зарегистрированные коды шаблонов. | `PropertyInspectorCard`, `ContextMetaPanel`, `DiffPanel`, `EffectiveSourcePanel`, `ValidationIssuePanel`, `GraphPanel`, изменение размера, ленивое дерево и `WizardTemplate` не считаются готовыми общими возможностями. |
| Workflow в пользовательском слое runtime | Runtime имеет панель Workflow, проекцию политики состояния и пути исполнения команд/действий. | Полный UX-контракт индикатора состояния, заблокированных причин, истории, действий строки и групповой политики требует совместной проверки с Workflow и Object Runtime. |

Это не означает, что предметные экраны нужно описывать заново во фронтенд-платформе.
Здесь фиксируются общие механизмы UI, состояние клиента и правила отображения.
Например, для экрана редактора артефакта здесь описываются оболочка, навигация,
состояние несохранённых изменений и переиспользуемые элементы управления, а
поля, операции и правила артефакта остаются в Configuration. Аналогично, семантика
Workflow, Object Runtime и Tenant Security остаётся у их владельцев. Статусы и
источники приведены в `90_traceability.md`.

## 7. Работа с файлами

Для файлов используются два presentation-паттерна.

### 7.1. Свойство объекта: `FileField`

`FileField` предназначен для одного значения свойства типа `File`.

| Режим | Поведение |
| --- | --- |
| Карточка, `View` | Имя файла является ссылкой на открытие/предпросмотр; рядом показываются иконка типа, размер и действие открытия. При отсутствии файла показывается `—`. |
| Карточка, `Edit` | Компактное поле: выбранный файл, размер, открыть, заменить и очистить; без файла — «Выбрать файл». |
| Список, `View` | Компактное имя файла-ссылка с усечением длинного имени и tooltip с полным именем. |
| Список, `Inline Edit` | Имя файла, заменить и очистить; без файла — «Выбрать файл». Высота строки не меняется. |

Компонент не поддерживает множественный выбор. В состояниях `Disabled` и
`ReadOnly` поле не позволяет выбрать, заменить или очистить файл, но ссылка на
сохранённый файл остаётся доступной. В режиме `Edit` изменение считается частью
текущего сеанса редактирования и применяется при сохранении объекта.

### 7.2. Параметр действия: `FileUploadParameter`

`FileUploadParameter` используется для параметра action/command типа `File`.
При `Multiple=false` он работает с одним файлом, а при `Multiple=true` — с
несколькими. Для одного файла drop-зона после выбора заменяется компактной строкой
с именем, размером и действиями открыть, заменить и очистить. Для нескольких
файлов drop-зона остаётся доступной, а ниже отображается отдельная строка для
каждого выбранного файла.

Компонент показывает ограничения политики непосредственно под областью выбора:
разрешённые расширения/MIME, максимальный размер и максимальное число файлов.
Для каждой ошибки доступна повторная попытка или удаление файла. Основное
действие диалога недоступно, пока обязательный файл не выбран, выполняется
загрузка или нарушена клиентская проверка. `Disabled` и `ReadOnly` блокируют
изменение, но не открытие уже выбранного файла.

В обоих паттернах показываются только пользовательские метаданные descriptor:
имя, размер, состояние и доступные действия. Физический путь и бинарное
содержимое в интерфейс не выводятся; клиентская проверка не заменяет серверную.
