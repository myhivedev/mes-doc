# Постановка задачи: разработка архитектурной документации новой версии Platform Foundation

## 1. Цель задачи

Разработать комплект архитектурной документации для **новой версии Platform Foundation**, который станет рабочей основой для команды разработки.

Документация должна позволять:

1. разработчикам понимать, **что именно необходимо реализовать**;
2. понимать, **в каком порядке необходимо выполнять разработку**;
3. понимать зависимости между компонентами и задачами;
4. лидам Backend и Frontend формировать на основании документации **детальный backlog разработки**;
5. команде разработки независимо реализовывать отдельные компоненты, сохраняя единые архитектурные принципы и контракты.

Документация должна быть ориентирована прежде всего на **практическое использование разработчиками**, а не только на архитектурное описание системы.

Документация должна быть написана для того, чтобы по ней программировали, а не для того, чтобы её было сложно читать.

---

# 2. Исходные материалы

При разработке документации необходимо использовать в качестве исходной базы:

* целевую архитектуру новой распределённой платформы;
* существующую документацию Platform Foundation;
* документацию по взаимодействию компонентов платформы;
* документы по Configuration, Object Runtime, Workflow, Rules, Value Sets, Settings, Numbering, Audit, Integration Events, Content Storage и Frontend Platform;
* согласованный план разработки из **29 этапов**.

Документация должна учитывать, что новая версия платформы разрабатывается **с нуля**.

Существующая реализация используется как источник требований и существующего поведения, но не должна автоматически переноситься в новую реализацию.

Если существующее техническое решение препятствует требованиям новой архитектуры, архитектор должен предложить более подходящее решение.

---

# 3. Границы платформы

Документация должна чётко соблюдать границы **Platform Foundation**.

В платформу входят общие технические механизмы, которые будут использовать будущие MES-модули.

В частности:

* Platform Context;
* Tenant Management;
* аутентификация и авторизация;
* роли и права;
* Audit / History;
* Object Model / Object Runtime;
* CRUD;
* Configuration;
* Value Sets;
* Settings;
* Numbering;
* Rules;
* Workflow Framework;
* Integration Events;
* Outbox / Inbox;
* Idempotency / Deduplication;
* Integration Framework;
* Content Storage;
* механизмы Central ↔ Local;
* Platform SDK / Extension API;
* общие Frontend-компоненты;
* Admin;
* Studio;
* Platform Execution.

**В Platform Foundation не должна включаться конкретная бизнес-функциональность MES.**

Необходимо также исключить из состава Foundation Low-Code / No-Code механизмы.

Studio является инструментом технической настройки платформы, а не средством визуального программирования бизнес-логики.

---

# 4. Что должна обеспечить архитектурная документация

Для каждого крупного компонента платформы документация должна отвечать на простые практические вопросы:

### Что это?

Краткое описание назначения компонента.

### Зачем он нужен?

Какую проблему решает компонент и какие другие компоненты используют его возможности.

### Что он предоставляет?

Перечень основных функций и публичных возможностей.

### Какие данные он хранит?

Основные сущности, данные и их назначение.

### С чем он взаимодействует?

Перечень зависимостей и интерфейсов взаимодействия.

### Какие API / контракты предоставляет?

Необходимо описать основные API, DTO, события, команды или другие публичные контракты там, где это применимо.

### От чего он зависит?

Явные зависимости от других компонентов платформы.

### Что необходимо реализовать?

Конкретный перечень функциональных задач для Backend и Frontend.

### В каком порядке реализовывать?

Необходимо определить последовательность реализации компонентов и задач.

### Когда компонент считается готовым?

Необходимо сформулировать понятные критерии завершения разработки компонента.

---

# 5. Последовательность разработки

Документация должна содержать **единый порядок реализации платформы**, соответствующий утверждённому плану из 29 этапов.

Для каждого этапа необходимо определить:

* какие компоненты разрабатываются;
* какие задачи входят в этап;
* какие компоненты должны быть готовы до начала работ;
* какие API и контракты должны быть определены;
* какие задачи могут выполняться параллельно;
* какие задачи блокируют последующие работы;
* результат этапа.

Особое внимание уделить формированию **цепочки зависимостей**.

Например:

> Platform Foundation → Object Model → Object Runtime → Configuration → Workflow → Execution

и

> Platform Foundation → Event Model → Outbox / Idempotency → Synchronization → Central ↔ Local.

Документация должна позволять лиду однозначно определить:

> **«Эту задачу можно брать в работу сейчас»**

или

> **«Эта задача зависит от другой задачи, поэтому её необходимо выполнять позже».**

---

# 6. Декомпозиция до уровня backlog

Архитектурная документация не должна останавливаться на уровне:

> «Реализовать Configuration Service».

Для каждого крупного компонента необходимо выполнить декомпозицию до уровня, достаточного для формирования backlog.

Например:

**Configuration**

→ модель конфигурации
→ scopes
→ draft
→ version
→ publication
→ effective configuration
→ schema registry
→ artifact storage
→ validation
→ configuration package
→ local projection
→ activation
→ rollback
→ API
→ frontend contracts.

При этом конкретная глубина декомпозиции должна определяться сложностью компонента.

**Не требуется превращать архитектурный документ в подробное техническое задание на каждую строку кода.**

Задача архитектора — определить архитектурно значимые элементы, контракты, зависимости и последовательность реализации.

---

# 7. Backend и Frontend

Необходимо разделять задачи:

### Backend

Для Java / Spring Boot необходимо определить:

* сервисы и модули;
* domain/application components;
* API;
* контракты;
* модели данных;
* события;
* команды;
* интеграции;
* транзакционные границы;
* взаимодействие с PostgreSQL;
* взаимодействие с Kafka;
* механизмы безопасности;
* механизмы расширения.

### Frontend

Для React необходимо определить:

* приложения;
* страницы;
* основные пользовательские сценарии;
* frontend-модули;
* API integration;
* общие компоненты;
* runtime contracts;
* UI configuration;
* extension points.

Особенно важно сохранить независимость:

**Admin → Admin API**

**Studio → Studio API**

**Platform Execution → Execution API**

Одно приложение не должно использовать API другого приложения для выполнения собственных функций.

---

# 8. Центральный и локальный контуры

Отдельный раздел документации должен описывать распределённую модель:

**Central → Local**

и

**Local → Central**.

Необходимо определить:

* какие данные могут передаваться;
* кто является владельцем данных;
* кто инициирует обмен;
* какие API / события используются;
* как формируется сообщение;
* как обеспечивается доставка;
* как выполняется повторная доставка;
* как обнаруживаются дубликаты;
* как подтверждается обработка;
* что происходит при недоступности Центрального контура;
* как восстанавливается синхронизация;
* как доставляется конфигурация;
* как выполняется её проверка;
* как выполняется активация;
* как выполняется rollback;
* как определяется версия конфигурации.

Базовый принцип:

> **Local должен продолжать производственную работу при недоступности Central.**

Необходимо отдельно описать, какие функции остаются доступными локально при потере связи с Центральным контуром.

---

# 9. API и контракты

Архитектурная документация должна определить публичные контракты между основными компонентами.

Для API необходимо по возможности указывать:

* назначение;
* endpoint;
* HTTP method;
* основные параметры;
* request;
* response;
* ошибки;
* права доступа;
* область действия Tenant / Site;
* особенности идемпотентности.

Для событий необходимо определить:

* Event Type;
* Event ID;
* Correlation ID;
* Tenant / Site;
* время события;
* версию;
* payload;
* правила обработки;
* retry;
* deduplication.

Не требуется описывать каждый внутренний метод класса.

---

# 10. Данные и владение данными

Для основных сущностей необходимо определить:

* кто является владельцем данных;
* где данные хранятся;
* кто имеет право их изменять;
* кто может только читать данные;
* какие данные публикуются в другие контуры;
* какие данные не должны покидать локальный контур.

Особое внимание уделить:

* Tenant;
* Configuration;
* Object Model;
* Value Sets;
* Settings;
* Workflow;
* Audit;
* Integration Events;
* Inbox / Outbox;
* Content;
* Runtime projections.

---

# 11. Архитектурные диаграммы

Документация должна содержать актуальные диаграммы, отражающие описанную архитектуру.

Минимальный набор:

1. **Логическая архитектура**
2. **Диаграмма развертывания**
3. **Диаграмма потоков данных**
4. диаграмма основных компонентов Platform Foundation;
5. диаграмма взаимодействия Central ↔ Local;
6. диаграмма взаимодействия Admin / Studio / Platform Execution;
7. при необходимости — отдельные диаграммы сложных механизмов Configuration, Object Runtime, Workflow и Synchronization.

Диаграммы должны соответствовать тексту документации.

---

# 12. Требования к понятности документации

### Это является обязательным требованием.

Документация предназначена для использования **разработчиками, лидами и техническими руководителями**.

Поэтому текст должен быть:

* однозначным;
* конкретным;
* коротким там, где не требуется подробное объяснение;
* структурированным;
* технически точным;
* ориентированным на практическую реализацию.

**Не следует усложнять текст ради придания ему академического или формального стиля.**

Необходимо избегать:

* редких терминов, если существует обычный технический термин;
* длинных сложноподчинённых предложений;
* чрезмерно абстрактных формулировок;
* философских и методологических рассуждений;
* нескольких смыслов в одном предложении;
* формулировок, которые можно трактовать по-разному;
* описания очевидных вещей большим количеством текста.

Предпочтительный стиль:

> **Короткое предложение → конкретное утверждение → конкретное действие.**

Например, вместо:

> «В целях обеспечения консистентности распределённого состояния конфигурационного пространства целесообразно предусмотреть механизм семантически согласованной публикации соответствующих артефактов...»

писать:

> **«Конфигурация публикуется версиями. Local получает версию, проверяет её и активирует только после успешной проверки.»**

Или вместо:

> «Необходимо обеспечить реализацию соответствующего механизма обработки повторных сообщений...»

писать:

> **«Consumer должен поддерживать повторную доставку сообщения. Повторная обработка одного Event ID не должна изменять данные второй раз.»**

Документ должен быть написан так, чтобы **Senior Java-разработчик или Senior React-разработчик мог прочитать описание задачи и понять, что именно от него требуется**.

---

# 13. Формат описания архитектурных решений

Для существенных архитектурных решений рекомендуется использовать единый шаблон:

| Раздел                | Содержание                        |
| --------------------- | --------------------------------- |
| Проблема              | Что необходимо решить             |
| Решение               | Как предлагается решить           |
| Причина               | Почему выбран именно этот вариант |
| Ограничения           | Какие есть ограничения            |
| Взаимодействия        | С какими компонентами связан      |
| Влияние на разработку | Что необходимо реализовать        |
| Зависимости           | От каких компонентов зависит      |
| Последовательность    | Когда реализуется                 |

Не следует создавать ADR или другие формальные документы там, где решение очевидно и не требует отдельного обоснования.

---

# 14. Итоговый результат

По завершении задачи должен быть подготовлен комплект документов, который позволяет перейти от архитектуры непосредственно к разработке.

В частности, лид разработки должен иметь возможность взять документ:

> **Architecture → Component → Capability → Development Task**

и на его основе сформировать backlog.

В результате документация должна содержать:

1. целевую архитектуру платформы;
2. описание компонентов;
3. границы ответственности компонентов;
4. API и основные контракты;
5. модели данных и владение данными;
6. взаимодействие компонентов;
7. взаимодействие Central ↔ Local;
8. Admin / Studio / Platform Execution;
9. Frontend / Backend границы;
10. архитектурные диаграммы;
11. зависимости между компонентами;
12. последовательность разработки;
13. декомпозицию до уровня, достаточного для формирования backlog;
14. критерии завершения разработки компонентов.

---

# 15. Главный критерий качества результата

Архитектурная документация считается качественной, если после её изучения **лид разработки без дополнительного архитектурного исследования может сформировать backlog для реализации соответствующего этапа**.

Документ не должен отвечать только на вопрос:

> **«Как устроена система?»**

Он должен также отвечать на вопросы:

> **«Что необходимо разработать?»**

> **«В каком порядке это разрабатывать?»**

> **«От чего зависит эта задача?»**

> **«Какой результат должен получить разработчик?»**

> **«Как понять, что компонент реализован в соответствии с архитектурой?»**

**Иными словами, задача архитектора — не просто описать будущую систему, а подготовить архитектурную основу, по которой команда сможет её последовательно разработать.**

### Я бы ещё добавил архитектору одну короткую фразу в начало постановки

> **Документация должна быть написана для того, чтобы по ней программировали, а не для того, чтобы её было сложно читать.**

Это довольно хорошо задаёт нужный тон. При этом требование не запрещает архитектору использовать профессиональную терминологию — наоборот, **термины должны быть точными, но формулировки простыми**.

И ещё один момент, который я считаю принципиальным: я бы **не требовал от архитектора заранее детализировать backlog до уровня отдельных Jira-задач**. Иначе он фактически начнёт выполнять работу лидов. Его зона ответственности — определить **архитектурно значимые компоненты, контракты, зависимости, границы и порядок реализации**. А уже лиды превращают это в конкретные User Story / Task / Sub-task.
