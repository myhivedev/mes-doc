# Бэклог реализации — 01 General Master Data v1

## 1. Назначение документа

Документ задает бэклог реализации `General Master Data v1` на основе:

- `00_module_overview.md`;
- `01_scope.md`;
- `02_domain_model.md`;
- `03_object_runtime_model.md`;
- `04_workflows.md`;
- `05_rules.md`;
- `06_ui_views.md`;
- `11_permissions.md`;
- `13_operations.md`;
- `90_traceability_pr01.md`;
- анализа текущей структуры `src/Modules`, реализаций Common и демонстрационного модуля Product Definition.

Документ является планом реализации. Нормативная семантика GMD остается в перечисленных дизайн-документах.

## 2. Текущее состояние реализации

На момент подготовки бэклога:

- производственный модуль `GeneralMasterData` отсутствует;
- каталог `DMP.Modules.ProductDefinition` не содержит целевой реализации объектов GMD;
- `CommonObject`, `CommonCatalogObject`, их runtime-контракты и baseline-конфигурация уже существуют в `DMP.Modules.Common`;
- в demo-контуре есть реализация `Nomenclature`, показывающая использование Object Runtime, workflow, settings и permissions, но ее модель и stable codes не являются контрактом GMD;
- доменные классы, persistence-схема, миграции, runtime-контракты, baseline, права и прикладные функции GMD не реализованы;
- готовность платформенных зависимостей должна проверяться до начала соответствующего этапа, а не заменяться временной логикой внутри GMD.

Следствие: GMD создается как новый production-модуль. Перенос demo-модели целиком не планируется; допустимо переиспользовать только платформенные паттерны и инфраструктурные решения.

## 3. Зафиксированные решения и границы

- Все объекты GMD принадлежат предприятию и имеют `TenantId`.
- Каталоговые объекты наследуются от `CommonCatalogObject`, строки, связи и некаталоговые объекты — от `CommonObject`.
- `Presentation` не хранится как обязательное поле, `Status` не добавляется ко всем объектам.
- Жизненный цикл включается только для `Nomenclature`, `NomenclatureKind` и `NomenclatureParameter`.
- Основной API модуля — Object Runtime; ручные endpoints допустимы только для операций, не выражаемых его контрактом.
- `UnitOfOperation` — единая модель пересчета с ровно одним владельцем и ровно одной целью.
- Значения реквизитов хранятся в отдельных типизированных строках коллекций владельцев, а не в универсальном JSON-хранилище.
- `Pack` — единый тип для упаковки набора и индивидуальной упаковки НП; вид определяется владельцем.
- Значение `SerialNumber.SerialNumber` уникально для номенклатуры в пределах предприятия. Технический ключ уникальности: `(TenantId, NomenclatureId, SerialNumber)`; исполнение НП, изготовитель, год и номер комплекта в ключ не входят.
- `NomenclatureParameterAssignment.DefaultValue` хранится тем же набором типизированных колонок, что и строки значений реквизитов: `ValueType`, `StringValue`, `NumberValue`, `BooleanValue`, `DateTimeValue`, `ReferenceCode`, `JsonValue`. Для несоставного типа заполняется ровно одна колонка значения, соответствующая `ValueType`.
- Общее назначение `NomenclatureParameterAssignment` имеет `NomenclatureKind = null` и `Nomenclature = null`. Оно создается и изменяется в карточке `NomenclatureParameter`, защищается правом изменения параметра и наследует его `TenantId`. Для одного параметра в пределах предприятия допускается не более одного активного общего назначения. Назначения на вид НП и конкретную НП в карточке параметра показываются только для чтения и редактируются в карточках своих владельцев.
- Неоднозначные цепочки пересчета запрещены. Для заданного контекста между исходной упаковкой или единицей операции и базовой ЕИ НП должен существовать не более чем один активный путь. Если найдено несколько допустимых путей, конфигурация считается ошибочной; GMD возвращает стабильную предметную ошибку и не выбирает путь по приоритету.
- GMD запускается на пустой БД. Миграция данных из demo `ProductDefinition.Nomenclature` не выполняется; demo-модуль не является источником production-данных GMD.
- Фактические партии, транспортные единицы, остатки, движения и документы не принадлежат GMD.
- Numbering, машиночитаемая идентификация, ValueSetData, IAM, Audit History и Integration Foundation остаются платформенными зависимостями.
- `Nomenclature.IsMain` и `Nomenclature.BlankSize` не реализуются в текущей версии GMD. Статус ожидания аналитического уточнения в исходных проектных документах сохраняется для возможного последующего развития модели.

## 4. Зависимости реализации

### 4.1. Внешние зависимости

| Зависимость | Что требуется GMD | Блокирует |
|---|---|---|
| `00 Common` | Базовые типы, системные поля, archive/restore/delete policy, разрешение сохраненных архивных ссылок | Все объекты GMD |
| Object Runtime | Контракты, list/lookup/details, составные коллекции, отдельные операции строк, validators/handlers, вычисляемое presentation | Весь пользовательский контур |
| Workflow Runtime | Состояния, команды, guard-проверки, история, синхронизация архива | Публикация НП, видов и реквизитов |
| ValueSetData | Типы контактов контрагентов, политики контроля, типы реквизитов и другие настраиваемые общие списки | Полноценные mutations и публикация |
| IAM / Tenant Security | Права объектов, действий и ролей в области предприятия | Приемка UI и runtime API |
| Audit History | Аудит mutations, переходов и системных обработчиков | Финальная приемка |
| Platform Numbering | Автонумерация поддерживаемых полей | Опциональные сценарии `Nomenclature.Code`, `SerialNumber.SerialNumber` |
| Машиночитаемая идентификация | Подключаемая capability объектов | Соответствующая часть трассировки ПР01 |
| Integration Foundation | Полноценное сопоставление с внешними системами | Не блокирует локальный GMD v1 |
| Модули — владельцы внешних ссылок | Проверка существования, tenant scope и предметной доступности внешнего объекта | Конкретные внешние поля НП и `Lot`-пересчеты |

### 4.2. Зависимости между сущностями GMD

| Слой | Сущности | Зависит от |
|---|---|---|
| Базовые справочники | `Unit`, `Contractor`, `ContractorGroup`, `NomenclatureGroup` | Common, tenant scope, системные enum классификации контрагента и ValueSetData для типов контактов |
| Классификация и схема | `NomenclatureParameter`, enum values, `NomenclatureKind`, assignments | `Unit`, ValueSetData, Workflow Runtime |
| Упаковочные справочники | `PackSet`, `TransportUnitType` | `Unit`; ссылка на НП может подключаться после появления НП |
| Ядро номенклатуры | `Nomenclature` | `Unit`, группы, виды, контрагенты, `PackSet`, ValueSetData, внешние reference contracts |
| Дочерние объекты НП | `NomenclatureVariant`, `SerialNumber`, `Pack` | `Nomenclature`; дополнительно `Contractor`, `PackSet`, `Unit` |
| Пересчеты | `UnitOfOperation` | `Unit`, все поддерживаемые владельцы и цели; внешний `Lot` подключается адаптером |
| Значения реквизитов | три типа parameter value | схема реквизитов, assignments, НП, варианты и серийные номера |
| Сквозное поведение | lifecycle, UI, permissions, audit | завершенные доменные вертикали и runtime-контракты |

## 5. Приоритеты и оценки

Приоритеты:

```text
P0 — блокирует создание корректной модели или первого сквозного среза
P1 — обязательное поведение GMD v1
P2 — завершение UI, интеграций, тестов и сопровождения
Decision — аналитическое решение, требующее подтверждения
```

Относительные оценки:

```text
S  — локальная доработка
M  — несколько связанных компонентов
L  — сквозная доработка одной доменной вертикали
XL — изменение нескольких вертикалей или платформенная интеграция
```

Оценки относительные и не являются календарным планом.

## 10. Открытые вопросы и принятые решения

### Блокируют модель или приемку

Блокирующих вопросов нет. `Nomenclature.ApplicationArea` и `UnitOfOperation.ApplicationArea` являются независимыми признаками с разными доменными смыслами и не сравниваются между собой.

### Открытые вопросы, влияющие на границу первого релиза

1. Какие внешние ссылки `Nomenclature` должны реально работать в первом релизе при отсутствии соответствующих модулей, а какие поля нужно временно скрыть в baseline views?
2. Нужен ли `Lot` как владелец `UnitOfOperation` уже в GMD v1, если модуль партий еще не поставлен, или достаточно заранее совместимого adapter-контракта?
3. Какие поля обязательно поддерживают Platform Numbering в v1: только `Nomenclature.Code` и `SerialNumber.SerialNumber` или более широкий набор?
4. Для каких типов GMD должна быть включена машиночитаемая идентификация в baseline, а для каких — только возможность включения настройкой предприятия?
5. Требуется ли разделить права на типовые упаковки `PackSet` и индивидуальные упаковки `Nomenclature`, либо единое право `Pack` приемлемо для v1?
6. Нужна ли проверка входящих ссылок из других модулей при `ReturnToDraft`, несмотря на то что текущая спецификация GMD ее исключает?

Открытые вопросы 1–6 допускают реализацию через feature/configuration boundary, если это отдельно согласовано. Они не блокируют начало `GMD-09`, пока отсутствующие внешние возможности удерживаются за adapter/configuration boundary и не порождают фиктивные сущности GMD.

### Принятые решения

1. Поля `Nomenclature.IsMain` и `Nomenclature.BlankSize` в текущей версии GMD не реализуются.
2. `SerialNumber.SerialNumber` уникален для номенклатуры в пределах предприятия. Технический ключ: `(TenantId, NomenclatureId, SerialNumber)`.
3. Общее назначение `NomenclatureParameterAssignment` имеет `NomenclatureKind = null` и `Nomenclature = null`, создается и изменяется в карточке `NomenclatureParameter` и наследует `TenantId` параметра. Для одного параметра в пределах предприятия допускается не более одного активного общего назначения.
4. Для заданного контекста пересчета допускается не более одного активного пути к базовой единице НП. Неоднозначные цепочки запрещены; автоматический выбор одного из путей по приоритету не выполняется.
5. `Nomenclature.ApplicationArea` и `UnitOfOperation.ApplicationArea` относятся к разным доменным областям, используют разные enum-типы и не сравниваются между собой.
6. `Contractor.Type` является обязательным одиночным системным enum `ContractorType`: `LegalEntity = 0`, `IndividualPerson = 1`, `SeparateDepartment = 2`.
7. `Contractor.Category` является обязательным флаговым системным enum `ContractorCategoryFlags`: `Supplier = 1`, `Manufacturer = 2`, `Builder = 4`, `Customer = 8`. Комбинации флагов хранятся непосредственно в `Contractor`; задача `plans/024_valueset_multiselect_object_member_backlog.md` к этому полю больше не относится.
8. Изготовитель определяется наличием флага `ContractorCategoryFlags.Manufacturer`; tenant-настройка `ManufacturerCategoryCode` и соответствующий host-адаптер не используются. `ContractorContactType` остается tenant-настраиваемым ValueSet и публикуется с начальными значениями `Supervisor` и `ContactPerson`.
9. Реквизиты контрагента в v1 проверяются без контрольных сумм и без зависимости от страны: ИНН — 10/12 цифр, КПП — 9 символов российского формата, ОГРН/ОГРНИП — 13/15 цифр, ОКПО — 8/10 цифр; e-mail имеет базовую синтаксическую проверку, телефон допускает цифры, пробелы и `+()-`. Все поля необязательны.

Статусы «ожидают ответ аналитика» в исходных предметных документах сохраняются без изменений; этот раздел отражает рабочие решения именно для реализации беклога.
