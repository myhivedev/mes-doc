# Требования к результатам работы по архитектуре Platform Core

## 1. Цель

За две недели руководитель разработки и технический архитектор должны по сводному комплекту проектной документации и исходному коду MVP:

- подтвердить фактическое состояние платформенного ядра;
- принять целевую архитектуру на Java и PostgreSQL;
- закрыть критические архитектурные вопросы;
- подготовить план перевода текущего MVP на стек для промышленной эксплуатации.

Требуется комплект решений и план, достаточные для начала реализации.

Сейчас материалы по Platform Core в `docs` являются рабочей документацией:
они разрознены по папкам и документам, включают сводные описания, исходные
концепции, требования и backlog, имеют разную степень детализации и не образуют
единого подтвержденного исходного комплекта. Отдельные статусные формулировки могут требовать
проверки по текущему коду MVP. В течение первой недели на
их основе будет подготовлен сводный комплект проектной документации по ядру.

На начало двухнедельного архитектурного этапа этот комплект используется
вместе с исходным кодом и тестами MVP. По уже реализованным возможностям нужно
подтвердить фактическое состояние, выявить расхождения и определить, что
сохраняется или изменяется при переходе на Java. По отсутствующим возможностям
нужно принять архитектурные решения и подготовить план реализации.

## 2. Исходное состояние

Текущий MVP реализован как модульный монолит (модули взаимодействуют между собой через шину событий или api) на .NET 9, ASP.NET Core, EF Core и SQL Server.

В Platform Core присутствуют следующие проекты и возможности:

| Capability | Текущее состояние |
|---|---|
| Building Blocks | Базовые предметные и инфраструктурные примитивы и контексты запроса |
| Tenant Security / IAM | Предприятия, площадки, пользователи, роли, права и назначения |
| Configuration Platform | Области действия конфигураций, версии конфигураций, черновики, публикация/архивирование, базовая и эффективная конфигурация; каноническая модель `ArtifactDocument` / `ArtifactNode` / `ArtifactValue`, реестр схем, сервисы редактирования и runtime-материализации |
| Runtime Facade | Клиентский слой Runtime API: получение точки входа и опубликованной конфигурации представлений, варианты выбора для ссылочных полей, списки и подробные данные объектов, создание/изменение/удаление объектов, действия объектов, состояние и команды Workflow. Логика объектов и Workflow реализуется в отдельных возможностях |
| Object Runtime | Стандартный путь уже реализован через `BusinessObjectContract`, `ObjectRuntimeDescriptor`, `GenericRuntimeObjectProvider` и `ObjectMutationPipeline`; остаются отдельные расширения и доведение до промышленной эксплуатации |
| Report Runtime | `ExecuteReportService` уже выполняет настроенный отчет: параметры, фильтры, запрос строк через `Object Runtime` и формирование служебного XML; реализован ограниченный набор сценариев |
| Output Runtime | `GenerateOutputService` уже получает опубликованный Output, запускает отчет и вызывает Java Report Service; в MVP подтверждены источники `Report` и режимы `Download`/`Inline` |
| Dataset / Read Query Capability | В `Object Runtime` есть `Object Dataset` для `List`/`Lookup`, фильтрации, сортировки и частично группировки. `RuntimeReportDatasetQuery` использует этот путь для отчетов. Общего механизма для `Standalone Dataset`, единого результата запроса и агрегатов нет; агрегаты в текущем `Object Runtime` не поддержаны |
| Workflow Engine | Среда выполнения, состояния, команды, переходы, условия, история, хранение |
| Rule Engine | Есть контракт `IRuleEvaluationGateway` и реализация `RuntimeRuleEvaluationGateway` для условий Workflow; фактически поддерживается ограниченное булево выражение с `==`/`!=`, остальные движки и синтаксис возвращают `NotEvaluated`, а реализация по умолчанию — `NotConfiguredRuleEvaluationGateway` |
| ValueSets / SystemEnums | `ValueSet` — настраиваемый список допустимых значений с `Code`, `Title`, активностью, порядком, иерархией, локализацией и переопределениями по области; для него есть `Value Set Data Editor` и runtime-запросы вариантов выбора. `SystemEnum` — фиксированный кодом/платформой список значений для технических состояний и режимов; он публикуется и читается через конфигурацию, но не редактируется в `Value Set Data Editor` |
| Audit / History | Постоянное хранение записей аудита и истории Workflow |
| IntegrationEvents / Outbox | Постоянное хранение исходящих сообщений, публикация, обработчик, повторные попытки и основа очереди неразобранных сообщений |
| API / Contracts | Серверные DTO и зеркала контрактов клиентской части |
| Settings | Платформа регистрации и ведения настроек, объявляемых модулями: каталог настроек, разделы и группы, типы и значения по умолчанию, проверки, локализация, области corporate/tenant/site, переопределения и получение эффективного значения; отдельно поддерживаются пользовательские preferences |
| Numbering | Правила нумерации, счетчики, разбиение счетчиков и интеграция с Object Runtime |

Текущие модули хранения используют отдельные схемы SQL Server, в том числе `tenant_security`, `configuration`, `value_sets`, `workflow`, `audit_history`, `integration_events`, `settings` и другие.

Целевой стек: Java + PostgreSQL.

## 3. Обязательные результаты

### 3.1 Матрица соответствия документации и MVP

Сопоставить сводный комплект проектной документации по каждой возможности
Platform Core с кодом MVP и составить матрицу соответствия:

- что уже описано в проектной документации;
- что подтверждается исходным кодом и тестами;
- какие расхождения есть между документацией и кодом;
- что является переходным решением;
- что отсутствует;
- что сохраняется без изменения семантики;
- что перепроектируется на Java;
- какие тесты подтверждают работоспособность;
- какие риски промышленной эксплуатации остаются.

### 3.2 Целевая архитектура Java/PostgreSQL

Использовать сводный комплект проектной документации как основу для проверки и
принятия решений по следующим вопросам. Если решение отсутствует или
противоречит фактическому состоянию MVP, принять и оформить уточненное решение
по:

- версии Java;
- фреймворку Java;
- подходу к хранению данных;
- API и OpenAPI;
- структуре целевых схем и начальной системной конфигурации;
- обработке событий и выбору брокера сообщений;
- аутентификации и авторизации;
- кэшированию;
- наблюдаемости;
- развертыванию и CI/CD;
- визуальным компонентам для трех приложений, включая `Calendar`, `Resource Scheduler` и `Gantt`.

Предварительно: `Material React Table (MRT)` рассматривать как основного кандидата для таблиц и таблицы ресурсов через `@dmp/ui/DataTable`; `Bryntum` оставить под вопросом как кандидата для `Calendar`, `Resource Scheduler` и `Gantt`. Через две недели нужно принять решение по этим компонентам с учетом лицензии, коммерческого использования, работы в закрытом контуре, функциональности, производительности и интеграции с сервером.

Отдельно определить, будет ли PostgreSQL использоваться как:

- одна база с отдельными схемами;
- несколько баз;
- комбинация базы и схем;
- отдельные хранилища для оперативных, интеграционных, аудиторских и аналитических данных.

### 3.3 Проверка и утверждение модели Platform Core

Проверить и утвердить границы и контракты следующих возможностей по сводному
комплекту документации и коду MVP. Изменения вносить только при наличии
расхождения с кодом MVP или необходимости перехода на целевую архитектуру:

- Tenant Security / IAM;
- Configuration Platform;
- Runtime и Object Runtime;
- Workflow Engine;
- Rule Engine;
- ValueSets / SystemEnums;
- Audit / History;
- Event Foundation / Outbox / Inbox;
- API / Contracts;
- Settings;
- Numbering;
- Dataset / Read Query Capability.

Проверить и утвердить в документации, что `Dataset` является общим именованным
контрактом чтения данных, а не источником только для отчетов и не таблицей базы
данных. Один и тот же
`DatasetCode` может использоваться в `Object Runtime`, `View`, `Report`,
`Output`, а в дальнейшем — в аналитике и интеграциях.

Проверить и сохранить в целевой модели разделение двух видов наборов данных:

- `Object Dataset` — `List`, `Lookup`, `Details` и другие сценарии чтения
  конкретного бизнес-объекта, объявленные через `BusinessObjectContract`;
- `Standalone Dataset` — отдельный контракт для объединенных, расчетных,
  аналитических, интеграционных или внешних данных.

Для общего механизма определить:

- реестр и владельца `DatasetCode`;
- источник данных и адаптер чтения;
- параметры, фильтры, сортировку, группировку, агрегаты и постраничное чтение;
- состав и типы полей результата, групповые итоги и ошибки выполнения;
- правила безопасности, tenant/site/corporate-области и доступные потребители;
- требования к согласованности, актуальности, синхронному или фоновому
  выполнению, кэшированию и ограничению объема результата;
- правила совместимости опубликованного контракта при изменении параметров и
  схемы результата.

`Dataset` не определяет физическое хранилище. Источником могут быть
операционные данные предприятия, общие корпоративные данные, отдельная
read-модель, аналитическое хранилище или внешний источник. Прямой доступ одного
владельца к таблицам другого владельца не допускается.

Для `Configuration Platform` не создавать новую модель артефактов. В результатах
работы подтвердить, как существующая каноническая модель переносится на Java и
какие изменения действительно необходимы.

Каноническая модель — это существующее единое внутреннее представление
конфигурации, из которого строятся редактор, API и runtime. Нужно проверить и
подтвердить:

- состав и структуру `ArtifactDocument`, `ArtifactNode`, `ArtifactValue` и
  `EffectiveArtifactDocument`;
- источник истины для схем, свойств, дочерних узлов, типов значений,
  локализации и ссылок;
- правила редактирования, проверки, сохранения, публикации и архивирования;
- правила наследования и переопределений на уровнях `corporate`, `tenant` и
  `site`;
- порядок построения effective-конфигурации и разрешения конфликтов;
- какие опубликованные данные передаются в API и runtime и как из них
  формируются runtime-представления;
- версионирование схем, совместимость изменений и обновление ранее созданных
  конфигураций.

Для каждого пункта указать: что уже подтверждено текущим кодом, что без
изменения переносится на Java, что требует изменения и какие существующие
контракты должны сохраниться. `Baseline Configuration` рассматривать как
поставку начальной конфигурации, а не как новый тип артефакта.

Для Object Runtime отдельно решить:

- окончательный контракт объекта;
- описатель объекта и реестр объектов;
- единый контур чтения/записи/изменения;
- жизненный цикл, проверки, действия и точки подключения Workflow;
- связи и массовые операции;
- транзакции, аудит, outbox и сброс кэша;

### 3.4 Незакрытые возможности, для которых нужен проектный результат

Должны быть приняты решения и подготовлены планы реализации для следующих направлений:

1. **Object Runtime** — определить и закрыть оставшиеся вопросы промышленной эксплуатации: группировки, сброс кэша, проверки массовых операций и импорта, а также расширения стандартного пути выполнения.
2. **Rule Engine** — границы обобщенного выполнения правил за пределами условий Workflow: проверки, расчеты, значения по умолчанию, авторизация и точки выполнения.
3. **Report Runtime** — сохранить существующие `ExecuteReportService` и связанные контракты, определить поддерживаемые сценарии и границу ответственности отчета: параметры, фильтры, выбор `DatasetCode`, структура результата, безопасность, аудит и ошибки. Чтение данных, группировки и агрегаты должны выполняться через общий `Dataset / Read Query Capability`.
4. **Output Runtime** — сохранить цепочку `GenerateOutput` → `ExecuteReport` → Java Report Service и определить недостающие возможности: предварительный просмотр, поддерживаемые форматы и источники, внешняя доставка, фоновое выполнение, безопасность, аудит и ограничения размера.
5. **Dataset / Read Query Capability** — определить общий механизм чтения для `Object Runtime`, `View`, `Report`, `Output`, аналитики и интеграций. Утвердить границу между `Object Dataset` и `Standalone Dataset`, реестр, владельца и источник каждого набора, контракт запроса и результата, параметры, фильтры, сортировку, группировку, агрегаты, постраничное чтение, безопасность, области данных, согласованность, актуальность, кэширование и ограничения результата. Текущий `RuntimeReportDatasetQuery` считать отчетным адаптером первого этапа, а не общей платформой наборов данных.
6. **Integration Capability** — Integration Service, ExternalSystem, IntegrationFlow, соединители, сопоставления, Inbox, IntegrationMessage/Attempt, внешние идентификаторы, состояние синхронизации и ручной повторный запуск.
7. **Хранение временных рядов и телеметрии** — прием данных, `OccurredAtUtc`/`IngestedAtUtc`, время источника, политика аномалий, сроки хранения, разбиение и контракты запросов.
8. **Граница безопасности промышленной эксплуатации** — аутентификация, проверка токенов, доверие между сервисами и единая серверная авторизация.
9. **Версионирование API** — отдельные политики версионирования Runtime, Admin и Integration API, совместимость и генерация контрактов клиентской части.
10. **Эксплуатационная готовность** — сроки хранения, повторные попытки, очередь неразобранных сообщений, диагностика, проверки работоспособности, метрики, трассировка, резервное копирование/восстановление, RPO/RTO и эксплуатационные инструкции.

## 4. Архитектура владения и размещения данных

Подготовить два связанных результата:

1. Матрицу владения и размещения данных Platform Core.
2. Решение по целевой схеме хранения и обмена данными в PostgreSQL и связанных
   хранилищах.

Матрица должна охватывать следующие классы данных:

| Класс данных | Что обязательно определить |
|---|---|
| IAM и tenant | Владелец, границы `tenant/site`, изоляция и способы чтения |
| Версионируемая конфигурация | `draft`/`published`/`effective`, наследование, источник истины и кэш |
| Данные `ValueSet` | Владелец значений, область `corporate/tenant/site`, переопределения и runtime-чтение |
| Runtime settings и user preferences | Владелец, область действия, эффективное значение и хранение |
| Workflow | Текущее состояние, история, владелец и транзакционные границы |
| Общие корпоративные данные | Источник истины, распространение, версионирование и доступ на чтение |
| Оперативные данные `tenant/site` | Владелец, транзакционные границы, основные сценарии чтения и сроки хранения |
| Состояние интеграций | `Inbox`/`Outbox`, попытки, сопоставления, идемпотентность и повторная обработка |
| Аудит, история и трассировка | Неизменяемость, поиск, сроки хранения и архивирование |
| Телеметрия и временные ряды | Прием, временные метки, объем, разбиение, агрегация и сроки хранения |
| Аналитические данные и read-модели | Источник, способ построения, агрегаты, задержка актуализации и потребители |
| Файлы и крупные объекты | PostgreSQL или файловое/объектное хранилище, метаданные и жизненный цикл |
| Кэш и проекции | Исходные данные, назначение, сброс, восстановление и согласованность |

Для каждого класса данных указать:

- владельца записи и источник истины;
- область действия и правила изоляции по `tenant` и `site`;
- целевое физическое хранилище и схему/базу PostgreSQL либо другое хранилище;
- допустимые способы чтения и изменения и основных потребителей;
- строгую согласованность или допустимую задержку актуализации;
- синхронный или асинхронный обмен, если данные передаются между контурами;
- сроки хранения, архивирование и удаление;
- репликацию и кэширование, если они необходимы;
- основные сценарии чтения и требования к производительности;
- запрет прямого доступа к таблицам другого владельца.

Для каждого используемого `Dataset` отдельно указать владельца контракта,
источник данных, класс данных, область действия, допустимых потребителей,
требуемую актуальность, допустимый уровень согласованности, требования к
безопасности и ограничение объема результата.

Отдельно принять решение по гибридному контуру:

```text
центральная корпоративная платформа
        ↕
предприятие
        ↕
площадка / цех / шлюз оборудования
```

Для каждого уровня определить:

- какие данные являются локальными, а какие поступают из корпоративного
  контура;
- какие операции должны работать при временной недоступности центральной
  платформы;
- где накапливаются данные до передачи;
- кто является владельцем записи при обмене;
- как выполняются повторная доставка и разрешение конфликтов;
- нужны ли локальные read-модели и как они восстанавливаются.

## 5. Обязательные решения по интеграциям

`IntegrationEvents / Outbox` уже являются частью MVP. Отдельно спроектировать
недостающую `Integration Capability`, которая управляет обменом с внешними
системами, а не только публикацией внутренних событий.

Для каждого объекта и процесса определить назначение, владельца, жизненный
цикл, связь с данными, способ запуска, состояние, обработку ошибок и права
доступа:

- `ExternalSystem`;
- `IntegrationFlow`;
- `Connector`;
- `ContractBinding`;
- `MappingDefinition`;
- `RetryPolicy` и `ErrorPolicy`;
- `Inbox` и `Outbox`;
- `IntegrationMessage` и `IntegrationAttempt`;
- `ExternalObjectMapping`;
- идемпотентность и обнаружение дубликатов;
- идентификаторы корреляции и причины запуска;
- мониторинг и ручная повторная обработка.

Для каждого объекта отдельно определить, какие данные он описывает и где
хранится его состояние. В частности, не смешивать:

- `Outbox` как источник исходящих сообщений;
- `Inbox` как защиту от повторной обработки входящих сообщений;
- `IntegrationMessage` как сообщение обмена;
- `IntegrationAttempt` как отдельную попытку доставки или обработки.

Описать первые сквозные сценарии интеграции:

- входящие и исходящие обмены с ERP;
- входящие обмены с CAD/PDM;
- входящая телеметрия от MDC и оборудования.

Для каждого сценария указать:

- состав и направление передаваемых данных;
- систему — источник истины;
- API, событие или файловый обмен;
- причину и момент запуска;
- синхронный или асинхронный режим;
- требования к порядку, идемпотентности и повторной доставке;
- поведение при конфликте, недоступности системы и попадании сообщения в
  очередь неразобранных сообщений;
- версионирование контракта сообщения, безопасность, аудит и владельца данных.

## 6. План перехода MVP с .NET/SQL Server на Java/PostgreSQL

План не предполагает автоматический перенос данных MVP из SQL Server. PostgreSQL проектируется как новое целевое хранилище. Если позднее потребуется использовать отдельные данные из MVP, это оформляется отдельным решением и отдельным планом.

План должен содержать:

- порядок перехода возможностей Platform Core;
- стратегию совместной работы .NET и Java;
- совместимость API и событий;
- правила создания целевых схем PostgreSQL и начального заполнения системной конфигурации;
- сохранение стабильных кодов и внешних идентификаторов в новых контрактах и новых данных;
- правила типов, JSON, временных меток, последовательностей и контроля конкурентного изменения для новой реализации;
- порядок поэтапного включения Java-реализации для отдельных возможностей и API;
- критерии остановки этапа и план действий при неготовности или сбое Java-реализации;
- критерии готовности каждого этапа;
- оценки, зависимости, ресурсы и критический путь.

## 7. Стратегия трех фронтовых приложений и API

Три существующих приложения сохраняются в целевой архитектуре:

| Приложение | Назначение |
|---|---|
| `Admin` | IAM, предприятия и площадки, права, пользователи, административные и эксплуатационные операции |
| `Studio` | Создание и публикация конфигурации, управление областями действия и версиями, редактор артефактов и настроек |
| `Runtime` | Работа с опубликованной конфигурацией, представления объектов, операции, действия и Workflow |

Общие пакеты клиентской части также сохраняются:

- `api-client`;
- `contracts`;
- `runtime-contracts`;
- `runtime-react`;
- `auth`;
- `access-control`;
- `platform-context`;
- `tenant-security-api`.

### 7.1 Правило совместимости

Переход на Java не должен требовать переписывания трех приложений. Java-сервер
должен сохранить смысл и основные способы использования текущего API, а
изменения должны быть ограничены необходимыми случаями и оформлены через
совместимые расширения или новую версию API.

В первую очередь должны сохраняться:

- назначение и семантика существующих API;
- адреса и HTTP-методы, если для их изменения нет архитектурной необходимости;
- имена и типы JSON-полей, если они не требуют изменения по утвержденному решению;
- стабильные коды объектов, действий, ошибок и прав;
- правила tenant/site-контекста;
- модель опубликованной конфигурации;
- контракты списка, карточки, создания, изменения и действий объекта;
- контракты Workflow и истории;
- правила пагинации, фильтрации, сортировки и обработки ошибок;
- формат дат, временных зон и идентификаторов.

Допустимы без создания новой версии:

- новые API-методы;
- новые необязательные поля;
- новые возможности, которые не меняют смысл существующих полей;
- внутреннее изменение реализации и хранения данных.

Изменение существующего поведения, обязательных полей, стабильных кодов или
формата ошибок допускается только при наличии утвержденного решения, новой
версии API или совместимого адаптера и плана перехода клиентов.

### 7.2 Что должно быть решено через две недели

Нужно утвердить:

- список API, которые считаются совместимыми с текущими приложениями;
- список контрактов, которые необходимо заморозить до начала миграции;
- источник контрактов: OpenAPI, JSON Schema и схемы событий;
- способ синхронизации серверных и TypeScript-контрактов;
- набор автоматических контрактных проверок;
- правила версионирования Runtime, Admin и Integration API;
- возможность одновременной работы .NET и Java за одним шлюзом;
- способ постепенного переключения приложений или отдельных API на Java.

### 7.3 Рекомендуемая схема перехода

```text
Текущие Admin / Studio / Runtime
              |
       стабильные API-контракты
              |
  шлюз или единая точка входа
       /                    \
текущий .NET MVP       новые Java-сервисы
```

На период перехода клиентская часть не должна знать, какой сервер выполняет запрос. Переключение выполняется на уровне шлюза, маршрутизации или конфигурации адреса API.

### 7.4 Критерий готовности фронтенд-части

До включения каждой Java-возможности в рабочий контур должны существовать:

- зафиксированные контракты текущих API;
- контрактные тесты для .NET-реализации;
- те же тесты для Java-реализации;
- проверка трех приложений на одинаковом наборе сценариев;
- план обработки несовместимых изменений.

Целевое правило: смена .NET на Java не является основанием для переписывания `Admin`, `Studio` и `Runtime`.

## 8. Артефакты, которые должны быть готовы через две недели

| № | Артефакт | Что должно быть внутри |
|---:|---|---|
| 1 | Матрица соответствия документации и MVP | По каждой возможности: что описано в сводном комплекте документации, что подтверждено кодом и тестами, расхождения, используемые контракты, ограничения, переходные решения и то, что нужно сохранить при переходе на Java |
| 2 | Целевая архитектура Java/PostgreSQL | Состав сервисов и модулей, границы ответственности, каноническая модель артефактов, сервисы редактирования и runtime-материализации, `Dataset / Read Query Capability`, взаимодействие между компонентами, API, события, безопасность, наблюдаемость, развертывание, визуальные компоненты для трех приложений и принятые технологические решения |
| 3 | Матрица владения и размещения данных | Классы данных, владелец записи и источник истины, область действия, правила изоляции по tenant и site, целевые схемы и базы PostgreSQL или другие хранилища, способы чтения и изменения, согласованность, актуальность, обмен, кэширование и сроки хранения |
| 4 | Архитектура Integration Capability и первые сценарии | Объекты и процессы интеграции, внешние системы, соединители, сопоставления, Inbox/Outbox, повторные попытки, дубликаты, ошибки, мониторинг и спецификации первых обменов с ERP, CAD/PDM, MDC и оборудованием |
| 5 | Реестр архитектурных решений | По каждому существенному решению: вопрос, выбранный вариант, отклонённые варианты, последствия, затронутые модули и указание на подтверждающие документы, код и тесты; самостоятельный ADR создаётся только по отдельному решению |
| 6 | Реестр нерешенных вопросов | Для каждого вопроса: формулировка, владелец решения, срок, влияние на архитектуру и план работ, зависимые решения и условие закрытия |
| 7 | Поэтапный план перехода и ввода в промышленную эксплуатацию | Этапы перехода возможностей Platform Core на Java/PostgreSQL, совместная работа .NET и Java, включение отдельных API, критерии остановки этапа, действия при неготовности или сбое Java-реализации, критерии готовности этапов и прямое указание, что перенос данных MVP не входит в план |
| 8 | План первой очереди разработки | Точный состав первой очереди, результат каждого шага, зависимости, оценки трудоемкости, необходимые специалисты, условия завершения и ожидаемый результат очереди |
| 9 | Матрица рисков и критерии приемки результата | Риски, вероятность, влияние, меры снижения и владелец; отдельно — проверяемые условия, при выполнении которых результат работы руководителя разработки и технического архитектора через две недели считается принятым |

## 9. Критерии готовности

Результат принимается, если:

- все артефакты из раздела 8 переданы в согласованном составе;
- выводы по текущему MVP подтверждены кодом и тестами, а расхождения либо
  устранены, либо внесены в реестр нерешенных вопросов;
- принятые архитектурные решения согласованы между собой и не содержат
  нерешенных вопросов, блокирующих начало реализации;
- план первой очереди, план перехода и план промышленной эксплуатации можно
  использовать для постановки работ;
- сохранение трех приложений (`Admin`, `Studio`, `Runtime`), допустимые
  изменения их API и отсутствие автоматического переноса данных MVP отражены
  в итоговых артефактах.
