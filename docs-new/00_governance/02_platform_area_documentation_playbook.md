# Playbook оформления платформенной области

## 1. Назначение

Документ задаёт рабочую последовательность подготовки одной платформенной области `03_platform/<area>` к ревью. Он дополняет [шаблон платформенной области](../03_platform/00_platform_documentation_template.md), но не заменяет его.

Playbook нужен, чтобы при разборе следующих областей ядра не повторять ошибки пилота Tenant/Security: не смешивать source-копии с целевыми документами, не выдавать будущие решения за MVP, не терять открытые вопросы, не плодить разные термины и не переносить общую frontend-платформу в документы отдельного модуля.

## 2. Входы и выходы

| Тип | Что использовать | Что не делать |
| --- | --- | --- |
| Код и контракты | Реальные projects, packages, migrations, tests, controllers, public contracts. | Не заменять проверку кода пересказом старого requirements. |
| Source/requirements | Использовать как материал анализа и покрытия. | Не копировать `offers/` и `requirements/` внутрь целевого пакета области. |
| Верхний слой | `01_concept`, `02_architecture`, backlog и двухнедельный архитектурный план. | Не блокировать MVP-пакет из-за ещё не нормализованного верхнего слоя; ставить ссылку в backlog. |
| Глоссарий | `11_glossary/platform_terms.md` и тематические глоссарии. | Не вводить новый термин только локально, если он нужен за пределами одного документа. |

Готовый выход — каталог `03_platform/<area>` с документами `00`-`08` и `90_traceability.md` по стандарту. Source-копий внутри каталога области быть не должно. Каталожные подпапки допускаются только как утверждённое исключение из шаблона, например `artifact_types/` для Configuration.

## 3. Последовательность работы

### 3.1. Снять карту области

1. Найти папку области в `docs-new/03_platform`.
2. Выписать все source/requirements/offer/backlog-файлы, которые сейчас лежат рядом.
3. Найти соответствующие старые исходники в `docs/`, если они существуют.
4. Проверить, есть ли уже кодовый владелец: project, package, contracts, migrations, tests.
5. Определить соседние области: runtime, frontend, configuration, audit, events, contracts.

Результат этапа — список материалов и первичная гипотеза границы.

### 3.2. Разделить source и целевой пакет

Source/requirements не входят в целевой комплект `03_platform/<area>`. Их содержание разбирается так:

| Содержание | Статус сведения | Куда переносить |
| --- | --- | --- |
| Подтверждено кодом, контрактом или тестом | `Подтверждено MVP` | В документ-владелец `00`-`08`. |
| Есть в коде, но используется только частично | `Подтверждено, но ограничено` | В документ-владелец с явным описанием ограничения; при необходимости — также в трассировку. |
| Согласовано как целевая модель, но не реализовано полностью | `Принято целевое решение` | В документ-владелец только с пометкой целевого решения и в `90_traceability.md` до реализации. |
| Противоречит MVP или требует выбора | `Открытый вопрос` | В `90_traceability.md` с устойчивым ID. |
| Является будущей идеей или отложенной работой | `Будущая доработка` | В backlog; при миграции также в `90_traceability.md`. |
| Шире одной области или относится к другому слою | `Владелец другой области` | В `01_concept`, `02_architecture`, `03_platform/<другая область>` или backlog; маршрут фиксируется в трассировке. |
| Является старой копией без уникального смысла | `Не переносить: устарело или противоречит MVP` | Только трассировка; удалить из целевой области после фиксации маршрута. |

В целевых документах не должно быть ссылок на старые `docs/...` или локальные `offers/requirements`.

#### Закрыть переходную папку после миграции

После завершения разбора области переходные копии в `docs-new/<target-area>/`
должны быть закрыты. Закрытие не означает удаление исходного материала из
`docs/`: исходник сохраняется, если для него не принято отдельное решение.

Перед удалением переходной копии автор обязан:

1. Сопоставить её с исходным файлом в `docs/` и проверить, что копия не содержит
   уникального материала, отсутствующего в исходнике.
2. Разнести всё существенное содержание по документу-владельцу, `90_traceability.md`,
   backlog или области другого владельца.
3. Убедиться, что запись в `90_traceability.md` понятна без открытия удаляемой
   копии и содержит текущий подтверждённый факт, статус, владельца и следующий
   маршрут.
4. Обновить `00_governance/99_archive_migration_review.md`: указать исходный
   файл, актуальный канонический документ или backlog и состояние переходной
   копии (`удалена` или `сохранена как исключение`).
5. Найти и исправить ссылки на удаляемый путь в нормативных документах,
   автоматизации и навигационных индексах. Исторические записи можно сохранить,
   но они должны быть явно обозначены как исторические.
6. Удалить только переходную копию из `docs-new`; исходный файл в `docs/` не
   удаляется этой процедурой.
7. Проверить отсутствие файлов в закрытой папке, ссылки на канонические места и
   `git diff --check`. Строки истории изменений вручную не добавляются: их
   заполняет автоматизация после Pull Request.

Если хотя бы один пункт не выполнен, переходную копию не удаляют, а фиксируют
оставшийся маршрут как работу в backlog или открытый вопрос.

### 3.3. Заполнить документы-владельцы

Документы создаются только при наличии предметного содержания:

| Документ | Когда нужен |
| --- | --- |
| `00_platform_overview.md` | Всегда. Даёт карту области, статус, термины и состав документов. |
| `01_scope.md` | Всегда. Фиксирует in/out boundary и соседних владельцев. |
| `02_architecture.md` | Есть модель, компоненты, storage, зависимости или invariants. |
| `03_contracts.md` | Есть C#/HTTP/event/frontend contracts, config или adapters. |
| `04_runtime.md` | Есть исполняемые сценарии, алгоритмы, lifecycle, consistency или failures. |
| `05_security_and_audit.md` | Есть права, проверки доступа, security controls или audit records. |
| `06_user_experience.md` | Есть frontend package, feature provider, route, navigation item или UI localization. |
| `07_quality.md` | Есть test evidence, reliability, observability, performance или known gaps. |
| `08_operations.md` | Есть startup, migrations, diagnostics, recovery или runbook. |
| `90_traceability.md` | Всегда при миграции source/requirements или наличии открытых решений. |

Если документа нет по предметной причине, его номер не используется для другой темы.

#### 3.3.2. Описать граничные контракты

Для `03_contracts.md` применяется [Стандарт описания контрактов](03_contract_documentation_standard.md).
Документ содержит сводную карту, а каждый значимый HTTP-, event-, C#- или
frontend-контракт описывается отдельным подразделом. Для HTTP-операции вместе
описываются маршрут, request, response, ошибки и ограничения. Повторно
используемые DTO описываются один раз и затем связываются ссылками.

В подробное описание включаются только контракты, пересекающие границу слоя,
модуля, приложения или extension point. Приватные implementation-типы не
переносятся. Структура контракта описывается отдельно от runtime-алгоритма,
frontend renderer и предметной модели.

Общая карта межмодульных взаимодействий находится в
`02_architecture/07_integration_architecture.md`. В ней фиксируются сквозные
связи между областями. Документы `03_platform/<area>` содержат только локальную
карту контрактов и подробности своего владельца; старые машинные материалы из
`docs/05 contracts` используются только как источники сверки, а не как отдельный
целевой раздел `docs-new`. Runtime-поведение описывается в `04_runtime.md`
области-владельца.
Одна и та же связь не должна описываться одинаковой таблицей в каждом пакете.

#### 3.3.3. Применить общий каркас архитектуры

Каждый существующий `02_architecture.md` использует один и тот же верхнеуровневый
каркас:

1. `Назначение документа`;
2. `Граница и компоненты`;
3. `Архитектурная модель и инварианты`;
4. `Persistence-модель и хранение`;
5. `Зависимости и точки расширения`;
6. `Технические ограничения`.

Содержание раздела `Архитектурная модель и инварианты` зависит от владельца
области: это может быть доменная модель, модель конфигурации или техническая
runtime-модель. Название раздела и его место не меняются. Полный каталог классов,
свойств и методов в `02_architecture.md` не ведётся; в документ включаются только
архитектурно значимые типы, связи, ответственность и инварианты.

Свойства конфигурационных артефактов описываются в `artifact_types/<artifact>.md`,
межкомпонентные контракты — в `03_contracts.md`, алгоритмы исполнения — в
`04_runtime.md`. Эти документы ссылаются друг на друга, но не дублируют полное
содержание.

Каждая платформенная область должна явно зафиксировать зависимость от
`03_platform/00_foundation/`, если код области использует общие BuildingBlocks,
контракты application-слоя, контексты, порты gateway или типы
`DMP.Platform.Contracts.Common`. Такая зависимость указывается один раз в
обзоре области или в `02_architecture.md` в таблице:

| Общий компонент | Как используется областью | Владелец определения | Владелец предметной семантики | Документ Foundation |
| --- | --- | --- | --- | --- |

Документ потребителя не копирует определение общего компонента. В нём
фиксируются только фактическое применение, ограничения и собственная
семантика. Физическая сборка не определяет владельца: `DMP.Platform.Contracts`
содержит как общие типы Foundation, так и контракты конкретных областей.

#### 3.3.4. Добавить поясняющие схемы по назначению раздела

Схема добавляется тогда, когда она делает границу, связь или последовательность
понятнее таблицы и текста. Набор схем выбирается по содержанию области, а не по
формальному требованию создать диаграмму в каждом файле:

| Документ | Рекомендуемое пояснение | Когда схема обязательна для чтения |
| --- | --- | --- |
| `00_platform_overview.md` | Карта области и соседних владельцев | Если область взаимодействует более чем с одним внешним владельцем |
| `01_scope.md` | Граница ответственности | Если обязанности разделены между несколькими областями или слоями |
| `02_architecture.md` | Компоненты, архитектурная модель или поток данных | Если статическая структура не объясняется одной таблицей |
| `03_contracts.md` | Карта контрактного взаимодействия | Если есть несколько потребителей или межмодульных границ; отдельная схема для каждого endpoint не требуется |
| `04_runtime.md` | Поток сценария или последовательность вызовов | Для самостоятельных pipeline, lifecycle и алгоритмов с важным порядком шагов |
| `05_security_and_audit.md` | Поток проверки доступа или побочных действий | Если область сама формирует security/audit boundary |
| `08_operations.md` | Startup, диагностика, отказ или восстановление | Если область имеет собственный эксплуатационный поток |

Для `07_quality.md` и `90_traceability.md` таблицы являются основным форматом;
схема добавляется только при появлении дополнительной информации. Диаграмма не
заменяет таблицу свойств, контракт или трассировку. Она размещается у
документа-владельца, имеет пояснение и ссылки на подтверждающие исходники.
Сплошные связи означают подтверждённое направление, пунктир — внешнюю границу,
использование или ограничение; будущая возможность не показывается как
реализованный поток.

В `08_operations.md` диагностическая таблица разделяет ситуацию, технический
код или сигнал и проверку. Коды ошибок, названия событий, `CorrelationId`, DTO
и источники диагностики не объединяются в одной неименованной колонке. Если
для ситуации нет отдельного подтверждённого кода, указывается `—`; новые коды
по смыслу не придумываются.

Для каждой области в пакете должен быть понятен хотя бы один основной путь
читателя: от входного контракта или события через владельцев и существенные
шаги до результата. Путь может быть показан схемой или последовательным текстом
в документе-владельце. Если у области нет единого исполняемого сценария, это
явно объясняется в `00_platform_overview.md` или `01_scope.md`; отсутствие
сценария не заполняется вымышленным потоком.

#### 3.3.1. Каталоги однотипных спецификаций

Если область владеет множеством однотипных спецификаций, их не нужно насильно объединять в один большой документ. Вместо этого можно создать каталог, если он разрешён шаблоном и зафиксирован в `00_platform_overview.md`.

Для `02_configuration/` таким каталогом является `artifact_types/`:

- каждый файл описывает один тип конфигурационного артефакта;
- каждый файл имеет `type: module-spec` во frontmatter;
- файл фиксирует полный schema-контракт: root/child properties, типы значений, обязательность, defaults, допустимые значения, источники значений, зависимости, validation, inheritance/override и schema-level operations;
- для каждого списка выбора указывается владелец источника истины, канонический класс или реестр, канал доставки, режим обновления и сторона проверки: server, client или hybrid;
- явные значения остаются в таблице свойства для читаемости, но рядом указывается канонический источник: static code constants задают технические коды, static option catalog задаёт разрешённый набор для конкретного свойства, а value-source definition задаёт динамический источник и его зависимости;
- если runtime поддерживает только часть значений schema, это указывается отдельно как ограничение runtime и не смешивается со списком допустимых значений schema;
- русские и английские названия свойства сверяются с `ConfigurationSchemaMetadataCatalog`, если для свойства есть UI-метаданные; отсутствие или расхождение метаданных фиксируется явно;
- `03_contracts.md` содержит карту артефактов и ссылки на файлы каталога, но не дублирует все поля;
- поведение соседней области остаётся у соседнего владельца: Workflow исполняется в `04_workflow/`, правила — в `05_rules/`, отчёты и вывод — в `11_reporting_output/`, frontend shell и routing — в `12_frontend_platform/`.

Каталог не должен называться `offers`, `requirements`, `source`, `drafts` или `archive` и не должен хранить старые документы без вычитки.

### 3.4. Вести `90_traceability.md`

`90_traceability.md` не является архивом source-файлов и не хранит ссылки на старые `docs`. Он отвечает на вопросы ревью:

| Обязательное поле | Что фиксировать |
| --- | --- |
| Тема | Короткое название факта, расхождения или вопроса. |
| Текущее подтверждённое состояние | Факт из кода, контракта, migration или теста с указанием границы MVP. |
| Расхождение или неопределённость | Что ожидалось иначе, чего не подтверждено или какой выбор пока не сделан. |
| Влияние на текущую документацию | Одна классификация: `Не блокирует текущую документацию`, `Требует решения для текущего контракта`, `Будущая доработка`, `Расхождение кода и источника` или `Передано другому владельцу`. |
| Статус сведения | Один контролируемый статус из шаблона. Он описывает состояние факта, а не влияние записи. |
| Владелец / следующий шаг | Конкретный владелец решения или работы и действие, которое должно быть выполнено следующим. |
| Документ для обновления после решения | Целевой документ-владелец, который нужно изменить после принятия решения. |

При необходимости перед этими полями сохраняется отдельная колонка `Ожидание или источник`: она кратко показывает, почему тема попала в трассировку, но не заменяет подтверждённое состояние. Состав таблицы не должен превращать `90_traceability.md` в каталог исходных файлов.

Для каждой строки расхождения дополнительно указывается один контролируемый
`Статус сведения` из шаблона: `Подтверждено MVP`, `Подтверждено, но ограничено`,
`Принято целевое решение`, `Открытый вопрос`, `Будущая доработка`, `Не
переносить: устарело или противоречит MVP` или `Владелец другой области`.
Статус строки не является статусом документа во frontmatter.

Формулировка открытого решения должна быть понятна без открытия старого source. В ссылке нельзя оставлять только ID: рядом указываются ссылка на `90_traceability.md`, сам ID и короткое название темы. Если решение уже принято, но ещё не перенесено в документ-владелец, оно остаётся в traceability с явной пометкой `Принято` и не должно описываться как нерешённый вопрос.

Чат, ревью или рабочее обсуждение используются для формулирования вариантов и принятия решения. После принятия решения основной документ содержит подтверждённое текущее поведение и принятое решение, а `90_traceability.md` сохраняет только устойчивую запись о расхождении, ограничении MVP, нерешённом вопросе и маршруте обновления. Будущие задачи и доработки направляются в backlog; будущая возможность не описывается как текущая гарантия.

Не всякая неопределённость требует решения владельца документации. Решение запрашивается только тогда, когда без него нельзя корректно описать текущую границу, межкомпонентный контракт, владельца или гарантию. Расхождение реализованного кода с requirements или старым документом само по себе не является архитектурным решением: сначала фиксируется подтверждённое состояние MVP и классификация расхождения.

### 3.5. Проверить терминологию

Для каждого устойчивого термина:

1. Выбрать русский термин.
2. Указать английский или технический alias при первом употреблении.
3. Проверить UI/manifest/code names.
4. Добавить термин в `11_glossary`, если он нужен за пределами одного документа.
5. Запретить нежелательные кальки, если они уже сбивали чтение.

При создании или обновлении тематический глоссарий переводится на общую базовую таблицу `Русский термин / Preferred English / Технический алиас / Статус / Определение / Источник в коде / Нежелательные синонимы`. Дополнительные таблицы допускаются только для предметных расширений: UI-подписей, исходных `TERM-*`, терминов, требующих владельца, или границ соседних областей. Локальная таблица в `00_platform_overview.md` повторяет определения для чтения и ссылается на тематический глоссарий.

Если техническое имя относится к входному DTO, manifest или другому описанию (`*TemplateRequest`), а после регистрации создаётся доменный объект, в архитектурном тексте используется термин доменного объекта. Техническое имя входной структуры приводится только как alias. Например, `CapabilityRoleTemplateRequest` описывает системную роль (`System role`), но не заменяет этот термин.

Пример правила из пилота: не использовать `поверхность/surface` для UI; писать `интерфейсная часть`, `раздел интерфейса`, `экран`, `сценарий` или `frontend-представление`.

### 3.6. Отделить frontend области от Frontend Platform

`06_user_experience.md` описывает только интерфейсную часть конкретной области:

- frontend contracts области;
- разделы Admin/Runtime/Studio, если они реально есть;
- navigation items;
- UI localization;
- visibility по правам;
- ограничения текущего frontend-потребления.

Общий shell, bootstrap, session, routing, app boundaries, runtime packages и shared UI принадлежат будущей `03_platform/12_frontend_platform`.

Если область backend-only, `06_user_experience.md` не создаётся; в overview или scope коротко фиксируется, что интерфейсной части нет.

### 3.7. Разделить артефакт, его исполнение и интерфейс

Каноническая модель (`ArtifactDocument`, `ArtifactNode`, `ArtifactValue`) задаёт
общую форму конфигурационного артефакта. Она не становится владельцем всего
поведения, которое может быть построено поверх этого артефакта.

Один конфигурационный артефакт может использоваться Configuration, runtime,
frontend и прикладным модулем, но подробное описание каждой части не
дублируется во всех этих областях. Источник истины определяется слоем:

| Слой | Что описывает | Владелец |
| --- | --- | --- |
| Каноническая структура и schema | Type code, stable code, properties, child collections, discriminators, schema rules и merge semantics | Платформенная область, которая владеет конфигурационным артефактом, обычно Configuration |
| Authoring, versioning и publication | Создание, редактирование, validation, сохранение, публикация и effective configuration | Configuration |
| Runtime-интерпретация | Как published/effective artifact используется при выполнении операций, чтении данных или расчёте результата | Runtime-владелец capability: Object Runtime, Rules, Workflow, Numbering и другой подтверждённый владелец |
| Editor UX | Server editor contract области и сценарии редактирования конкретного артефакта | Configuration для server contract; общая оболочка и shared UI — Frontend Platform |
| Frontend runtime | Renderer, runtime packages, app-specific registry, shell, routing и приложение | Frontend Platform и конкретное приложение |
| Предметный смысл | Как модуль использует артефакт для своих объектов и сценариев | Прикладной модуль |

Документ `artifact_types/<artifact>.md` обязан описывать первый слой и явно
показывать ссылки на владельцев остальных слоёв. Он не должен включать полный
runtime-алгоритм или реализацию frontend renderer.

Компактная схема в разделе `4.1` использует единую нотацию: `properties: { ... }`
означает словарь свойств узла и не является дочерней коллекцией; настоящая
коллекция записывается как `Collection[0..n] → ChildNode`. Для иерархической
коллекции указывается связь родителя, например `ParentCode → ChildNode.Code`.
`Code` и `ArtifactTypeCode` показываются отдельно как identity. Дискриминатор
(`ViewType`, `ItemKind` и аналогичные свойства) задаёт допустимую ветку, но не
является дочерним узлом. Если `View` отображает иерархию данных объектов,
свойства `Tree*` описываются отдельно от иерархии конфигурационных узлов.

Например, для `ObjectType` Configuration описывает `ObjectType`, `Members`,
`MemberBehaviors`, `RuleBindings` и их schema; Object Runtime описывает
исполнение object type; Frontend Platform описывает renderer и приложения; а
domain module описывает конкретный объект и его предметные ограничения.

Поле артефакта не считается описанным, пока не указаны его `PropertyCode`,
русский термин, value kind, required/default, допустимые значения и их источник,
условия применимости, validation, edit/override policy, ссылка на код, смысл
значения и влияние на потребителя. Для каждого enum-кода описывается отдельный
смысл; для `Bool` описываются `true` и `false`; для `ReferenceCode`, `String`,
`Number` и `Json` фиксируются целевой объект, формат, ограничения и потребитель.
Если schema не определяет эффект, это пишется явно, а runtime/frontend-владелец
указывается ссылкой на соответствующий документ.

Смысл каждого значения указывается в строке соответствующего свойства в
таблице свойств. Отдельную повторную таблицу `Семантика значений и влияние` не
создаём: она дублирует каталог свойств и ухудшает читаемость.

Во всех таблицах свойств сохраняется один набор столбцов: `Технический код`,
`Русский смысл`, `Тип значения`, `Обязательность / значение по умолчанию`,
`Допустимые значения или источник`, `Смысл значения и влияние`, `Когда
используется / переопределение`. Даже если отдельный столбец неприменим, он не
удаляется: в ячейке пишется `Не применяется`. Для одноимённых матриц операций
используется набор `Уровень`, `Создание`, `Изменение`, `Удаление`, `Изменение
порядка`, `Ограничение и подтверждение`.

Если текущий MVP использует переходный frontend registry или локальный runtime
provider вместо published configuration, это фиксируется как текущее состояние
или backlog. Переходный путь не меняет владельца целевого конфигурационного
артефакта.

Эталонным примером полного файла является
`03_platform/02_configuration/artifact_types/object_type.md`. Он задаёт не
предметную модель для остальных артефактов, а обязательный порядок объяснения:
назначение, identity и граница, место в Configuration, состав схемы в `4.1`,
общие свойства корня, условные свойства корня при наличии, дочерние узлы и их
properties, связи и структурные правила, источники значений, ограничения,
операции, inheritance/effective и lifecycle при применимости, затем
статус/границы, термины, источники и история. `View` и следующие
артефакты должны сохранять этот смысловой каркас, но не копировать чужие
свойства или неприменимые разделы.

Если дискриминатор меняет структуру артефакта, в `4.1` показываются отдельные
ветки для его значений. Общие свойства описываются один раз в `4.2`, условные
свойства корня — в `4.3`, а вложенные типы — начиная с `4.4` либо с `4.3`, если
условных свойств корня нет. Полные таблицы свойств не дублируются внутри каждой
ветки.

Раздел `Статус и границы документа` фиксирует только подтверждённое и
исключённое из текущего schema-контракта. Открытые решения не дублируются в
artifact-файле: им присваивается ID в `90_traceability.md`.

До переноса поля из source нужно определить его слой: schema property,
каноническая identity, baseline/persistence field, editor projection или
runtime-derived value. Нельзя считать `OriginKey`, `ModuleCode`, `DisplayName`,
`Options`, `AvailableOperations` или `IsReadOnly` свойствами артефакта только
потому, что они присутствуют в DTO или editor response. Такие поля описываются
у владельца соответствующего контракта и связываются с artifact document.

Перед таблицей properties сначала дать короткое объяснение модели на обычном
языке: что является самим артефактом, что является его настройками, какие есть
дочерние узлы и какие данные появляются только при импорте, effective merge,
runtime или открытии editor. Это обязательная часть читаемого artifact doc.

Каждое найденное поле нужно классифицировать и сохранить в маршруте документации:
свойство schema, identity/хранение, editor contract или runtime result. Если
поле не является свойством артефакта, его нельзя молча исключать: указывается
документ-владелец и короткое объяснение, почему оно находится там.

### 3.9. Контрольные точки согласования

После каждого существенного этапа автор явно сообщает состояние работы и не скрывает решения, которые требуют участия владельца документации. Используются три сигнала:

| Сигнал | Когда используется | Что получает владелец документации |
| --- | --- | --- |
| **Нужно вычитать** | Подготовлен целевой документ или спорный фрагмент, который можно проверить по смыслу, языку и соответствию коду. | Точные файлы и разделы, которые нужно прочитать; список вопросов к тексту. |
| **Нужно решение** | Обнаружена граница владельца, неоднозначный термин, конфликт source с MVP, открытое архитектурное решение или кандидат на удаление/перенос. | Варианты, последствия и рекомендуемый вариант; без молчаливого выбора за владельца. |
| **Можно продолжать автоматически** | Изменение механическое и уже следует из принятого стандарта, кода или ранее согласованного решения. | Краткое описание действия и проверка результата; отдельное согласование не требуется. |

Сигнал **Нужно решение** применяется только к вопросам, которые блокируют корректное описание текущей границы, контракта, владельца или гарантии. Вопрос, относящийся только к будущей возможности или промышленной доработке, остаётся в `90_traceability.md` с понятным маршрутом в backlog и не задерживает описание текущего MVP.

Перед созданием нового целевого документа автор сначала сообщает, какие исходные материалы покрываются и какие решения уже подтверждены. Перед переносом или удалением source-файлов требуется отдельное подтверждение владельца. Перед изменением статуса документа, подготовкой commit или pull request автор сообщает итоговый список файлов и результаты проверок.

Для каждой следующей области автор должен отдельно указать:

1. что владелец документации должен вычитать;
2. какие решения нужно принять;
3. какие проверки автор выполнит самостоятельно.

## 5. Рабочие промты

### 5.1. Первичный анализ области

```text
Проанализируй платформенную область <area>. 
Сначала перечисли все файлы в docs-new/03_platform/<area>, отдельно source/requirements/offers/backlog. 
Потом найди подтверждающие code owners: projects, contracts, migrations, tests, frontend packages. 
Ничего не меняй. Дай карту: что является текущим MVP, что является source-ожиданием, что спорно, какие соседние области затронуты.
```

### 5.2. Решение по source/requirements

```text
Для source/requirements в <area> определи по каждому файлу:
1) есть ли уникальное содержание относительно старого docs;
2) какие темы уже покрыты целевыми документами;
3) какие темы должны стать open decision;
4) какие темы уйдут в concept/architecture/backlog/другую platform area;
5) можно ли удалить копию из area.
Пока ничего не удаляй, дай таблицу решений.
```

Удаление выполняется отдельным шагом после согласования таблицы решений и по
процедуре «Закрыть переходную папку после миграции». Само наличие канонического
документа не доказывает, что все уникальные требования уже разобраны.

### 5.3. Проверка готового пакета

```text
Вычитай все документы docs-new/03_platform/<area>. 
Проверь: все ли документы нужны, нет ли дублирования, воды, непонятного русского языка, противоречий между документами, ссылок на source/requirements, непроверенных будущих обещаний и терминологических разъездов. 
Отдельно проверь 90_traceability.md: понятны ли открытые решения без открытия старых документов.
Пока ничего не меняй, дай список точечных правок.
```

### 5.4. Приведение к стандарту


## 6. Уроки пилота Tenant/Security

| Урок | Правило для следующих областей |
| --- | --- |
| Source-копии быстро превращаются в мусорную папку. | Не оставлять `offers/requirements` в целевом package после разбора. |
| Открытое решение без названия непонятно читателю. | В ссылке указывать ID и тему: `TS-DEC-02 — User membership`. |
| Старый requirements может противоречить MVP. | В нормативный документ переносить только подтверждённое; остальное в traceability/backlog. |
| UI-термины легко становятся калькой. | Фиксировать русские термины и нежелательные формулировки в глоссарии. |
| Frontend модуля и frontend-платформа смешиваются. | В модуле описывать только его разделы/сценарии; общий shell и runtime packages вынести в `12_frontend_platform`. |
| История изменений вызывает путаницу. | Не добавлять новые строки руками; существующие строки не удалять без отдельного решения. |
| Перенос из pilot-папки ломает ссылки. | После перемещения всегда искать старый путь и пересчитать относительные ссылки. |
