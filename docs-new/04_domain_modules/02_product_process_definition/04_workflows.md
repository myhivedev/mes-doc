# Жизненный цикл - 02 Составы и технологии

## 1. Назначение документа

Документ фиксирует жизненный цикл ревизионных объектов модуля `02 Product & Process Definition`.

Доменная модель описана в `02_domain_model.md`. Проверки переходов описаны в `05_rules.md`. UI-карточки и стандартный WF-блок описываются в `06_ui_views.md` только ссылочно.

## 2. Объекты с жизненным циклом

Workflow `ProcessDocumentLifecycle` подключается к корневым ревизионным объектам:

| Тип объекта | Русское название | Почему нужен жизненный цикл |
|---|---|---|
| `ManufacturingBill` | Спецификация | Состав должен быть подготовлен и выпущен перед использованием в планировании, производстве или калькуляции. |
| `ProcessDefinition` | Технологическое описание | Технология должна быть подготовлена и выпущена перед рабочим использованием. |
| `CooperationScheme` | Схема кооперации | Схема кооперации влияет на обеспечение потребностей и должна проходить выпуск. |

Строки и зависимые объекты собственного workflow не получают. Их редактируемость определяется владельцем.

`NomenclatureSubstitution` не подключается к `ProcessDocumentLifecycle` в v1. Это правило применимости, а не технологический документ. Для него используются Common-архивирование, период действия и условия применимости.

`ManufacturingBillTemplate` и `ProcessTemplate` не подключаются к `ProcessDocumentLifecycle`. Это настроечные объекты параметров создания и нумерации; для них используются стандартные механизмы Common для архивирования и удаления.

`LabourType`, `ProcessingOperation`, `ManufacturingOperationType` и `WorkEnvironment` не подключаются к `ProcessDocumentLifecycle`. Это классификаторы технологии; для них используются стандартные механизмы Common для архивирования и удаления.

`ProductComposition` не подключается к `ProcessDocumentLifecycle`. Это расчетный результат, который использует `ProductCompositionStatus`.

## 3. Состояния

| StateCode | Русское название | Назначение | Runtime-политика |
|---|---|---|---|
| `Draft` | Черновик | Ревизия готовится. Рабочие поля, строки и области использования редактируются. | `IsInitial = true` |
| `PendingApproval` | На утверждении | Ревизия отправлена на согласование. Рабочие поля, строки и области использования заблокированы. | `Object/Self/ReadOnly` |
| `Released` | Выпущена | Ревизия утверждена. Использование определяется хранимыми областями использования. | `Object/Self/ReadOnly` |
| `Archived` | Архив | Архивное состояние жизненного цикла. | `IsArchiveState = true`, Common `IsArchived = true`, `Object/Self/ReadOnly` |

Алгоритмы продуктивного подбора исключают ревизию по `IsArchived`, а не по `WorkflowStateCode`.

## 4. Переходы

| Команда | Из состояния | В состояние | Назначение |
|---|---|---|---|
| `SubmitForApproval` | `Draft` | `PendingApproval` | Отправить ревизию на утверждение с выбранными областями использования. |
| `ReturnToDraft` | `PendingApproval` | `Draft` | Вернуть ревизию на доработку. |
| `Approve` | `PendingApproval` | `Released` | Утвердить и выпустить ревизию для выбранных областей использования. |
| `Archive` | `Draft`, `PendingApproval`, `Released` | `Archived` | Архивировать ревизию через lifecycle. |
| `Restore` | `Archived` | `Draft` | Вернуть ревизию из архива на доработку без автоматического выпуска. |

После `Restore` ревизия повторно проходит `SubmitForApproval` и `Approve`.

Переход `SubmitForApproval` по умолчанию заполняет поле ревизии `SubmittedForApprovalAt` текущей датой/временем. Переход `Approve` после успешного выполнения проверок по умолчанию заполняет поле ревизии `ApprovedAt` текущей датой/временем. Эти значения могут быть скорректированы пользователем только в состояниях, секциях и ролях, разрешенных workflow-политикой.

## 5. WorkflowStatePolicy

Минимальные политики:

| StateCode | TargetKind | TargetCode | EffectKind |
|---|---|---|---|
| `PendingApproval` | `Object` | `Self` | `ReadOnly` |
| `Released` | `Object` | `Self` | `ReadOnly` |
| `Archived` | `Object` | `Self` | `ReadOnly` |

При необходимости конфигурация может задавать более точечные field/section policies. Базовая политика v1 - блокировка всего объекта и его рабочих коллекций, но для дат `SubmittedForApprovalAt` и `ApprovedAt` допускается отдельная policy, разрешающая корректировку документной даты при наличии права.

## 6. WorkflowRuleBinding

Переход `Approve` должен вызывать прикладные проверки.

Переходы жизненного цикла должны иметь действия, заполняющие даты текущей ревизии по умолчанию:

| Переход | Действие | Результат |
|---|---|---|
| `SubmitForApproval` | `SetSubmittedForApprovalAt` | `SubmittedForApprovalAt = now()` |
| `Approve` | `SetApprovedAt` | `ApprovedAt = now()` после успешных проверок перехода |

Эти действия являются частью настройки workflow-переходов. Ручная корректировка `SubmittedForApprovalAt` и `ApprovedAt` возможна только через обычное сохранение карточки в рамках явно разрешенной workflow-политики.

Workflow не устанавливает все области использования автоматически и не требует включать полный набор флагов. Ревизия может выпускаться только для тех задач, для которых она готова: планирование, производство, калькуляция или их комбинация.

Области использования задаются как хранимые поля ревизии до отправки на утверждение. Переход `Approve` проверяет выбранный набор и блокирует выпуск, если выбранная область не обеспечена обязательными данными.

Механика проверки:

1. Workflow runtime на переходе `Approve` вызывает правила, привязанные к переходу через `WorkflowRuleBinding`.
2. Прикладной валидатор модуля читает текущие значения ревизии и ее строк, включая `UseInPlanning`, `UseInProduction`, `UseInCosting`, `AllowNewOperationalSelection`, период действия и условия применимости.
3. Общие проверки выполняются всегда.
4. Проверки готовности по областям выполняются только для включенных областей.
5. Если хотя бы одна обязательная проверка не проходит, переход не выполняется и ревизия остается в `PendingApproval`.

Общие проверки:

- обязательные поля ревизии заполнены;
- выбрана хотя бы одна область использования: `UseInPlanning`, `UseInProduction` или `UseInCosting`;
- `Revision` уникален внутри цепочки `Initial`;
- `ValidFrom` не позже `ValidTo`, если обе даты заданы;
- нет пересечения активных ревизий в той же области использования, периоде и контексте применимости;
- условия применимости корректны;
- связанные ревизии совместимы по продукту, исполнению, типу процесса, периоду и областям использования.

Проверки по областям:

| Область | Проверка при `Approve` |
|---|---|
| `UseInPlanning = true` | Заполнены данные, необходимые для планирования и разузлования. |
| `UseInProduction = true` | Заполнены данные, необходимые для производственного использования: операции, маршрут, материальные и ресурсные нормативы по правилам модуля. |
| `UseInCosting = true` | Заполнены данные, необходимые для калькуляции: нормы, количества, единицы и технологические ресурсы, если они участвуют в расчете. |

`AllowNewOperationalSelection` не является областью использования. Если он включен, ревизия должна иметь хотя бы одну выбранную область использования и проходить проверки продуктивного подбора.

## 7. Отображение в интерфейсе

Карточка объекта с жизненным циклом показывает стандартный WF-блок:

| Элемент | Правило |
|---|---|
| Текущее состояние | Показывается из workflow runtime. |
| Команды переходов | Показываются только команды, разрешенные из текущего состояния и прав пользователя. |
| Рабочие поля | В `PendingApproval`, `Released`, `Archived` доступны только для чтения. |

Состав списков, карточек и вкладок описан в `06_ui_views.md`. Кнопки стандартных workflow-переходов не повторяются в каждой UI-форме.
