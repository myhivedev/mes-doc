# Шаблон нормативного документа

Для создания нового документа копируйте только блок «Полный шаблон для
копирования». Справочную часть этого файла не копируйте. Замените все значения
в угловых скобках и удалите неприменимые разделы.

При создании нового документа:

- вычислите `id` и `type` по пути документа;
- замените все значения в угловых скобках;
- сохраните `version: '0.1'`, `status: draft` и `review_status: not_started`;
- `title` должен точно совпадать с единственным H1;
- в конце документа оставьте раздел «История изменений» только с заголовком и
  пустой таблицей;
- строки истории вручную не добавляйте: их создаёт workflow.

Папка `_working` является исключением: её файлы относятся к рабочим материалам
и не являются версионируемыми документами `docs-new`. Для файлов в `_working`
не создаются YAML-шапка и раздел «История изменений»; workflow их не проверяет,
не версионирует и не меняет статусы.

## 2. Краткая памятка по заполнению

| Что выбрать | Правило |
|---|---|
| `id` | Выбрать по таблице правил назначения ID ниже; основной случай — три числовых префикса пути |
| `type` | Выбрать по [разделу `docs-new`](#31-тип-по-разделу-docs-new), а для прикладного модуля или платформенной области — по имени файла |
| `status` / `review_status` | Для нового документа: `draft` / `not_started` |
| `scope` | Взять область верхнего уровня: `governance`, `platform`, `domain`, `operations` и т. п. |
| `module` | Взять имя папки модуля без числового префикса |
| `owner`, `created_by` | Указать GitHub username ответственного и автора с `@` |
| `reviewers` | Указать GitHub usernames проверяющих с `@` либо оставить `[]` |
| `holder` | Указать GitHub username держателя процесса с `@`; при создании нового документа по умолчанию поставить текущего автора |
| `version` | Для нового документа: `0.1`; далее обновляет workflow |

Правила назначения `id`:

| Расположение | Правило | Пример |
|---|---|---|
| Нумерованный документ модуля или области | Три кода берутся из пути | `03_platform/02_configuration/04_runtime.md` → `DOC-03-02-04` |
| Документ непосредственно в `00_governance` | Код модуля `00` | `00_governance/02_platform_area_documentation_playbook.md` → `DOC-00-00-02` |
| Служебный документ непосредственно в другом разделе, вне нумерованного модуля | Резервный код модуля `99` | `03_platform/00_platform_documentation_template.md` → `DOC-03-99-00` |
| Документ нумерованного модуля `00` | Код модуля берётся из папки `00_*` | `03_platform/00_foundation/00_platform_overview.md` → `DOC-03-00-00` |
| Документ непосредственно в `docs-new` | Область `99`, модуль `00` | `00_module_documentation_method.md` → `DOC-99-00-00` |
| Папка `requirements` | Код папки `99` | `00_governance/requirements/001_....md` → `DOC-00-99-01` |
| Ненумерованный `backlog.md` | Код документа `99` | `04_domain_modules/02_.../backlog.md` → `DOC-04-02-99` |
| Именованные тематические глоссарии | Закреплённые коды `02`–`05` | `11_glossary/platform_terms.md` → `DOC-11-99-02` |

## 4. Канонический промпт для работы через ИИ

Пользователь передаёт ИИ следующий текст, заменив путь и задачу:

```text
Оформи документ `<ПОЛНЫЙ ПУТЬ В DOCS-NEW>`.
Задача по содержанию: `<ЧТО СОЗДАТЬ ИЛИ ИЗМЕНИТЬ>`.

Перед работой обязательно открой актуальный файл
docs-new/00_governance/01_document_template.md, используй блок «Полный шаблон
для копирования» и правила этого канонического промпта. Не воспроизводи шапку
по памяти и не копируй справочную часть шаблона в целевой документ.

Если путь находится в docs-new/04_domain_modules/, дополнительно открой
docs-new/04_domain_modules/00_module_documentation_template.md и используй его
только для содержательной структуры соответствующего вида документа.
Если путь находится в целевом пакете docs-new/03_platform/ и существует файл
docs-new/03_platform/00_platform_documentation_template.md, используй его для
содержательной структуры платформенной области. YAML-шапку и историю во всех
случаях бери только из 01_document_template.md.

Сначала определи режим работы:
- новый файл — создай его из блока «Полный шаблон для копирования»;
- существующий файл без шапки — сохрани всё содержание и добавь шапку и пустую
  таблицу истории;
- уже подключённый документ — не сбрасывай version, status, created_at,
  created_by и существующие строки истории.

Обязательные правила:
- вычисли id и type по полному пути и таблицам шаблона;
- title должен точно совпадать с единственным H1;
- замени все значения в угловых скобках и удали неприменимые разделы;
- для нового или впервые подключаемого документа установи version: '0.1',
  status: draft, review_status: not_started и оставь точную пустую таблицу
  истории из шаблона;
- для существующего подключённого документа не меняй review_status вручную:
  его нормализует workflow по состоянию PR;
- version, updated_at, last_modified_by и строки истории не редактируй вручную;
- created_at должен совпадать с updated_at, а created_by — с
  last_modified_by только при создании нового документа;
- укажи реальный GitHub username автора. Не придумывай технического автора.
  Если username нельзя достоверно определить, запроси его у пользователя;
- holder может быть любым корректным GitHub username с @; для нового документа
  по умолчанию укажи текущего автора;
- reviewers может быть пустым списком [];
- раздел «История изменений» должен быть последним, после таблицы не должно
  быть текста; строки истории добавляет только workflow;
- не меняй содержательные разделы существующего документа за пределами
  поставленной задачи.

Перед завершением выполни проверку только этого документа:

python3 scripts/update_document_versions.py \
  --base origin/master \
  --validate-only \
  --path "<ПОЛНЫЙ ПУТЬ В DOCS-NEW>"

Затем выполни:

git diff --check -- "<ПОЛНЫЙ ПУТЬ В DOCS-NEW>"

Исправь найденные ошибки и повтори проверки. Не коммить, не отправляй ветку и
не создавай PR, если пользователь не попросил об этом отдельно.
```
