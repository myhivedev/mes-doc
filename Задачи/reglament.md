## КОНТЕКСТ РЕШЕНИЯ

Разрабатывается **MES-платформа**, которая одновременно работает на нескольких предприятиях и обеспечивает единый корпоративный подход к управлению.

Архитектура построена по принципу **«Центральный контур + независимые локальные контуры предприятий»**.

- **Центральный контур** — корпоративное управление, общие настройки, конфигурация, управление предприятиями, централизованная обработка данных.
- **Локальный контур** — MES-система предприятия; содержит всё необходимое для работы и способен работать автономно при недоступности центрального контура.
- Центральный контур **не является обязательным посредником** для выполнения производственных операций.
- Обмен между контурами — **асинхронный** (Kafka).
- Прямого обмена между предприятиями нет.
- Версия локального контура **не может быть новее** центрального.

### Функциональные части платформы

| Часть | Назначение |
|---|---|
| **Admin** | Управление платформой: предприятия, площадки, пользователи, роли, права, настройки |
| **Studio** | Настройка и конфигурирование платформы без изменения кода (типы объектов, формы, действия, процессы, правила, справочники, меню, нумерация, интеграции). **Не является Low-Code/No-Code** |
| **Platform Execution** | Исполняющая часть; предоставляет MES-модулям механизмы работы с объектами, данными, процессами, правами, справочниками, событиями, аудитом, интеграциями |

Платформа **не содержит бизнес-функций MES**, но предоставляет единый фундамент для их создания.

### Технологический стек

- **Java / Spring Boot** — серверная часть
- **React** — пользовательские приложения
- **PostgreSQL** — хранение данных
- **Kafka** — обмен событиями и асинхронная синхронизация
- **Keycloak** — внешняя система идентификации и аутентификации
- **Kubernetes** — запуск и масштабирование
- **Liquibase** — миграции БД
- **Harbor** — хранение Docker-образов
- **Nexus** — хранение артефактов (Maven, npm, Helm-чарты)
- **SonarQube** — статический анализ кода
- **GitLab CI** — сборка, тесты, анализ
- **Argo CD** — доставка на окружения
- **Vault** — хранение секретов

### Производственный уровень

Оборудование, станки, роботы, линии, датчики, контроллеры, PLC, SCADA. Взаимодействие — только через локальный контур предприятия.

### Главное архитектурное свойство

> Центральный контур обеспечивает единообразие и корпоративное управление, а локальные контуры обеспечивают автономную работу предприятий.

## ИСХОДНЫЕ ДАННЫЕ ПО ПРОЦЕССУ РАЗРАБОТКИ

### Модель ветвления

**Git Flow**.

Основные ветки: `main`, `develop`, `release/*`, `feature/*`, `bugfix/*`, `hotfix/*`.

Именование веток: `<type>/<issue-id>-<short-description>`, только латиница, нижний регистр, дефис, описание ≤ 5 слов.

Примеры:
- `feature/MES-123-equipment-state`
- `bugfix/MES-456-fix-sync-timeout`
- `hotfix/MES-789-critical-auth-fix`
- `release/1.4.0`

### Сценарий работы

1. Задача заводится в трекере.
2. Ветка создаётся от `develop`.
3. Разработка → PR в `develop`.
4. Code review (минимум 1 аппрув) → CI зелёный → merge.
5. Перед релизом создаётся `release/X.Y.Z` от `develop`.
6. Стабилизация, тесты, release notes.
7. Merge `release/*` → `main` + тег `vX.Y.Z`.
8. Merge `release/*` → `develop`.
9. `hotfix/*` создаётся от `main`, после исправления merge в `main` и `develop`.

### Долгоживущие release-ветки

Да. Для каждой поддерживаемой версии создаётся `release/X.Y.Z`. Живёт, пока версия поддерживается.

### Hotfix на предприятии, которое не обновилось

Исправление выпускается как patch-версия (например, `1.3.5`) от соответствующей `release/1.3.x`. Обновление — по регламенту.

### LTS-версии

Да. Каждая третья minor-версия объявляется LTS. Поддержка — 12 месяцев.

### Обратная совместимость

Локальный контур совместим с центральным на 2 minor-версии назад.

### Feature-флаги

Да, обязательны для функциональности, включаемой поэтапно. Удаляются после полного включения.

## ИСХОДНЫЕ ДАННЫЕ ПО ПРОЦЕССУ РАЗРАБОТКИ (детали)

- Уровень формализации: **средний** (issue → ветка → PR → review → CI → merge).
- Code review обязателен, минимум **1 аппрув**.
- Обязательное документирование до начала разработки: **ADR, RFC, design doc**.
- Коммиты: **Conventional Commits**.
- Практик парного программирования нет; разработчики работают индивидуально, в паре только обсуждают контракты backend + frontend.

### Требования к покрытию тестами

- **Unit:** ≥ 70% для нового кода, ≥ 60% для модуля.
- **Integration:** обязательны для всех интеграций с БД, Kafka, внешними системами.
- **Contract:** обязательны для API между frontend и backend, между контурами.
- **E2E:** обязательны для критичных сценариев.
- **Нагрузочные:** обязательны перед выпуском LTS и при изменениях производительности.

### Окружения

| Окружение | Назначение |
|---|---|
| dev | Разработка, автотесты |
| test | Приёмочное тестирование |
| stage (в перспективе) | Предпродуктивное тестирование |
| prod (в перспективе) | Продуктив |

## ИСХОДНЫЕ ДАННЫЕ ПО CI/CD

### Инструменты

- **GitLab CI** — сборка, тесты, статический анализ.
- **Argo CD** — доставка на окружения.
- **Harbor** — хранение Docker-образов.
- **Nexus** — хранение артефактов (Maven, npm, Helm-чарты).
- **SonarQube** — статический анализ кода.
- **Линтеры** — для кода и конфигураций.
- **Vault** — секреты.

### Pipeline на PR

1. Линтеры.
2. Unit-тесты.
3. Проверка Conventional Commits.
4. Проверка ссылки на issue.
5. Сборка без публикации.

### Pipeline при merge в основную ветку

1. Unit + integration + contract тесты.
2. **SAST** (SonarQube).
3. **SCA** — проверка зависимостей и лицензий.
4. Сборка Docker-образа.
5. Публикация в **Harbor**.
6. Публикация артефактов в **Nexus**.
7. Развёртывание на **dev** через Argo CD.

### Pipeline при создании тега

1. Полный набор тестов (unit, integration, contract, e2e).
2. SAST + DAST.
3. SCA.
4. Сборка и **подпись** Docker-образов (Cosign).
5. Публикация Helm-чартов в **Nexus**.
6. Формирование release notes.
7. Развёртывание на **test**.
8. Передача артефактов release manager.

### Окружения и доставка

- dev и test — CI автоматически.
- stage и prod — release manager через Argo CD.
- Развёртывание на prod — **только по тегу**.
- Обновление локальных контуров — в окна обслуживания.

### Подписание артефактов

- Docker-образы — Cosign.
- Helm-чарты — подпись.
- Проверка подписи обязательна на stage и prod.

### Rollback

- Автоматический при провале health-check.
- Ручной — по решению release manager.
- Откат БД — только через обратно совместимые миграции.

### Canary / blue-green

- dev и test — blue-green.
- prod — canary для центрального контура, поэтапное обновление для локальных.

### Тестирование асинхронной синхронизации в CI

- Разворачиваются два контура (центральный + локальный).
- Сценарии: разрыв связи, накопление данных, восстановление, доставка конфигурации, порядок событий.
- Результаты — обязательный gate для релиза.

## ИСХОДНЫЕ ДАННЫЕ ПО БД И МИГРАЦИЯМ

- Инструмент: **Liquibase**.
- Модель **expand/contract** обязательна.
- Откат — только для expand-миграций.
- Contract-миграции откату не подлежат.
- Миграции должны быть **zero-downtime**.
- Миграция на предприятии — в момент обновления релиза.
- Перед миграцией — обязательный бэкап.

## ИСХОДНЫЕ ДАННЫЕ ПО ВЕРСИОНИРОВАНИЮ

- Схема: **SemVer**.
- Breaking change → **MAJOR**-версия, требуется ADR и согласование с техническим архитектором.
- Версионируется: платформа, MES-модули, API, конфигурации Studio, Helm-чарты.
- Release manager — выделенная роль.
- Артефакты релиза: Docker-образы, Helm-чарты, миграции, конфигурации, документация, release notes.

### Формат release notes

```
# Release X.Y.Z
## Дата
## Тип (major/minor/patch/LTS)
## Состав
## Изменения (Added / Changed / Fixed / Security)
## Breaking changes
## Совместимость
## Инструкции по обновлению
## Известные проблемы
```

### Матрица совместимости

Ведётся в `mes-docs`. LTS поддерживаются 12 месяцев. Каждая третья minor — LTS.

### Откат релиза на предприятии

- Инициирует ответственный представитель предприятия или release manager.
- Решение принимает release manager.
- Откат — возврат к предыдущему тегу.
- Инцидент регистрируется, проводится разбор.

## ИСХОДНЫЕ ДАННЫЕ ПО БЕЗОПАСНОСТИ

- Секреты — в **Vault**, ротация не реже 1 раза в 6 месяцев.
- **SAST** — на каждый merge в основную ветку и при создании тега (SonarQube).
- **DAST** — при создании тега, на test-окружении.
- **SCA** — на каждый merge.
- Лицензионная чистота (с учётом специфики РФ): приоритет — Apache 2.0, MIT, BSD; запрещены GPL/AGPL без согласования; обязательная проверка SCA; реестр зависимостей; импортозамещение; запрет зависимостей без подтверждённого источника поставки в РФ.
- Регуляторные требования: считаем применимыми требования ФСТЭК/ГОСТ в области ИБ.
- SLA на уязвимости: Critical — 24 часа, High — 7 дней, Medium — 30 дней, Low — 90 дней.
- Ответственный — security officer.

## ИСХОДНЫЕ ДАННЫЕ ПО СИСТЕМЕ ПОСТАНОВКИ И КОНТРОЛЯ ЗАДАЧ

### Иерархия

```
Инициатива → Эпик → Задача/История → Подзадача
```

### Обязательные поля задачи

Заголовок (инфинитив), тип, эпик, описание, приоритет, Story Points, компонент, ссылки.

### Правила формулировки

Заголовок — краткий и точный. Описание содержит: проблему, предлагаемое решение, критерии приёмки, влияние на совместимость контуров.

### Связи

`is blocked by`, `relates to`, `causes` / `is caused by`.

### Эпики

- Атрибуты: название, инициатива, владелец, целевая веха, статус, прогресс.
- Прогресс: `(Story Points Done / Total Story Points) × 100`.
- Автозакрытие при завершении всех дочерних задач.
- Обязательная привязка задач к эпику.
- Еженедельный dependency scrub.

### Состояния задач

```
Open → In Progress → In Review → Done
         ↑                ↓
      Reopened ←──── Rejected
```

Для багов: `Open → In Progress → In Review → Resolved → Closed`.

Дополнительно: `Needs Explanation`.

### Таймтрекинг

- Двойная оценка: Story Points + Original Estimate (часы) + Time Spent.
- Логирование ежедневно.
- Одна запись — одна задача.
- При завершении Remaining Estimate обнуляется.
- Уведомление при `Time Spent > Original Estimate × 1.5`.
- Еженедельный отчёт по отклонениям.

### Дашборды

1. **Program Health** — для технического архитектора и product owner.
2. **Development** — для команды.
3. **Release** — для release manager.
4. **Enterprise** — для специалистов внедрения.

### Автоматическая отчётность по вехам

- Формулы: Epic Progress, Milestone Progress, Release Progress.
- Jira Automation: суммирование Story Points, автозакрытие эпиков, еженедельный отчёт, обнаружение зависших эпиков.
- RAG-статус: Green / Amber / Red по прогрессу, блокерам, просрочкам.
- Формат еженедельного отчёта — Markdown + snapshot в PostgreSQL.

### Метрики

Velocity, Cycle Time, Lead Time, WIP, Blocked Rate, Estimation Accuracy, Epic Progress Accuracy.

### Регламентные мероприятия

Daily Stand-up, Backlog Refinement, Dependency Scrub, Milestone Review, Retrospective.

12. **Выпуск релизов** (release manager, артефакты, release notes, откат).
13. **Доставка на предприятия и обновление** (окна, регламент, инциденты, телеметрия).
14. **Безопасность** (Vault, SAST/DAST/SCA, лицензии, ФСТЭК/ГОСТ, SLA на уязвимости).
15. **Документация** (docs-as-code, обязательные документы, ответственные).
16. **Корпоративные стандарты.**
17. **Управление задачами** (иерархия, принципы, эпики, состояния, таймтрекинг, дашборды, автоматическая отчётность, метрики, регламентные мероприятия).
18. **Приложения** (шаблоны PR, ADR, RFC, release notes, задачи, эпика, еженедельного отчёта).

### Требования к качеству

- Документ — на русском языке.
- Стиль — нормативный, однозначный, без воды.
- Все правила — проверяемые и однозначно трактуемые.
- Все автоматизации — описаны так, чтобы их можно было реализовать в GitLab CI, Argo CD, Jira Automation, SonarQube, Harbor, Nexus.
- Все пороги и SLA — числовые.
- Все роли — с указанием ответственности.
- Документ пригоден для утверждения как внутренний регламент.

### Чего избегать

- Общих формулировок без критериев.
- Противоречий между разделами.
- Смешения процессов разработки и управления задачами без явного разделения.
- Упоминания инструментов, не указанных в исходных данных, без пометки «предложение».

## ФОРМАТ ОТВЕТА

Выдай готовый документ в Markdown, с заголовками, таблицами, списками, шаблонами и формулами. В конце — раздел «Что осталось уточнить» с вопросами, которые требуют ответа перед утверждением.

## ДОПОЛНИТЕЛЬНО

Если в процессе разработки документа возникнут противоречия в исходных данных — явно укажи их и предложи вариант разрешения. Если каких-то данных не хватает — задай уточняющие вопросы в конце документа, но не останавливай разработку.
