# Прикладные операции и алгоритмы - 02 Составы и технологии

## 1. Назначение документа

Документ описывает прикладные операции, внутренние функции и алгоритмы модуля `02 Product & Process Definition`.

Документ не описывает стандартные create/read/update/delete, сохранение карточки, проверку прав и выполнение workflow-переходов без предметного алгоритма модуля.

## 2. Общие функции и политики операций

Раздел описывает внутренние прикладные функции и предметные политики. Они вызываются прикладными операциями, обработчиками Object Runtime или другими модулями, но не являются отдельными пользовательскими командами сами по себе.

### 2.1 Использование функций GMD для `UnitOfOperation`

Модуль не реализует собственный механизм выбора и пересчета единиц количественных норм.

Все операции модуля, которые работают с количеством или материальной нормой, используют функции GMD:

- получение доступных единиц операции;
- определение единицы операции по умолчанию;
- проверка применимости выбранной единицы операции;
- пересчет количества из `UnitOfOperation` в базовую ЕИ НП и обратно.

Это относится к спецификациям, технологическим нормам, анализу состава и результатам применения замен номенклатуры.

При сохранении объектов и строк, где предусмотрены базовые количественные поля, обработчик пересчитывает их через функции GMD. Пользователь вводит норму в выбранной `UnitOfOperation`, а поля в базовой ЕИ являются системным результатом пересчета.

Нормативная карточка `NomenclatureSubstitution` не хранит собственную базовую пару нормы. Она задает правило возможной замены, а базовые количества рассчитываются и фиксируются в результате применения замены.

### 2.2 Использование шаблонов при создании

`ManufacturingBillTemplate` и `ProcessTemplate` задают параметры создания и нумерации. Если пользователь не выбрал шаблон явно, Object Runtime использует активный шаблон текущего `Tenant` с `IsDefault = true`.

При создании `ManufacturingBill` выбранный `ManufacturingBillTemplate`:

- сохраняется в `ManufacturingBill.ManufacturingBillTemplate`;
- задает `PositionNumberingStep` для нумерации новых позиций спецификации.

При создании `ProcessDefinition` выбранный `ProcessTemplate`:

- сохраняется в `ProcessBase.ProcessTemplate`;
- задает шаги нумерации переделов, операций, переходов и ресурсных позиций;
- задает длины форматированных номеров передела, операции и перехода в ТП.

Для переделов, операций и переходов поле `Number` хранит числовой номер строки внутри владельца. Если пользователь не указал `NumberInProcess`, система заполняет его из `Number` с длиной, заданной в `ProcessTemplate`: `SegmentNumberInProcessLength`, `OperationNumberInProcessLength` или `StepNumberInProcessLength`. Пользовательское значение `NumberInProcess` сохраняется, если оно прошло проверку уникальности.

Последующее изменение шаблона не изменяет уже созданные спецификации, технологии и их строки.

### 2.3 Использование классификаторов при создании передела и операции

Классификаторы `LabourType`, `ProcessingOperation`, `ManufacturingOperationType` и `WorkEnvironment` используются как источники выбора и значений по умолчанию для строк технологии.

При создании или сохранении `ProcessSegment`:

- если `Name` не задано и выбран `LabourType`, система заполняет `Name = LabourType.Name`;
- если `DurationRateType` не задан, применяется `PerLot`;
- если `DurationUnit` не задана, применяется `WorkShift`;
- пользователь может переопределить `Name`, если состояние технологии и права разрешают изменение передела.

При создании или сохранении `ProcessOperation`:

- если выбрана `ProcessingOperation`, система заполняет `LabourType` из `ProcessingOperation.LabourType`, если пользователь не задал значение явно и значение задано в классификаторной операции;
- если выбрана `ProcessingOperation`, система заполняет `ManufacturingOperationType` из `ProcessingOperation.ManufacturingOperationType`, если пользователь не задал значение явно и значение задано в классификаторной операции;
- если `Name` не задано и выбрана `ProcessingOperation`, система заполняет `Name = ProcessingOperation.Name`;
- если `Name` не задано, `ProcessingOperation` не выбрана, но выбран `ManufacturingOperationType`, система заполняет `Name = ManufacturingOperationType.Name`;
- если `ConfirmationStages` не задана и выбран `ManufacturingOperationType`, система заполняет `ConfirmationStages = ManufacturingOperationType.ConfirmationStages`.

`PaymentGroup` используется как внешняя ссылка на ресурсный модуль. Его выбор не вызывает создания или изменения справочника группы оплаты в модуле.

## 3. Изменение компонента технологии

Операция применяет создание, изменение или удаление материальной позиции передела технологии и связанной позиции индивидуальной спецификации ТО.

Операция используется для технологии с индивидуальной спецификацией ТО. Для общей технологии без `ProcessDefinition.ManufacturingBill` пользователь распределяет и уточняет материальные позиции переделов и операций через ссылки на позиции применимых спецификаций продукта; скрытая индивидуальная спецификация ТО при этом не создается.

Вход:

| Параметр | Описание |
|---|---|
| `ProcessDefinition` | Редактируемая технология. |
| `ChangeMode` | `Create`, `Update` или `Delete`. |
| `SegmentNumber` | Значение `ProcessSegmentBase.Number` для передела, в котором создается, изменяется или удаляется материальная позиция. Обязательно для создания; при изменении или удалении может использоваться как дополнительное ограничение отбора. |
| `CurrentMaterialPosition` | Изменяемая материальная позиция передела; не заполняется при создании. |
| `CurrentComponent` | Текущий компонент для массовой замены, если позиция не указана напрямую. |
| `PositionData` | Значения материальной позиции: компонент, исполнение, тип входа/выхода, количественные нормы, единицы, округление, места отпуска/списания и другие поля `MaterialPositionBase`. |
| `SubstitutionFactor` | Коэффициент пересчета текущих норм при замене компонента; используется только для `ChangeMode = Update`. |

Алгоритм:

1. Проверить, что технология доступна для изменения по workflow-policy и правам пользователя.
2. Проверить, что `ProcessDefinition.ManufacturingBill` заполнена и указывает на индивидуальную спецификацию ТО с `IsForProcessDefinition = true`.
3. Проверить совместимость индивидуальной спецификации ТО с технологией по продукту, исполнению и типу процесса.
4. Найти передел по `SegmentNumber`.
5. Для `Create` найти или создать позицию индивидуальной спецификации ТО для компонента из `PositionData`, затем создать `ProcessSegmentMaterialPosition` в переделе и связать ее с этой `ManufacturingBillPosition`.
6. Для `Update` найти изменяемые `ProcessSegmentMaterialPosition` по `CurrentMaterialPosition` или по `CurrentComponent` и, если задан, по `SegmentNumber`.
7. Для `Update` изменить компонент, исполнение и нормы материальных позиций. Если `SubstitutionFactor > 0`, пересчитать `RateForSetup` и `RateForProcessing` от текущих значений; иначе использовать явно переданные значения `PositionData`.
8. Для `Delete` удалить найденные `ProcessSegmentMaterialPosition`. Связанная позиция индивидуальной спецификации ТО удаляется только если она больше не используется ни одной материальной позицией этой технологии и проходит правила удаления строки состава.
9. Пересчитать базовые количественные нормы через функции GMD.
10. Выполнить проверки материальных позиций технологии, позиции индивидуальной спецификации ТО и их связи.

Операция может запускаться для нескольких технологий. Каждая технология обрабатывается в отдельной транзакции; ошибка по одной технологии не откатывает изменения по другим технологиям.

## 4. Создание новой ревизии

### 4.1 Общая операция `CreateNewRevision`

Применяется к:

- `ManufacturingBill`;
- `ProcessDefinition`;
- `CooperationScheme`.

Вход:

| Параметр | Описание |
|---|---|
| `SourceRevision` | Исходная ревизия. |
| `NewRevision` | Новый номер ревизии. Если не задан, берется следующий номер. |
| `CopyUseAreas` | Копировать области использования. |
| `CopyUseConditions` | Копировать условия применимости. |

Алгоритм:

1. Проверить, что исходная ревизия существует и доступна пользователю для чтения.
2. Проверить, что новая ревизия не существует в той же цепочке `Initial`.
3. Создать новый объект того же типа.
4. Скопировать рабочие поля исходной ревизии.
5. Установить `Initial` равным `SourceRevision.Initial`.
6. Установить `Revision = NewRevision`.
7. Скопировать строки коллекций по политике типа объекта.
8. Если создается новая ревизия `ProcessDefinition` с индивидуальной спецификацией ТО, создать новую ревизию этой индивидуальной спецификации и установить ее в `ProcessDefinition.ManufacturingBill` новой технологии.
9. Очистить системные даты жизненного цикла новой ревизии: `SubmittedForApprovalAt = null`, `ApprovedAt = null`.
10. Установить workflow-состояние новой ревизии `Draft`.
11. Сохранить связь новой ревизии с исходной в audit history.

Операция не закрывает старую ревизию автоматически.

### 4.2 Новая ревизия с предметным изменением компонента

Операция используется для предметных действий создания новой ревизии с созданием, изменением или удалением компонента.

Это отдельный алгоритм, но не отдельное право.

Алгоритм:

1. Выполнить `CreateNewRevision`.
2. Если новая ревизия технологии использует индивидуальную спецификацию ТО, работать с новой связанной ревизией этой спецификации.
3. Применить операцию изменения компонента технологии к новой ревизии.
4. Выполнить обычные проверки сохранения новой ревизии.

## 5. Создание копии технологии

Вход:

| Параметр | Описание |
|---|---|
| `SourceProcessDefinition` | Исходная технология. |
| `NewCode` | Код новой технологии. |
| `NewProduct` | Новый продукт, если копия создается для другого продукта. |
| `NewProductVariant` | Новое исполнение продукта, если копия создается для другого исполнения. |
| `NewProcessType` | Новый тип процесса, если копия создается для другого типа процесса. |

Алгоритм:

1. Проверить доступ на чтение исходной технологии.
2. Создать новый `ProcessDefinition`.
3. Скопировать рабочие поля и коллекции по политике копирования.
4. Установить `Initial` на новую первую ревизию.
5. Установить `Revision = 1`.
6. Если исходная технология использует индивидуальную спецификацию ТО, создать копию этой спецификации, применить к ней новый продукт, исполнение и тип процесса, если они переданы, и установить ее в `ProcessDefinition.ManufacturingBill` новой технологии.
7. Установить состояние `Draft`.
8. Применить новые значения продукта, кода и контекста, если они переданы.

### 5.1 Копия технологии с предметным изменением компонента

Операция используется для предметного действия создания копии технологии с созданием, изменением или удалением компонента.

Это отдельный алгоритм, но не отдельное право.

Алгоритм:

1. Выполнить создание копии технологии.
2. Если копия технологии использует индивидуальную спецификацию ТО, работать с новой связанной копией этой спецификации.
3. Применить операцию изменения компонента технологии к копии.
4. Выполнить обычные проверки сохранения копии.

## 6. Подбор применимой спецификации

Вход:

| Параметр | Описание |
|---|---|
| `Product` | Продукт. |
| `ProductVariant` | Исполнение продукта, если задано. |
| `ProcessType` | Тип процесса, если задан. |
| `UsageArea` | `Planning`, `Production` или `Costing`. |
| `Date` | Дата подбора. |
| `Context` | Контекст условий применимости. |
| `ForNewOperationalSelection` | Требуется ли выбор для новой рабочей ссылки. |

Алгоритм:

1. Отобрать `ManufacturingBill` по продукту, исполнению и типу процесса.
2. Исключить `IsDeleted = true` и `IsArchived = true`.
3. Применить период действия.
4. Применить нужную область использования.
5. Если `ForNewOperationalSelection = true`, применить `AllowNewOperationalSelection = true`.
6. Проверить `UseCondition`.
7. Проверить отсутствие конфликтующих ревизий.
8. Выбрать наиболее подходящую ревизию по правилу приоритета: точное исполнение, точный тип процесса, период, номер ревизии.

Проверка `UseCondition` выполняется единообразно для всех владельцев условий: пустая коллекция условий означает отсутствие дополнительных ограничений; непустая коллекция должна выполниться по всем строкам, применимым на дату проверки. Строка условия берет значение из `Context` по `ConditionSubject` и сравнивает его с соответствующим типизированным значением строки через `ComparisonOperator`.

Для `ConditionSubject = ItemParameter` контекст должен содержать значения реквизитов продукта, исполнения, заказа или другого расчетного контекста. Сравнение выполняется по строкам `UseCondition.ParameterValues` через общий контракт GMD для значений реквизитов.

## 7. Подбор применимой технологии

Алгоритм аналогичен подбору спецификации, но выполняется для `ProcessDefinition`.

Если `ProcessDefinition.ManufacturingBill = null`, технология является общей. Применимая спецификация продукта подбирается отдельно по продукту, исполнению, типу процесса, периоду действия, области использования и условиям применимости.

Если `ProcessDefinition.ManufacturingBill` заполнена, технология использует индивидуальную спецификацию ТО:

- `ManufacturingBill.IsForProcessDefinition = true`;
- индивидуальная спецификация должна быть совместима с технологией по продукту, исполнению и типу процесса;
- для планирования индивидуальная спецификация должна иметь `UseInPlanning = true`;
- для производства индивидуальная спецификация должна иметь `UseInProduction = true`;
- для калькуляции индивидуальная спецификация должна иметь `UseInCosting = true`.

## 8. Подбор схемы кооперации

Вход:

- продукт;
- исполнение;
- дата;
- область использования;
- контекст условий.

Алгоритм:

1. Отобрать `CooperationScheme` по продукту и исполнению.
2. Исключить удаленные и архивные ревизии.
3. Применить период действия и область использования.
4. Проверить условия применимости.
5. Выбрать подходящую ревизию схемы.

## 9. Расчет потребностей по нормативному источнику

Раздел описывает внутренние функции расчета потребностей, которые вызываются анализом состава, разузлованием, подбором применимых нормативов и будущими операционными модулями.

Функции не являются самостоятельными пользовательскими командами. В UI пользователь запускает операцию `RunProductCompositionAnalysis`, а расчет потребностей выполняется внутри нее.

### 9.1 Получить потребности по спецификации

Функция рассчитывает потребности по строкам выбранной `ManufacturingBill`.

Вход:

| Параметр | Описание |
|---|---|
| `ManufacturingBill` | Спецификация, по которой рассчитываются потребности. |
| `ProductVariant` | Исполнение продукта, для которого выполняется расчет. |
| `QuantityBaseUnit` | Количество продукта в базовой ЕИ продукта. |
| `NormDate` | Дата применимости норм. |
| `IsBaseProductBill` | Признак расчета только по базовому составу без дополнительных условий применимости. |
| `Context` | Контекст проверки условий применимости. |

Алгоритм:

1. Проверить доступность спецификации для расчета: не удалена, не архивна, дата попадает в период действия.
2. Отобрать позиции `ManufacturingBillPosition`, действующие на `NormDate`.
3. Если `IsBaseProductBill = true`, исключить позиции с условиями применимости.
4. Проверить условия применимости позиции по `Context`.
5. Для каждой позиции рассчитать потребность из `QuantityBaseUnit`, норм `RateForSetup` / `RateForProcessing`, размера партии и правил округления позиции.
6. Пересчитать результат в базовую ЕИ компонента через функции GMD.
7. Вернуть строки потребности со ссылкой на `ManufacturingBillPosition`, рассчитанным количеством в `UnitOfOperation`, базовым количеством и типом входа/выхода.

Функция не изменяет спецификацию и ее позиции.

### 9.2 Получить потребности по технологическому описанию

Функция рассчитывает потребности по материальным позициям `ProcessDefinition`.

Вход:

| Параметр | Описание |
|---|---|
| `ProcessDefinition` | Технологическое описание, по которому рассчитываются потребности. |
| `ManufacturingBill` | Спецификация продукта, если она уже подобрана или задана вручную. |
| `ProductVariant` | Исполнение продукта. |
| `QuantityBaseUnit` | Количество продукта в базовой ЕИ продукта. |
| `NormDate` | Дата применимости норм. |
| `IsBaseProductBill` | Признак расчета только по базовому составу без дополнительных условий применимости. |
| `IsCalcWithLossScrap` | Учитывать выход годного, технологические потери и брак переделов. |
| `BySegments` | Возвращать детализацию по переделам. |
| `Context` | Контекст проверки условий применимости. |

Алгоритм:

1. Проверить доступность технологии для расчета: не удалена, не архивна, дата попадает в период действия.
2. Определить спецификацию, с которой сопоставляются материальные позиции технологии:
   - для технологии с индивидуальной спецификацией ТО используется `ProcessDefinition.ManufacturingBill`;
   - для общей технологии используется переданная или подобранная спецификация продукта.
3. Отобрать материальные позиции переделов и операций, связанные с позициями выбранной спецификации.
4. Проверить период действия и условия применимости связанных позиций спецификации.
5. Если `IsBaseProductBill = true`, исключить позиции с условиями применимости.
6. Рассчитать потребности по нормам материальных позиций технологии.
7. Если `IsCalcWithLossScrap = true`, применить параметры передела: `YieldFactor`, `ManufacturingLossFactor`, `LossQty`, `FactorRoundingRule`.
8. Пересчитать результат в базовую ЕИ компонента через функции GMD.
9. Вернуть строки потребности со ссылками на `ManufacturingBillPosition`, материальную позицию передела или операции, передел, рассчитанное количество в `UnitOfOperation` и базовое количество.

Функция не создает скрытую индивидуальную спецификацию для общей технологии.

### 9.3 Расчет количества строки потребности

Функция рассчитывает количество конкретной строки потребности и используется функциями `Получить потребности по спецификации` и `Получить потребности по технологическому описанию`.

Правила:

- исходное количество продукта передается в базовой ЕИ продукта;
- количественная норма строки хранится в `UnitOfOperation` и имеет базовый эквивалент в базовой ЕИ компонента;
- допустимость `UnitOfOperation`, значение по умолчанию и пересчет в базовую ЕИ выполняются через функции GMD;
- временные нормы `RateFor...Time` не участвуют в расчете количественной материальной потребности и хранятся в секундах;
- `DurationUnit` передела и lead time схемы кооперации не используется как единица материальной нормы.

Результат функции содержит рассчитанное количество в единице операции, рассчитанное количество в базовой ЕИ компонента и диагностическое сообщение, если расчет невозможен.

## 10. Анализ состава

Операция `RunProductCompositionAnalysis` создает новый `ProductComposition` или пересчитывает существующий анализ состава.

Вход:

| Параметр | Описание |
|---|---|
| `ProductComposition` | Существующий анализ состава, если выполняется перерасчет. Не заполняется при создании нового анализа. |
| `Product` | Продукт анализа. |
| `ProductVariant` | Исполнение продукта. |
| `ProductQty` | Количество продукта. |
| `Unit` | Единица операции. |
| `NormDate` | Дата норм. |
| `CompositionType` | Тип анализа. |
| `ProcessType` | Тип процесса для подбора нормативов. |
| `ProductManufacturingBill` | Исходная спецификация продукта, если задана. |
| `ProductProcessDefinition` | Исходная технология продукта, если задана. |
| `CooperationScheme` | Схема кооперации, если задана. |
| `MainProduct` | Конечное изделие для проверки условий применимости. |
| `MainProductSerialNumber` | Серийный номер конечного изделия для проверки условий применимости. |
| `DemandGroup` | Группа спроса для проверки условий применимости. |
| `Project` | Проект для проверки условий применимости. |
| `ProjectPhase` | Этап проекта для проверки условий применимости. |
| `ProductOrder` | Заказ на ГП для проверки условий применимости. |
| `ProductOrderPosition` | Позиция заказа на ГП для проверки условий применимости. |
| `ParameterValues` | Значения реквизитов расчетного контекста. |

Тип анализа:

| `CompositionType` | Использование источников |
|---|---|
| `ByManufacturingBill` | Разузлование выполняется по применимым спецификациям. |
| `ByProcessDefinitionBill` | Разузлование выполняется по применимым технологиям с агрегированием материалов по позициям состава. |
| `ByProcessDefinitionSegment` | Разузлование выполняется по применимым технологиям с детализацией материалов по переделам. |

Алгоритм:

1. Если `ProductComposition` не передан, создать заголовок анализа с параметрами расчета, `CompositionDate` и начальным `CompositionStatus = New`.
2. Если `ProductComposition` передан, использовать его как текущий анализ; перед расчетом очистить прежние строки результата `Positions`, счетчики и сообщения.
3. Пересчитать `ProductQtyBaseUnit` из `ProductQty` и `Unit` через функции GMD.
4. Определить исходную спецификацию и/или технологию через параметры анализа или операции подбора.
5. Выполнить разузлование состава с использованием функций расчета потребностей по спецификации или технологическому описанию.
6. Применить условия применимости по контексту анализа состава: продукт, исполнение, тип процесса, дата норм, конечное изделие, серийный номер, спрос, проект, заказ и значения реквизитов.
7. Применить правила замен номенклатуры.
8. Применить схему кооперации, если она задана.
9. Сформировать корневую строку `ProductCompositionPosition` для продукта анализа и дочерние строки результата разузлования.
10. Заполнить `PositionStatus` и `Message` у строк `ProductCompositionPosition`.
11. Установить `CalculationDate`, счетчики `PositionsCount`, `WarningsCount`, `ErrorsCount` и итоговый `CompositionStatus`: `Calculated`, `CalculatedWithWarnings` или `CalculatedWithErrors`.

Повторный расчет существующего анализа обновляет текущий расчетный результат. Если требуется сохранить сравнимую историю старого результата, пользователь создает новый `ProductComposition` с теми же параметрами и запускает расчет для новой записи.

Если после успешного расчета изменены параметры анализа или расчетный контекст, Object Runtime устанавливает `CompositionStatus = RequiredRecalculation`.

Флаги расчета:

- `IsBaseProductBill`: при подборе нормативов исключаются ревизии и позиции с непустыми условиями применимости.
- `IsSetBaseVersion`: если по заданному контексту не найдена применимая ревизия, допускается fallback на действующую базовую ревизию без условий применимости.
- `IsCalcWithLossScrap`: при расчете по технологиям учитываются `YieldFactor`, `ManufacturingLossFactor`, `LossQty` и правила округления переделов.
- `IsCalcByCoproducts`: в результат включаются попутные продукты, если они заданы в составе или технологии.

## 11. Проверка циклов состава

Операция проверяет, что разузлование не содержит циклического включения номенклатуры или ревизии состава.

Результат:

- список найденных циклов;
- сообщение ошибки для блокирующего цикла;
- предупреждения для потенциальных повторных включений, если они допустимы.

## 12. Входимость

Операция показывает, где используется выбранная номенклатура, исполнение или ревизия состава.

Вход:

| Параметр | Описание |
|---|---|
| `Nomenclature` | Номенклатура, для которой строится входимость. |
| `NomenclatureVariant` | Исполнение номенклатуры, если задано. |
| `ManufacturingBill` | Ревизия состава, если входимость строится для конкретной спецификации. |
| `Direction` | `BottomUp` или `TopDown`. |
| `Date` | Дата применимости. |
| `UsageArea` | Область использования для отбора применимых ревизий. |
| `Context` | Контекст условий применимости. |

Алгоритм:

1. Найти позиции спецификаций, где выбранная номенклатура или ревизия указана как компонент.
2. Отобрать только применимые ревизии спецификаций по архивности, области использования, периоду действия и условиям применимости.
3. Исключить циклические включения и сформировать диагностическое сообщение для найденных циклов.
4. Для направления `BottomUp` построить дерево от компонента к изделиям, в которые он входит.
5. Для направления `TopDown` построить дерево от изделия к входящим компонентам.
6. Вернуть иерархический расчетный результат с уровнями, родительскими строками, источником-спецификацией и источником-позицией.

Операция не изменяет нормативные данные и не создает постоянный объект результата в модуле.

## 13. Подбор применимой замены

Операция используется при разузловании, расчете потребностей, подготовке производственных данных и последующей комплектации.

Вход:

| Параметр | Описание |
|---|---|
| `SubstitutableComponent` | Заменяемая НП. |
| `SubstitutableComponentVariant` | Исполнение заменяемой НП, если задано. |
| `Product` | Изделие / продукт контекста, если замена ограничена продуктом. |
| `ManufacturingBill` | Спецификация контекста, если замена ограничена составом. |
| `ProcessDefinition` | Технология контекста, если замена ограничена технологией. |
| `Date` | Дата применимости. |
| `RequiredQuantity` | Требуемое количество заменяемого компонента. |
| `RequiredUnit` | ЕИ требуемого количества, если она известна. |
| `Context` | Контекст условий применимости. |

Алгоритм:

1. Отобрать активные `NomenclatureSubstitution` по заменяемой НП и исполнению.
2. Применить ограничения по продукту, спецификации, технологии и периоду действия.
3. Проверить `UseCondition`.
4. Применить тип замены и признаки `IsMandatorySubstitution`, `IsReverseSubstitution`.
5. Для `SubstitutionType = Substitution` рассчитать количество заменяющего компонента по `SubstitutionFactor`.
6. Для `SubstitutionType = RateSubstitution` использовать `RateUnit`, `RateForSetup` и `RateForProcessing` как нормативные значения правила замены в выбранной `UnitOfOperation`.
7. Для результата применения замены рассчитать количества и нормы в базовой ЕИ через функции GMD.

Результат подбора не изменяет нормативное правило замены. Расчетные и операционные объекты фиксируют факт применения замены собственными полями: ссылка на `NomenclatureSubstitution`, замененная НП, замененное количество, ЕИ, коэффициент и причина/основание замены.
