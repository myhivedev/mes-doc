# Архитектурные принципы DMP

## 1. Назначение

Документ фиксирует общие архитектурные принципы DMP. Они применяются к верхней архитектуре, платформенным областям и прикладным модулям.

## 2. Принципы

| Принцип | Правило применения |
| --- | --- |
| Единая платформа | Общие механизмы реализуются один раз в Platform Core и используются прикладными модулями через контракты. |
| Конфигурируемость вместо кастомизации | Отличия предприятий, площадок и сценариев выражаются через configuration, settings, workflow, rules, value sets, views и permissions, если это не нарушает доменные инварианты. |
| Импортонезависимость | Технологические решения должны учитывать доступность и поддержку целевого стека без критической зависимости от недоступных лицензий. |
| Стандартизация | Общие процессы, stable codes, contracts, runtime conventions и документационные шаблоны должны быть едиными для всех областей. |
| Поэтапная цифровизация | Архитектура поддерживает ручной ввод, терминалы, интеграции с оборудованием и постепенное расширение автоматизации. |
| Явные границы владения | Каждый факт, каждый контракт, данные и runtime-поведение имеют владельца документации и реализации. |
| Слабая связанность | Взаимодействия между областями идут через HTTP API, application ports, integration events или extension points. |
| Проверяемость | Нормативный документ описывает подтверждённое поведение, принятое целевое решение или явно помеченный открытый вопрос. |

## 3. Конфигурируемость

Конфигурируемость не означает произвольную low-code модель без границ. Платформа должна разделять:

- schema и configuration artifacts;
- runtime execution;
- frontend representation;
- domain invariants;
- settings and user preferences;
- published/effective state.

Детальная граница этих механизмов принадлежит `03_platform`.

## 4. Интеграции

Интеграционная архитектура DMP строится на комбинации:

- REST/HTTP API для синхронных операций;
- application ports и gateways внутри host-композиции;
- integration events для публикации фактов изменения;
- external adapters для ERP, CAD/PDM, MDC и других систем.

Общая карта взаимодействий находится в [интеграционной архитектуре](07_integration_architecture.md).

## 5. Данные

Каждая область владеет своими данными. Прямой доступ к таблицам другой области не является публичным контрактом, даже если текущая host-композиция технически содержит общие persistence-зависимости.

Типы данных и правила владения описаны в [архитектуре данных](05_data_architecture.md).
