# Методика подготовки проектной документации модуля из MSWord/ПР

## 1. Назначение

Документ описывает методику совместной подготовки проектной документации прикладного модуля DMP из исходного MSWord или проектного решения.

Цель методики - получить не пересказ исходного документа, а целевой комплект проектной документации в структуре `docs-new`, согласованный с:

- стратегией документации;
- шаблоном документации прикладного модуля;
- `00 Common`, `01 General Master Data` и платформенной документацией;
- `DMP_DATA`;
- паттернами кода DMP;
- решениями, принятыми при обсуждении спорных вопросов.

Главный принцип:

```text
источник -> расхождение -> варианты -> решение человека -> документ -> вычитка -> трассировка
```

Документы модуля создаются только после первичного анализа источников и фиксации открытых вопросов.

## 2. Стартовый анализ

В начале работы нужно явно запретить немедленное создание полного комплекта документов.

Пример:

```text
Изучи проектное решение `<PR_DIR>/<PR_FILE>.docx` и обязательные источники:
- `<DMP_ROOT>/docs-new/00_governance/00_documentation_strategy.md`;
- `<DMP_ROOT>/docs-new/00_governance/requirements/001_dmp_functional_requirements_and_constraints.md`;
- `<DMP_ROOT>/docs-new/04_domain_modules/00_module_documentation_template.md`;
- `<DMP_ROOT>/docs-new/11_glossary`;
- `<DMP_ROOT>/docs-new/04_domain_modules/00_common`;
- уже спроектированные модули в `<DMP_ROOT>/docs-new/04_domain_modules`, если они влияют на текущий модуль;
- `<DMP_ROOT>/docs-new/03_platform`;
- структура данных `<DMP_DATA_DIR>`;
- исходный код DMP в `<DMP_ROOT>`.

Сначала не создавай документы.
Подготовь аналитический отчет:
- предметные области и объекты;
- объекты владения модуля;
- внешние ссылки;
- enum/SystemEnum/ValueSet;
- UI;
- правила, workflow, операции, права;
- зависимости от других ПР;
- спорные места и открытые вопросы;
- рекомендуемый порядок проектирования.
```

Проверка человеком:

- агент не начал писать документы сразу;
- объекты, поля, enum, вкладки и операции не придуманы сверх ПР, DMP_DATA или уже принятых решений;
- зависимости от соседних модулей названы явно;
- спорные места вынесены в вопросы, а не спрятаны в целевую модель.

## 3. Рабочий журнал решений

После первичного отчета создается рабочий журнал решений модуля.

Пример промпта:

```text
Создай в папке модуля `_working/decision_log.md` по образцу существующих рабочих журналов решений и зафиксируй открытые вопросы.
Документы модуля пока не создавай.
```

Проверка человеком:

- каждый вопрос имеет понятную формулировку;
- вопрос связан с конкретным источником или расхождением;
- в журнале нет решений, которые человек еще не подтвердил;
- рабочий журнал не подменяет целевую документацию.

Файлы в `_working` являются рабочими материалами модуля. Они могут храниться
в Git для совместной работы, но не являются документами `docs-new` и полностью
исключены из механизма версий, истории изменений и статусов PR. Для них не
требуются YAML-шапка, `id`, `type` или раздел «История изменений».

### 3.1 Рабочие реестры в журнале решений

Рабочие реестры по умолчанию ведутся разделами внутри `_working/decision_log.md`. Они нужны для анализа, сверки и принятия решений; целевые документы модуля должны содержать уже принятое решение, без черновых рассуждений.

Минимальный рабочий файл:

| Документ | Когда обязателен | Что фиксирует |
|---|---|---|
| `_working/decision_log.md` | Всегда | Открытые вопросы, варианты, рекомендации, решения человека, рабочие реестры сверки и ссылки на документы, куда решение перенесено. |

Типовые разделы-реестры внутри `decision_log.md`:

| Раздел | Когда нужен | Что фиксирует |
|---|---|---|
| Реестр объектов, коллекций и полей | Перед написанием или крупной переработкой `02_domain_model.md` | Тип, обязательность, Word ПР, `DMP_DATA`, текущая проектная документация, код или документация платформы, предложение, статус решения, целевой документ. |
| Реестр наследования и владения | Если есть базовые типы, наследники или спорное владение элементами коллекций | Сравнение наследования Word ПР / `DMP_DATA` / целевой модели, владелец элемента, причина отличий. |
| Реестр переименований | Если есть переименования полей, объектов или enum | Исходное имя, целевое имя, тип, причина переименования, где отличие отражено в трассировке. |
| Реестр enum/SystemEnum/ValueSet | Если есть enum, SystemEnum, ValueSet или спорный владелец списка | Значения из Word ПР / `DMP_DATA`, тип `SystemEnum` или `ValueSet`, модуль-владелец, целевой документ. |
| Реестр runtime-контрактов | Если решение зависит от Object Runtime, lookup, коллекций, workflow, settings, numbering, permissions или baseline | Проверенный платформенный механизм, ссылка на код или платформенный документ, ограничение, нужна ли backlog-задача. |
| Реестр UI / операций / прав | Если проектируются списки, карточки, действия, прикладные операции или роли | Источник, отличие от ПР, предложение, принятое решение, целевой документ. |

Любой элемент целевой документации, который не является прямым переносом из источника, должен иметь рабочую строку сверки: источник, расхождение, предложение, решение, целевой документ.

Отдельный файл в `_working` создается только для крупного реестра, который делает `decision_log.md` плохо читаемым. В `decision_log.md` при этом должна остаться ссылка на вынесенный реестр и краткий итог принятого решения. Рекомендуемые имена:

```text
_working/entity_attribute_register.md
_working/inheritance_register.md
_working/name_mapping.md
_working/enum_register.md
_working/runtime_contract_register.md
_working/ui_register.md
_working/operations_register.md
_working/permissions_register.md
```

Статусы строк реестра:

```text
Accepted / Rejected / Rename / External / Open / Needs code check
```

Правило переноса:

- принятое решение переносится в целевые документы (`01_scope.md`, `02_domain_model.md`, `03_object_runtime_model.md`, `05_rules.md` и т.д.);
- отличие от исходного ПР или `DMP_DATA` переносится в `90_traceability_prXX.md`;
- черновые варианты, промежуточные ошибки и неподтвержденные предложения остаются только в `_working`.

## 4. Обсуждение вопросов

Открытые вопросы обсуждаются по одному.

Рабочий промпт:

```text
Давай следующий открытый вопрос.
Сформулируй:
- вопрос;
- что говорит ПР;
- что говорит DMP_DATA;
- что принято в Common, GMD и платформенной документации;
- варианты решения;
- рекомендацию;
- что попадет в документацию после решения.
```

После ответа человек должен явно принять решение:

```text
согласен
```

или:

```text
вариант B
```

или:

```text
оставить вопрос открытым до проектирования <модуль/ПР>
```

Проверка человеком:

- агент не закрывает несколько спорных вопросов одним ответом;
- рекомендация отделена от принятого решения;
- зависимость от будущего модуля не превращается во владение текущего модуля;
- открытый вопрос не попадает в целевую модель как уже принятое решение.

## 5. Обязательные классы вопросов

При проектировании модуля нужно отдельно проверить:

- границу модуля и зависимость от соседних ПР;
- какие объекты принадлежат модулю;
- какие объекты являются внешними ссылками;
- абстрактные и наследуемые объекты;
- `Tenant`, `Site/Plant`, область данных и область прав;
- SystemEnum и ValueSet;
- параметры/settings и доменные объекты;
- жизненный цикл и архивирование;
- Object Runtime contracts, lookup, baseline;
- UI: списки, карточки, вкладки, меню;
- права и роли;
- специфические операции;
- платформенные backlog-задачи.

### 6.1 Единый стандарт доменной модели

`02_domain_model.md` является нормативным источником описания типов, полей,
ссылок и коллекций. Схемы в этом документе являются визуальным представлением
таблиц и не могут добавлять объекты или связи, отсутствующие в таблицах.

Для каждого модуля обязательны Mermaid-схемы:

- `classDiagram` «Типы и наследование»;
- одна или несколько схем «Внутренние связи и коллекции» (`erDiagram` предпочтительна; `classDiagram` допускается, если это требуется инструментом отображения).

Большая модель может быть разделена на несколько схем по предметным областям,
но для всех схем используются одинаковые обозначения:

| Обозначение | Смысл |
|---|---|
| `<|--` | Логическое наследование типа. |
| `-->` | Обычная ссылка на объект. |
| `o--` | Коллекция объекта-владельца; физическое хранение определяется таблицами владельца и элемента коллекции. |
| `..>` | Внешняя зависимость или обратная навигация без владения данными. |

Для `erDiagram` используются стандартные обозначения кардинальности Mermaid и
подписи с именами ссылочных полей и обратных коллекций. Схема внутренних связей
должна показывать обычные ссылки, самоссылки и коллекции, а не только коллекции.
Внешние ссылки не смешиваются с внутренней схемой: они фиксируются в таблице
границы с внешними объектами и при необходимости в отдельной компактной схеме.

В схемах не перечисляются поля. Поля описываются только в таблице объекта.
Для внешних типов используется пометка `<<external>>`. Для каждого типа в
тексте указывается его базовый тип, характер (`абстрактный` или
`самостоятельный`) и физическое хранение.

В содержательном тексте доменной модели используется термин «тип»: «базовый
тип», «абстрактный тип», «самостоятельный тип» и «тип-наследник». Термин
«класс» используется только для обозначения синтаксиса Mermaid (`classDiagram`,
`erDiagram`)
или как точное имя программного класса при ссылке на исходный код.

Подразделы внутри нумерованных разделов получают иерархические номера:
например, `4.1`, `4.2`, а вложенный блок - `7.1.1`. Название типа не заменяет
номер подраздела.

В схеме наследования внешний тип показывается только как контекст для типа
текущего модуля. Связи наследования между двумя внешними типами в документе
модуля не воспроизводятся: такая иерархия описывается в документе-владельце
внешних типов.

Наследник описывает только добавленные поля, ссылки и коллекции. Унаследованные
поля не повторяются; документ должен явно указать, что они получены от базового
типа и сохраняют его обязательность и правила.

Если тип ссылки зависит от конкретного наследника, запись `тот же тип` не
используется без расшифровки. В таблице поля указываются конкретные варианты
для самостоятельных наследников, например: `WorkPlaceGroup.Parent` ссылается
на `WorkPlaceGroup`, а `PersonnelGroup.Parent` - на `PersonnelGroup`. Такая
ссылка является свойством и runtime-контрактом наследника; `ParentId`, имя
внешнего ключа и другие детали SQL в доменной модели не указываются.

Схемы связей и коллекций в совокупности должны покрывать все сохраненные ссылки
и коллекции из таблиц объектов. Если модель разделена на несколько схем, каждая
ссылка или коллекция показывается ровно один раз. Самоссылки (`Parent`,
`Previous` и аналогичные) также включаются. Вычисляемые свойства и enum не
являются связями и на схемах не показываются.

Композиция `o--` уже показывает связь владельца с элементом коллекции. Ссылку
элемента на этого владельца второй стрелкой не дублируют. Для обратной
навигации к данным, которыми владеет другой модуль, допускаются две стрелки:
ссылка элемента на внешний объект и обратная навигация внешнего владельца.
Такая навигация не передает текущему модулю владение данными.

Коллекция описывается в разделе владельца таблицей с колонками:
`Коллекция`, `Тип элемента`, `Кратность`, `Владение`, `Связующее поле или
условие`, `Назначение`. Режим Object Runtime (`Состав владельца`, `Отдельные
операции`, `Навигация`) указывается только в `03_object_runtime_model.md`.

Если у типа нет собственных полей, пустую таблицу не оставляют: пишут
«Собственных предметных полей нет» и указывают, какие поля он получает от
базового типа. Блок общих полей базового типа размещается внутри его раздела,
до разделов наследников.

Блоки `text` с псевдосинтаксисом наследования, ссылок или коллекций для этой
цели не используются. Текстовые блоки допускаются только для алгоритмов,
примеров значений и пояснения правил, если они не заменяют нормативную таблицу
или Mermaid-схему.

### 6.2 Создание и подключение документов с версионностью

Единый полный промпт поддерживается в разделе «Канонический промпт для работы
через ИИ» файла `docs-new/00_governance/01_document_template.md`. Его нельзя
копировать в несколько стандартов: ИИ каждый раз должен прочитать актуальную
версию из рабочей ветки.

Пользователь передаёт своему ИИ короткий запускающий промпт:

```text
Оформи документ `<ПОЛНЫЙ ПУТЬ В DOCS-NEW>`.
Задача по содержанию: `<ЧТО СОЗДАТЬ ИЛИ ИЗМЕНИТЬ>`.

Сначала открой актуальный файл
docs-new/00_governance/01_document_template.md и полностью выполни раздел
«Канонический промпт для работы через ИИ». Используй правила и шаблоны только
из текущей ветки репозитория. Не коммить и не отправляй изменения без отдельной
команды пользователя.
```

Канонический промпт сам различает создание, первичное подключение и изменение
уже версионируемого документа. Новый документ создаётся со статусом
`draft` / `not_started`; дальнейшее состояние PR, версии и историю обновляет
workflow.

## 7. Контроль после каждого документа

Промпт для вычитки:

```text
Вычитай <документ>:
- нет ли воды;
- нет ли повторов из других документов;
- соответствует ли шаблону;
- нет ли полей/enum/UI/операций, которых нет в ПР, DMP_DATA или решениях;
- нет ли противоречий с `00_common`, `01_general_master_data` и платформенной документацией.
Пока ничего не меняй, сначала перечисли найденные проблемы.
```

Если проблемы понятны:

```text
Исправь только перечисленные проблемы. Бизнес-смысл не меняй.
```

Проверка человеком:

- каждое исправление действительно относится к найденной проблеме;
- спорные решения не меняются молча;
- документ не начинает дублировать соседние документы.

## 8. Контроль SystemEnum и ValueSet

Отдельный промпт:

```text
Пройди по всем полям с типами enum/ValueSet.
Для каждого поля укажи:
- где оно описано в ПР;
- есть ли значения в ПР/DMP_DATA;
- SystemEnum или ValueSet;
- модуль-владелец;
- где должно быть описано.
Не меняй документы, сначала дай таблицу.
```

Проверка человеком:

- фиксированные таблицы значений из ПР обычно оформляются как `SystemEnum`;
- `ValueSet` используется только для настраиваемых наборов значений;
- enum внешнего модуля не объявляется владением текущего модуля без решения;
- в `10_value_set_data_usage.md` не дублируются SystemEnum из `02_domain_model.md`.

## 9. Контроль границ модулей

Промпт:

```text
Найди все объекты/поля, которые могут принадлежать соседним модулям.
Для каждого укажи:
- почему это кандидат на внешний объект;
- что говорит ПР;
- что говорит DMP_DATA;
- что уже принято в документах;
- оставить в модуле или вынести.
```

Проверка человеком:

- будущий объект не включается во владение текущего модуля только потому, что он показан на вкладке;
- ссылка на внешний объект остается ссылкой;
- настройки платформы не превращаются в доменный объект без решения;
- зависимость от будущего модуля отражается в traceability.

## 9.1 Стандарт межмодульных ссылок и навигации

Внешняя ссылка не означает владение целевым объектом. Владелец данных
определяется границей модуля, а не тем, в карточке какого объекта ссылка
показывается.

Квалифицированное имя типа в межмодульном контракте записывается в формате
`ModuleCode:ObjectTypeCode`. `ModuleCode` берется из регистрации модуля и не
заменяется именем каталога `docs-new`.

Для каждой внешней ссылки в рабочем реестре и целевых документах фиксируются:

| Элемент | Что указывать |
|---|---|
| Локальное поле | Поле, кратность и назначение ссылки. |
| Целевой тип | Квалифицированное имя `ModuleCode:ObjectTypeCode`. |
| Владелец данных | Модуль, который создает, изменяет и удаляет целевые записи. |
| Источник выбора | Lookup, API или иной согласованный источник значений. |
| Ограничение выбора | Tenant, состояние, тип, иерархия, принадлежность и другие условия. |
| Проверка | Модуль или платформа, проверяющие существование, доступность и совместимость. |
| Изменение цели | Разрешено ли текущему модулю изменять целевую запись. |
| Обратная навигация | Есть ли коллекция связанных объектов и в каком режиме она работает. |

Если ссылка образует обратную навигацию, коллекция может быть описана в модели
модуля-потребителя в режиме `Навигация`. Такая коллекция не создает владение,
физическое поле или таблицу в модуле-потребителе. Ее тип, владелец данных,
условие отбора и доступные операции должны быть указаны явно.

## 10. Контроль UI и меню

Промпт для UI:

```text

- какие поля;
- какие действия;

Сначала отчет, без правок.
```

Промпт для меню:

```text
Изучи ПР00/источник меню.
Сопоставь пункты меню с `06_ui_views.md`.
Сформируй `15_navigation_menu.md` по целевой структуре меню.
Укажи только целевые группы и конечные пункты модуля, их связь с `ViewCode`,
режим открытия, правила публикации и связь с правами.
Источник укажи краткой ссылкой или полным путем, но не копируй исходную
структуру меню в документ.
Не включай в документ пересказ доменной модели, Object Runtime, полей UI,
бизнес-правил, операций или список всех представлений, которые не являются
пунктами главного меню.
```

Проверка человеком:

- карточки, lookup, вкладки и строки коллекций не становятся пунктами главного меню без явного решения;
- каждый конечный пункт меню связан с представлением из `06_ui_views.md`;
- если исходный ПР задает несколько форм в одном пункте, это явно описывается;
- структура исходного меню не скопирована в целевой документ;
- стандартные действия Object Runtime не превращаются в прикладные операции без предметного алгоритма.

```text

- baseline;

- workflow;
- permissions;
- settings;
```

Проверка человеком:

- backlog-задача не подменяет целевую модель модуля;
- если у объекта нет `SiteId`, права и фильтрация не должны молча становиться site-scoped;
- технический термин платформы не смешивается с предметным объектом модуля.

## 12. Финальная вычитка пакета

Промпт:

```text
Вычитай весь пакет документации модуля:
- соответствие шаблону;
- нормальный русский язык;
- отсутствие воды;
- отсутствие противоречий;

- список реально открытых вопросов;
- список платформенных зависимостей.
Не исправляй спорные места без подтверждения.
```

После отчета:

```text
Исправь только технические несогласованности и формулировки, которые не меняют решения.
```

Проверка человеком:

- открытые вопросы действительно открытые, а не уже принятые решения;
- платформенные зависимости не записаны как незакрытые предметные вопросы;
- документы не противоречат друг другу;
- язык целевых документов не содержит пояснений о том, как писать документацию.

## 13. Diff, commit и push

Перед коммитом:

```text
Посмотри diff только по папке модуля.
Отдельно проверь, есть ли связанные изменения в `plans`, `docs-new/03_platform`, `00_common`, `src`.
Напиши короткий комментарий для коммита только по модулю.
```

Коммит:

```text
Закоммить и запуш только изменения по <папка модуля> с сообщением:
<сообщение>
```

Проверка человеком:

- в staged попали только файлы нужного модуля и подтвержденные связанные изменения;
- untracked соседние папки не попали в коммит случайно;
- `git diff --check` не показывает ошибок;
- commit message отражает модуль и суть изменений.

## 14. Типовые ошибки

Нельзя:

- писать полный комплект документов до анализа источников;
- придумывать поля, enum, UI-вкладки и операции;
- смешивать SystemEnum и ValueSet;
- переносить объекты будущих модулей во владение текущего модуля;
- дублировать одно решение в нескольких документах;
- писать правила документации внутри проектных документов модуля;
- описывать стандартные create/update/delete/read как прикладные операции без предметной политики модуля;
- делать права site-scoped, если у объектов нет `SiteId` или явного правила сопоставления с `Site`;
- переносить предметную модель тестового модуля в новый модуль.

Нужно:

- фиксировать источники и расхождения;
- обсуждать спорные решения по одному;
- держать границы документов;
- использовать уже принятую терминологию;
- отделять целевое решение модуля от платформенных backlog-задач;
- после каждого изменения сверять документы между собой.
