# GMD v1 — план ручного тестирования

## 1. Назначение и область

План закрывает отложенную ручную приемку `GMD-02`, `GMD-05` — `GMD-18`,
`GMD-21` и `GMD-22` из `20_implementation_backlog.md`. Проверка выполняется
через целевой Runtime Web UI production-host, а не через Swagger, прямые SQL
изменения или demo-host.

В текущий прогон не входят отложенные зависимости `GMD-20`:

- Platform Numbering;
- машиночитаемая идентификация;
- Integration Foundation и конкретные adapters внешних ссылок;
- миграция данных из demo Product Definition;
- полная нагрузочная и кросс-браузерная приемка.

Открытые platform backlog `GMD-23` — `GMD-25` проверяются отдельно и не должны
блокировать функциональную приемку GMD, если дефект не воспроизводится в
production-контуре GMD.

## 2. Основания

- `20_implementation_backlog.md` — состав и критерии готовности задач GMD;
- `05_rules.md` — доменные инварианты;
- `06_ui_views.md` — списки, карточки, lookup и коллекции;
- `04_workflows.md` — жизненный цикл публикуемых объектов;
- `11_permissions.md` — роли и матрица доступа;
- `13_operations.md` — пересчеты и эффективная схема;
- `15_navigation_menu.md` — структура общего меню приложения;
- `91_implementation_acceptance.md` — границы технической приемки.

## 3. Виды прогона

| Прогон | Назначение | Состав |
|---|---|---|
| Smoke | Проверка пригодности сборки к расширенной приемке | `GMD-M-01` — `GMD-M-08` |
| Основной | CRUD, UI, ссылки, tenant scope, workflow и права | Все сценарии с приоритетом `P0` и `P1` |
| Расширенный | Сложные коллекции, пересчеты, реквизиты, audit и негативные границы | Сценарии `P2` |

Smoke должен быть завершен без блокирующих дефектов до начала основного
прогона.

## 4. Тестовый контур и предусловия

1. Развернут production-host с Runtime Web UI и актуальными миграциями.
2. Созданы два предприятия: `TENANT-A` и `TENANT-B`.
3. Выполнен bootstrap и опубликован system baseline.
4. В DMP.Admin после bootstrap доступны шаблоны ролей GMD. Это коды ролей,
   а не логины автоматически создаваемых пользователей:
   - `GeneralMasterDataAdmin` — Администратор общей НСИ;
   - `GeneralMasterDataUser` — Пользователь общей НСИ;
   - `GeneralMasterDataMethodologist` — Методолог общей НСИ;
   - `GeneralMasterDataNomenclatureResponsible` — Ответственный за номенклатуру;
   - `GeneralMasterDataContractorResponsible` — Ответственный за контрагентов.
5. В каждом предприятии созданы отдельные тестовые пользователи и через
   DMP.Admin им назначены перечисленные роли в tenant scope. Рекомендуемые
   логины для `TENANT-A`: `gmd.admin.a`, `gmd.user.a`, `gmd.methodologist.a`,
   `gmd.nomenclature.a`, `gmd.contractor.a`; для `TENANT-B` достаточно
   `gmd.admin.b` и `gmd.user.b`.
6. Назначение выполняет tenant/security administrator. В development-контуре
   для этого можно использовать seeded-пользователей `alpha.admin` или
   `alpha.security` для `tenant-alpha`, а также `beta.admin` или
   `beta.security` для `tenant-beta`. Эти учетные записи сами по себе не
   заменяют пользователей предметных ролей GMD.
7. Язык интерфейса можно переключать между `ru-RU` и `en-US`.
8. До прогона зафиксированы версия сборки, commit, URL, СУБД, браузер и дата
   bootstrap.

Если названия ролей или их коды в развернутом контуре отличаются от документа,
это фиксируется как расхождение конфигурации до выполнения security-сценариев.

## 5. Базовые тестовые данные

Для каждого прогона использовать уникальный префикс, например `MT-260817`.

| Объект | TENANT-A | TENANT-B |
|---|---|---|
| Единицы | `PCS` (шт., precision 0), `KG` (кг, precision 3), `BOX` | `PCS-B` |
| Группы ЕИ | `COUNT` с базовой `PCS`, `WEIGHT` с базовой `KG` | `COUNT-B` |
| Группы НП | `MATERIALS`, дочерняя `FASTENERS` | `MATERIALS-B` |
| Контрагенты | `MFG-A` с категорией Manufacturer, `SUP-A` с категорией Supplier | `MFG-B` |
| Группы контрагентов | `SUPPLIERS-A` | `SUPPLIERS-B` |
| Наборы упаковок | `STD-PACK` с базовой `PCS` | — |
| Типы транспортных единиц | `PALLET` | — |
| Виды НП | `PART` | — |
| НП | `BOLT-M8`, базовая ЕИ `PCS` | `BOLT-B` |
| Реквизиты | `COLOR` (`LocalEnum`), `GRADE` (`ValueSet` при наличии данных) | — |

Тестовые записи не переиспользовать между негативными сценариями, если
предыдущая попытка могла частично изменить состояние.

## 6. Общие правила фиксации результата

Для каждого сценария фиксируются:

- статус: `Passed`, `Failed`, `Blocked`, `Not run`;
- фактический результат и шаг ошибки;
- пользователь, роль и предприятие;
- идентификаторы созданных объектов;
- screenshot UI и request/correlation id для дефекта;
- ожидаемый и фактический стабильный код ошибки, если UI его показывает;
- ссылка на defect и решение о повторном прогоне.

Ошибки классифицируются так:

| Severity | Критерий |
|---|---|
| Blocker | Нельзя войти, выполнить bootstrap, открыть общее меню или сохранить любой объект GMD. |
| Critical | Нарушена tenant-изоляция, права, целостность ссылок или данных; потеря/повреждение данных. |
| Major | Не работает обязательный CRUD, workflow, коллекция или предметное правило. |
| Minor | Локализация, порядок, подпись, необязательная колонка или некритичное UX-расхождение. |

## 7. Smoke-прогон

### GMD-M-01. Загрузка production-модуля и bootstrap (`GMD-02`, `GMD-04`)

Приоритет: `P0`.

1. Запустить production-host на пустой поддерживаемой БД.
2. Выполнить bootstrap.
3. Войти тестовым пользователем, которому назначена роль
   `GeneralMasterDataAdmin`, например `gmd.admin.a`.

Ожидается: host стартует без demo-модуля; bootstrap завершается успешно; GMD
доступен без ручного наполнения системных таблиц; в ValueSetData присутствуют
`Supervisor` и `ContactPerson` с локализованными названиями.

### GMD-M-02. Общее меню GMD (`GMD-02`, `GMD-17`)

Приоритет: `P0`.

1. Открыть главное меню Runtime Web.
2. Найти группу `Общая НСИ` в общем меню `RuntimeWeb_MainMenu`.
3. Проверить порядок и переходы: Группы ЕИ, Единицы измерения, Номенклатура,
   Группы номенклатуры, Виды номенклатуры, Реквизиты номенклатуры, Серийные
   номера, Группы контрагентов, Контрагенты.
4. Убедиться, что lookup, detail views и коллекции не имеют отдельных пунктов.
5. Убедиться, что PackSet, Pack и TransportUnitType не опубликованы в группе
   `Общая НСИ`.

Ожидается: структура, коды, русские названия и порядок соответствуют
`15_navigation_menu.md`; каждый конечный пункт открывает требуемый список.

### GMD-M-03. Минимальный CRUD Unit (`GMD-05`, `GMD-17`)

Приоритет: `P0`.

Создать `PCS`, открыть карточку, изменить Name, найти запись поиском, проверить
сортировку, архивировать и включить отображение архивных.

Ожидается: create/view/edit/search/archive выполняются штатными действиями
Object Runtime; обязательные поля и системная секция соответствуют
`06_ui_views.md`; архивная запись по умолчанию скрыта.

### GMD-M-04. Минимальный CRUD основных справочников (`GMD-05` — `GMD-08`)

Приоритет: `P0`.

Повторить create/view/edit/search для UnitGroup, NomenclatureGroup, Contractor,
ContractorGroup, PackSet и TransportUnitType.

Ожидается: списки и карточки открываются без необработанных ошибок; ссылки
выбираются через lookup; presentation ссылок отображается человекочитаемо.

### GMD-M-05. Создание Nomenclature (`GMD-09`, `GMD-11`)

Приоритет: `P0`.

Создать `BOLT-M8` с Unit=`PCS`, ApplicationArea и NomenclatureType, затем снова
открыть карточку.

Ожидается: НП сохранена; значения enum отображаются локализованно; автоматически
создана базовая UnitOfOperation с ToUnit=`PCS`, factor=1, IsDefault=true и
пустой ApplicationArea.

### GMD-M-06. Коллекция карточки (`GMD-12`, `GMD-16`)

Приоритет: `P0`.

В карточке `BOLT-M8` добавить исполнение и индивидуальную упаковку, сохранить,
обновить страницу, изменить и удалить строки.

Ожидается: строки сохраняются у правильного владельца, не теряются после reload,
действия строки доступны из карточки и не позволяют сменить владельца/tenant.

### GMD-M-07. Workflow (`GMD-15`)

Приоритет: `P0`.

Для Nomenclature выполнить допустимую последовательность публикации и открыть
историю lifecycle.

Ожидается: начальное состояние, доступные команды и итоговое состояние
соответствуют `04_workflows.md`; история содержит пользователя, время и переход;
недопустимая команда отсутствует или отклоняется.

### GMD-M-08. Read-only роль (`GMD-18`)

Приоритет: `P0`.

Войти тестовым пользователем с ролью `GeneralMasterDataUser`, например
`gmd.user.a`, открыть меню, список и карточку Unit и Nomenclature.

Ожидается: просмотр и lookup доступны; create/edit/delete и lifecycle transition
не показываются либо надежно отклоняются сервером.

## 8. Основной функциональный прогон

### GMD-F-01. Unit и UnitGroup (`GMD-05`, `GMD-10`)

Приоритет: `P1`.

- проверить обязательность Acronym и BaseUnit;
- проверить Precision на границах 0 и 8, отклонение -1 и 9;
- добавить пересчет в UnitGroup и проверить factor > 0;
- проверить запрет смены BaseUnit при активных пересчетах;
- проверить неделимую ЕИ с дробным количеством, если операция доступна UI.

Ожидается: валидные границы сохраняются, нарушения отклоняются без частичной
записи и с понятной диагностикой.

### GMD-F-02. Иерархия групп номенклатуры (`GMD-07`)

Приоритет: `P1`.

Создать `MATERIALS -> FASTENERS`; проверить фильтр/иерархию; попытаться назначить
группу родителем самой себе и создать цикл; попытаться архивировать родителя с
активной дочерней группой и с активной НП.

Ожидается: корректная иерархия отображается, self-parent/cycle и недопустимое
архивирование отклоняются.

### GMD-F-03. Контрагенты, категории, группы и контакты (`GMD-06`)

Приоритет: `P1`.

- создать Manufacturer и Supplier, включая несколько category flags;
- проверить условную видимость секции ТОиР;
- добавить контакт типов Supervisor и ContactPerson;
- отклонить второй активный контакт того же Contractor+ContactType;
- включить контрагента в группу и отклонить повторное включение;
- проверить запрет нового включения в архивную группу.

### GMD-F-04. Nomenclature: ссылки и defaults (`GMD-09`)

Приоритет: `P1`.

- проверить обязательность Unit, ApplicationArea и NomenclatureType;
- для ComponentPart/AssemblyUnit/RoughPart не задавать ObtainMethod и ProcessType;
- проверить автоматическое значение Production;
- назначить BaseManufacturer без флага Manufacturer и затем с ним;
- назначить PackSet с несовпадающей и совпадающей BaseUnit;
- проверить согласованность срока годности и политики контроля.

### GMD-F-05. Смена базовой ЕИ НП (`GMD-11`)

Приоритет: `P1`.

В разрешенном состоянии сменить Unit НП и проверить синхронизацию базовой
UnitOfOperation. Повторить при несовместимом PackSet/дополнительном пересчете и
в состоянии, запрещающем изменение.

Ожидается: успешная смена атомарно обновляет базовую запись; конфликтующие
зависимости или lifecycle state блокируют всю операцию.

### GMD-F-06. Матрица UnitOfOperation (`GMD-10`)

Приоритет: `P1`.

Проверить допустимые owner/target пары для UnitGroup, Nomenclature, Pack и
TransportUnitType. Для каждой записи проверить factor, precision, tenant и
application-area. Создать две default-записи с пересекающимися flags и две
альтернативные цепочки к базовой ЕИ.

Ожидается: допустимые пары и однозначный пересчет работают; запрещенная пара,
пересечение defaults и неоднозначная цепочка возвращают предметную ошибку без
выбора произвольного пути.

### GMD-F-07. Исполнения и серийные номера (`GMD-12`)

Приоритет: `P1`.

- создать исполнения, отклонить второй active IsBasic для одной НП;
- создать SerialNumber с обязательными AssemblyKitYear и OrdinalNumber;
- отклонить повтор SerialNumber в той же НП;
- разрешить такой же номер в другой НП;
- отклонить Variant другой НП и Manufacturer без нужной категории.

### GMD-F-08. Схема реквизитов (`GMD-13`)

Приоритет: `P1`.

- создать строковый, числовой, LocalEnum и ValueSet-реквизиты;
- проверить обязательные AttributeCode, DataType, AssignmentArea;
- проверить Length/Precision и зависимость ValueSetCode от AllowedValuesSource;
- создать LocalEnum values и отклонить повтор Number;
- создать общее назначение, назначение вида и прямое назначение НП;
- отклонить одновременно заполненные Kind и Nomenclature;
- проверить запрет смены DataType/source/assignment area после использования.

### GMD-F-09. Эффективные реквизиты и typed values (`GMD-14`)

Приоритет: `P1`.

Для НП с видом проверить объединение общих, видовых и прямых назначений,
порядок OrdinalNumber, required и default values. Сохранить значения String,
Number, Boolean, DateTime, LocalEnum и ValueSet; выполнить те же базовые проверки
для Variant и SerialNumber.

Ожидается: показываются только применимые реквизиты; заполнена ровно одна typed
колонка; тип, source и уникальность owner+parameter валидируются; default
подставляется при подготовке карточки, но не становится отдельным признаком
строки.

### GMD-F-10. Lifecycle трех объектов (`GMD-15`)

Приоритет: `P1`.

Для Nomenclature, NomenclatureKind и NomenclatureParameter проверить начальное
состояние, все допустимые переходы, guards, возврат/архивирование согласно
`04_workflows.md`, историю и синхронизацию Common archive state.

### GMD-F-11. Списки, поиск, фильтры и lookup (`GMD-16`, `GMD-17`)

Приоритет: `P1`.

Для каждого самостоятельного объекта из `11_permissions.md` проверить:

- заявленные default columns и сортировку;
- query по полям из `06_ui_views.md`;
- быстрые/панельные фильтры и Show archived;
- открытие detail из списка;
- lookup из ссылочного поля, поиск и выбор;
- отсутствие cross-tenant и недопустимых archived candidates.

### GMD-F-12. Матрица ролей (`GMD-18`)

Приоритет: `P1`.

Для пяти ролей выполнить по одному разрешенному и одному запрещенному действию
в каждой предметной области: методология, номенклатура, контрагенты. Проверить
отдельные lifecycle permissions и отсутствие delete/archive в рабочих ролях по
умолчанию.

Ожидается: видимость меню, lookup, кнопок и серверная авторизация согласованы с
матрицей `11_permissions.md`; прямой URL или повтор HTTP-запроса не обходит запрет.

### GMD-F-13. Tenant isolation (`GMD-03`, `GMD-18`)

Приоритет: `P0`.

Из TENANT-A попытаться найти и выбрать записи TENANT-B через список, lookup,
ручную подстановку id/повтор запроса и mutation. Проверить смену tenant в
открытой сессии.

Ожидается: данные другого tenant не раскрываются; cross-tenant reference и
mutation отклоняются до записи; дочерние строки наследуют tenant владельца.

## 9. Расширенный и эксплуатационный прогон

### GMD-X-01. Archive, restore и delete dependencies (`GMD-05` — `GMD-16`)

Приоритет: `P2`.

Для каждого самостоятельного объекта проверить archive/restore и отображение в
lookup. Для NomenclatureParameter, enum value и assignment проверить запрет
удаления при зависимых значениях. Для Nomenclature проверить обработку owned
UnitOfOperation. Убедиться, что ошибка не оставляет частично удаленные строки.

### GMD-X-02. Concurrency (`GMD-16`, `GMD-21`)

Приоритет: `P2`.

Открыть одну карточку в двух сессиях, сохранить разные изменения последовательно.

Ожидается: второе устаревшее сохранение не перетирает первое молча; пользователь
получает понятное сообщение и может перечитать актуальные данные.

### GMD-X-03. Audit и lifecycle history (`GMD-15`, `GMD-21`)

Приоритет: `P2`.

Для create/update/archive/restore/delete, изменения коллекции, lifecycle
transition и системной синхронизации базовой ЕИ проверить доступную историю.

Ожидается: зафиксированы actor, tenant, объект, операция, время и изменения;
системная операция отличима от пользовательской; sensitive/internal значения не
попадают в пользовательскую диагностику.

### GMD-X-04. Локализация (`GMD-04`, `GMD-17`, `GMD-21`)

Приоритет: `P2`.

Повторить меню, один список, карточку, lookup, enum/ValueSet и validation error
в `ru-RU` и `en-US`.

Ожидается: title, labels, actions, options и сообщения локализованы; stable codes
не показываются вместо текста при наличии перевода; данные не меняются при
смене языка.

### GMD-X-05. Диагностика внешней ссылки (`GMD-03`, `GMD-20`, `GMD-21`)

Приоритет: `P2`.

Если adapter модуля-владельца не установлен, попытаться сохранить новую внешнюю
ссылку. Если adapter доступен, проверить missing, archived и cross-tenant target.

Ожидается: без adapter новая ссылка отклоняется стабильной диагностикой, а не
принимается как непроверенная; сохраненная историческая ссылка отображается по
зафиксированной fallback policy.

### GMD-X-06. Повторное открытие и устойчивость состояния (`GMD-16`, `GMD-17`)

Приоритет: `P2`.

После сложного сохранения обновить страницу, выйти/войти и открыть объект из
списка и прямой ссылки. Повторить после validation error и Cancel.

Ожидается: сохраненное состояние полностью восстанавливается; несохраненные или
отклоненные изменения не появляются в БД; UI не остается в ложном busy/saved
состоянии.

## 10. Критерии завершения приемки

Ручная приемка GMD v1 считается завершенной, если:

1. Все `P0` и `P1` сценарии выполнены.
2. Нет открытых Blocker/Critical дефектов.
3. Major-дефекты либо исправлены и перепроверены, либо явно приняты владельцем
   продукта с ограничением и сроком устранения.
4. Tenant isolation и серверная авторизация подтверждены негативными проверками.
5. CRUD, workflow и коллекции проверены через Runtime Web.
6. Структура меню подтверждена по `15_navigation_menu.md`.
7. Для отложенных сценариев указана причина `Blocked` и platform dependency.
8. Итог внесен в раздел результатов ниже и в `91_implementation_acceptance.md`;
   открытые пункты `GMD-17`/`GMD-22` обновлены только после фактического прогона.
