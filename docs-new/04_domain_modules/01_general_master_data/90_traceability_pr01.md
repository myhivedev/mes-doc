# Трассировка требований ПР01 - 01 General Master Data

## 1. Назначение документа

Документ является реестром требований, принятых решений и оставшихся открытых вопросов по ПР01 для модуля `01 General Master Data`.

Состояние реализации и автоматизированной проверки фиксируется в `20_implementation_backlog.md`. Основные точки реализации: object contracts и validators в `src/Modules/DMP.Modules.GeneralMasterData/Objects`, прикладные алгоритмы `UnitOfOperationService` и `NomenclatureParameterSchemaService`, единая persistence-модель `GeneralMasterDataDbContext`, а также GMD-наборы тестов в `tests/DMP.Platform.ArchTests` и `tests/DMP.Platform.IntegrationTests`.

Platform Numbering, машиночитаемая идентификация и Integration Foundation остаются отложенными внешними зависимостями. Их отсутствие не переносит правила, счетчики, идентификаторы или mappings в модель владения GMD.

Трассировка фиксирует, как требования ПР01, DMP_DATA, решения `00 Common` и модульная архитектура DMP отражаются в проектной документации GMD. В документ попадают только элементы, которые влияют на текущие документы модуля или требуют отдельного решения:

- модель объектов;
- правила и ограничения;
- жизненный цикл;
- API, прикладные операции и функции;
- представления интерфейса и Object Runtime;
- явно зафиксированные границы модуля.

## 2. Источники

Основные источники:

- `DMP ПР01 Общая НСИ.docx`;
- модель данных `DMP_DATA`;
- `docs-new/04_domain_modules/00_common`;
- `docs/00_documentation_strategy.md`, раздел `7.5 04_domain_modules/`.

`DMP.Modules.ProductDefinition` не используется как источник предметной модели для `01 General Master Data`.

## 3. Базовое проектное решение

Модуль `01 General Master Data` строится поверх проектных решений `00 Common`.

Это означает:

- справочники модуля наследуются от `CommonCatalogObject`, если у объекта есть `Code` и `Name`;
- объекты без универсального кода/наименования наследуются от `CommonObject`;
- `Status` из ПР01 не переносится как обязательное поле базового типа;
- `Presentation` не считается обязательным физическим полем, если может вычисляться через Object Runtime;
- `ExternalId` используется как поле совместимости с внешними источниками, но не заменяет полноценное сопоставление внешних систем;
- `TenantId` не входит в `CommonObject`, но объекты владения GMD должны явно объявлять область предприятия;
- архивирование и мягкое удаление описываются через Common-поля и возможности объекта.

## 6. Ключевые решения по модели

| Требование ПР01 | Решение для DMP | Почему | Где фиксируется |
| --- | --- | --- | --- |
| У НП есть одна ЕИ | `Nomenclature.Unit` является базовой основной единицей измерения НП. Все документы и остатки должны приводиться к ней. | Это стабильная основа для логистики, учета запасов и производства. | `02_domain_model.md`, `05_rules.md` |
| Системные enum из ПР01 | Enum, для которых ПР01 задает фиксированную таблицу значений, переносятся в `02_domain_model.md` как системные перечисления GMD. Поля объектов ссылаются на конкретный enum-тип, а не на `ValueSetCode`. | `ValueSetCode` используется для настраиваемых наборов значений. Фиксированные enum ПР01 являются частью доменного контракта и должны быть видны в проектной модели. | `02_domain_model.md`, `06_ui_views.md` |
| `WarehouseBinControlType`, `TransportUnitControlType`, `ObtainMethod`, `ProcessType` | `WarehouseBinControlType` и `TransportUnitControlType` используют enum `InventoryLocationControlType`. `ObtainMethod` использует enum `NomenclatureObtainMethod`. `ProcessType` использует enum `ProcessType`. | ПР01 задает эти поля как enum, а не как настраиваемые классификаторы. Значения `NomenclatureObtainMethod` и `ProcessType` уточнены по ПР02, где эти enum используются для спецификаций, технологий, схем кооперации и расчета состава. | `02_domain_model.md`, `05_rules.md`, `06_ui_views.md` |
| Области применения и присвоения | `Nomenclature.ApplicationArea` использует флаговый enum `ApplicationArea`: производство, ТОиР. `UnitOfOperation.ApplicationArea` использует отдельный флаговый enum `UnitApplicationAreaFlags`: производство, закупки, сбыт. `NomenclatureParameter.AssignmentArea` использует не флаговый enum `NomenclatureParameterAssignmentArea`: все НП, виды номенклатуры, номенклатура. У `NomenclatureParameter` нет поля `ApplicationArea`. | В ПР01 эти поля имеют разные смыслы. Их нельзя объединять в один enum или переносить `ApplicationArea` на реквизит НП. | `02_domain_model.md`, `05_rules.md`, `06_ui_views.md` |
| Область применения единицы операции | `UnitOfOperation.ApplicationArea` задается флаговым перечислением `UnitApplicationAreaFlags` из ПР01: `Production = 1`, `Purchase = 2`, `Sale = 4`. Если значение не заполнено, единица операции применяется во всех областях. | Для единицы операции нужно хранить одну или несколько областей применения и проверять пересечения областей для `IsDefault`. Пустое значение используется как краткая форма "все области". | `02_domain_model.md`, `05_rules.md`, `06_ui_views.md`, `13_operations.md` |
| Дополнительные ЕИ задаются для группы ЕИ, НП или партии | Использовать `UnitOfOperation` как ссылочный объект операции. `UnitGroup`, `Nomenclature`, `Lot` являются владельцами пересчета. | Документы смогут ссылаться на одну сущность, не дублируя коэффициенты. | `02_domain_model.md`, `05_rules.md` |
| Для НП при создании/смене базовой ЕИ создается `UnitOfOperation` с коэффициентом 1 | Оставить явную базовую запись `UnitOfOperation` для НП: `Nomenclature = текущая НП`, `ToUnit = Nomenclature.Unit`, `ConversionFactor = 1`, `ApplicationArea` не заполнено, `IsDefault = true`. При смене базовой ЕИ эта запись изменяется вместе с НП. | Это правило прямо задано в ПР01 и упрощает ссылки из заказов, документов и спецификаций на единый тип "единица операции". Пустое `ApplicationArea` означает применение во всех областях. | `05_rules.md`, `03_object_runtime_model.md`, `13_operations.md` |
| Изменение базовой ЕИ опубликованной НП | Ограничения изменения `Nomenclature.Unit`, базовой `UnitOfOperation`, дополнительных ЕИ и упаковок задаются жизненным циклом НП. В `05_rules.md` остаются только правила согласованности данных при разрешенном изменении. | ПР01 требует синхронизировать базовую `UnitOfOperation` при изменении `Nomenclature.Unit`, но не задает пересчет старых документов или операций. | `04_workflows.md`, `05_rules.md` |
| `UnitOfOperation.IsDefault` и множественная `ApplicationArea` | `IsDefault` действует в разрезе областей применения. Для одного владельца пересчета и каждой отдельной области применения допускается не более одной активной `UnitOfOperation` с `IsDefault = true`. Пересечение флагов `ApplicationArea` у записей по умолчанию запрещено; пустое `ApplicationArea` пересекается с любой областью. | ПР01 задает базовую запись НП для всех применимых областей и `IsDefault = true`, но также позволяет выбирать несколько областей применения для единицы операции. Без проверки пересечений система сможет получить несколько ЕИ по умолчанию для одной операции. | `05_rules.md`, `03_object_runtime_model.md` |
| `UnitOfOperation.Nomenclature` и `UnitOfOperation.ToNomenclature` присутствуют в одной таблице | Разделить смысл: `Nomenclature` - владелец пересчета для конкретной НП; `ToNomenclature` - цель только для сценария `TransportUnitType`. | Иначе модель смешивает "для какой НП задана доп. ЕИ" и "какую НП вмещает транспортная тара". | `02_domain_model.md`, `05_rules.md` |
| Упаковка пересчитывается в ЕИ или другую упаковку | `Pack` остается самостоятельным объектом; пересчет описывается через `UnitOfOperation`: `Pack -> Unit` или `Pack -> Pack`. | Упаковка имеет собственную карточку и логистический смысл. Машиночитаемая идентификация упаковки подключается через общий механизм REQ-00-B-019..022. | `02_domain_model.md`, `05_rules.md`, `03_object_runtime_model.md` |
| `Pack` бывает общей и индивидуальной | Не вводить `Pack.Type` без необходимости; тип выводить из XOR-ссылки: либо `PackSet`, либо `Nomenclature`. | В DMP_DATA отдельного поля `Type` нет, а инвариант выражается связями. | `02_domain_model.md`, `05_rules.md` |
| Для упаковки могут быть заданы вес брутто, габариты, объем, возвратность | Не включать эти поля в базовую модель `Pack` v1. Зафиксировать как будущую логистическую проработку по ПР09. | В DMP_DATA этих полей нет, а ПР01 отсылает упаковки к ПР09. Добавлять их без анализа логистики нельзя. | `01_scope.md`, `02_domain_model.md` |
| Граница `PackSet`/`Pack` с логистикой | `PackSet` и `Pack` входят в GMD v1 как справочная модель допустимых упаковок НП и правил пересчета. Физические характеристики, правила складского хранения, паллетизация, возвратная тара, фактические экземпляры упаковок, остатки и движения упаковок не входят в GMD v1 и относятся к ПР09 / производственной логистике. | GMD должен предоставить стабильные допустимые упаковки и пересчеты для НП, заказов, поступлений, отпусков и планирования. Но складские и операционные свойства упаковки зависят от логистических сценариев и не должны преждевременно расширять модель GMD. | `01_scope.md`, `02_domain_model.md`, `05_rules.md` |
| Тип единицы транспортировки имеет вместимость по НП | Описать отдельный сценарий `TransportUnitType -> Nomenclature` через `UnitOfOperation.ToNomenclature`. `ConversionFactor` означает количество НП в ее базовой учетной ЕИ, размещаемое на одной единице транспортировки данного типа. | Это не обычная дополнительная ЕИ НП и не упаковочный пересчет, а правило вместимости типа единицы транспортировки для конкретной НП. | `02_domain_model.md`, `05_rules.md` |

## 7. Правила проверки

| Область | Правило |
| --- | --- |
| `Unit` | `Precision` в диапазоне 0..8; обязательны `Name`, `Acronym`, `Precision`. |
| `UnitGroup` | Обязателен `BaseUnit`; `BaseUnit` должен относиться к тому же предприятию. |
| `NomenclatureGroup` | Иерархия групп не должна содержать циклов; группа не может быть дочерней самой себе; архивирование группы запрещено, если у нее есть неархивные дочерние группы или неархивные НП. |
| `Nomenclature` | Обязательны `Name`, `Unit`, `ApplicationArea`, `NomenclatureType`; `Unit`, `NomenclatureKind`, `NomenclatureGroup`, `PackSet` и `BaseManufacturer` должны относиться к тому же предприятию, если заполнены. |
| Граница основных данных, политик и настроек других модулей | Для каждого спорного поля объектов GMD определить категорию: основные данные объекта, общая политика объекта GMD, настройка или ссылка другого модуля. Поле остается в GMD, если GMD владеет его смыслом и инвариантами, даже если потребителями будут другие модули. |
| `NomenclatureVariant` | Исполнение принадлежит одной НП; должно быть не более одного базового исполнения в рамках НП. |
| Жизненный цикл | Полный жизненный цикл `Draft -> Published -> Archived` подключается только для объектов, которым нужна подготовка и контроль допуска к использованию. Простые справочники и дочерние объекты используют Common-архивирование и удаление без собственного состояния публикации, если отдельным решением не будет обосновано иное. |
| `UnitOfOperation` | Ровно один владелец пересчета; ровно одна цель пересчета; допустимые пары описываются матрицей ниже. Для одного владельца и одной области применения допускается не более одной активной `UnitOfOperation` с `IsDefault = true`; записи по умолчанию не должны иметь пересекающиеся `ApplicationArea`. |
| `Pack` | Ровно один владелец упаковки: `PackSet` или `Nomenclature`; пересчет упаковки обязателен через `UnitOfOperation`; `Pack.Type` не вводится как физическое поле, тип выводится из владельца. |
| Граница упаковок и логистики | `PackSet` и `Pack` описывают допустимые упаковки и пересчеты. Вес брутто, габариты, объем, возвратность, правила хранения, паллетизация, фактические упаковочные единицы, остатки и движения относятся к производственной логистике. |
| Область предприятия | Все записи объектов GMD имеют `TenantId`. У дочерних объектов `TenantId` должен совпадать с `TenantId` владельца; значение не принимается от пользователя и не может быть изменено отдельно от владельца. |
| `TransportUnitType` | Вместимость к НП описывается отдельно от обычных дополнительных ЕИ НП: `ConversionFactor` задает количество `ToNomenclature` в базовой учетной ЕИ на одну единицу транспортировки данного типа. |
| `NomenclatureParameter` | Нельзя менять тип данных после появления enum values или parameter values. |
| `NomenclatureParameterAssignment` | Область назначения нельзя менять после появления строк значений по этому назначению. |
| Значения реквизитов | Для каждого владельца и реквизита допускается одно фактическое значение. Перед записью строки значения Object Runtime должен проверить применимость реквизита к типу объекта-владельца, тип данных, длину/точность, обязательность и допустимость значения: для `LocalEnum` - по `NomenclatureParameterEnumValue`, для `ValueSet` - по актуальным данным Platform ValueSetData. Значение по умолчанию хранится на уровне назначения и подставляется при подготовке строк значений для карточки, а не через отдельный признак `IsDefaultValue` в строке значения. |
| `Contractor.Type` | Проектировать как обязательное одиночное поле `ContractorType`. Фраза ПР01 о нескольких видах контрагента трактуется как относящаяся к категориям контрагента. |
| `Contractor.Category` | Проектировать как обязательное поле `ContractorCategoryFlags`. Это флаговый системный enum с кодами ПР03: поставщик, изготовитель, подрядчик, заказчик. Поле описывает системные роли контрагента, а не произвольный расширяемый классификатор. |
| `ContractorContact.ContactType` | Проектировать как обязательное одиночное поле `ValueSetCode` с начальными значениями ПР03: руководитель, контактное лицо. Это осознанное отклонение от enum в ПР01/ПР03: конкретные значения не участвуют в зафиксированной бизнес-логике, а список типов контактов может отличаться у предприятия. ValueSet модуля описан в `10_value_set_data_usage.md`. |
| `ContractorInContractorGroup` | Контрагент может быть включен в одну группу только один раз: уникальность `ContractorGroup + Contractor`. |
| `ContractorContact` | У `Contractor` есть коллекция `Contacts`. Для одного `Contractor + ContactType` допускается один контакт. |
| Машиночитаемая идентификация | Объекты GMD могут подключать общую возможность REQ-00-B-019..022. Правила уникальности, генерации, проверки и количества идентификаторов на объект определяются в Common/Platform, не в GMD. |
| Интеграция с нумерацией | GMD может подключать Platform Numbering для своих полей, например `Nomenclature.Code` и `SerialNumber.SerialNumber`. `Nomenclature.IsLotsControlRequired` и `Nomenclature.SerialNumbersControlType` определяют необходимость контроля партий и серийных номеров, но не задают формат номера. Правила нумерации, область действия, условия, шаблоны и счетчики описываются в Platform Numbering, не в `05_rules.md` GMD. |

### Матрица `UnitOfOperation`

| Владелец | Цель | Смысл |
| --- | --- | --- |
| `UnitGroup` | `ToUnit` | Общий пересчет из базовой ЕИ группы в дополнительную ЕИ. |
| `Nomenclature` | `ToUnit` | Пересчет для конкретной НП из ее базовой ЕИ в дополнительную ЕИ. |
| `Lot` | `ToUnit` | Партионный пересчет, если коэффициент зависит от партии. |
| `Pack` | `ToUnit` | Упаковка содержит количество в ЕИ. |
| `Pack` | `ToPack` | Упаковка содержит другую упаковку. |
| `TransportUnitType` | `ToNomenclature` | Тип единицы транспортировки связан с НП и задает вместимость: количество НП в ее базовой учетной ЕИ на одну единицу транспортировки данного типа. |

## 10. Статус спорных решений

| ID | Статус и решение | Куда влияет |
| --- | --- | --- |
| GMD-DD-006 | Закрыто: расхождения ПР01 и DMP_DATA разобраны. `Pack.Type` закрыт: физическое поле не вводится, тип выводится из владельца `PackSet` или `Nomenclature`. `Pack.UnitPack` из форм ПР01 нормализуется в `PackUnit`, так как DMP_DATA задает это имя поля. `TransportUnitType.IsDefault` закрыт: такого поля у `TransportUnitType` в ПР01/DMP_DATA нет; значение по умолчанию относится к `UnitOfOperation.IsDefault`. `NumeratorDescriptor`/`NumeratorValue` закрыты: нумераторы относятся к Platform Numbering, не к GMD. `NomenclatureParameterValue` закрыт: значения реквизитов проектируются как отдельные типы объектов строк коллекций Object Runtime, наследуемые от `NomenclatureParameterValueBase`; единая таблица значений для всех владельцев не используется. `NomenclatureParameterEnumValue` закрыт: сохраняется как локальный GMD-источник значений перечислимого реквизита; для общих и переиспользуемых списков `NomenclatureParameter` должен ссылаться на Platform `ValueSetCode`. | `02_domain_model.md`, `05_rules.md` |
| GMD-DD-007 | Закрыто: GMD не проектирует отдельный альтернативный слой API по ПР01. Объекты GMD доступны через Object Runtime: контракты объектов, настроенные списки и карточки, стандартные операции чтения и изменения, объектные действия и действия жизненного цикла по платформенному стандарту. Описания API из ПР01 используются как требования к составу объектов, прикладных функций и сценариев, но не как буквальный REST-контракт API. Ручные API-методы допускаются только там, где стандартного Object Runtime недостаточно. | `03_object_runtime_model.md` |
| GMD-DD-008 | Закрыто: поле остается в GMD, если оно описывает саму НП, общий признак основных данных или общую политику использования НП, даже если поле используют логистика, производство, склад, закупки или качество. Поле не остается в GMD только если его смысл и правила проверки принадлежат конкретному другому модулю и без этого модуля поле нельзя корректно валидировать. Очевидные связи ПР01 (`NomenclatureVariant`, `UnitOfOperation` для НП, `Pack`/`PackSet`, реквизиты НП) фиксируются в доменной модели без отдельного повторного обсуждения. | `01_scope.md`, `02_domain_model.md`, `05_rules.md` |
| GMD-DD-009 | Ожидаем ответ аналитика по смыслу `Nomenclature.IsMain`. До получения ответа поле не обсуждается повторно и не используется как основание для других проектных решений. | `02_domain_model.md`, `05_rules.md` |
| GMD-DD-010 | Ожидаем ответ аналитика по смыслу `Nomenclature.BlankSize`. До получения ответа поле не обсуждается повторно и не используется как основание для других проектных решений. | `02_domain_model.md`, `05_rules.md` |
| GMD-DD-011 | Закрыто: для поля контроля партий используется техническое имя `IsLotsControlRequired`, как в ПР01. Причина: поле имеет тип `bool`, поэтому имя с префиксом `Is` лучше соответствует принятому стилю именования признаков. Русское имя поля фиксируется как "Контроль партий". | `02_domain_model.md`, `03_object_runtime_model.md`, код модуля |
