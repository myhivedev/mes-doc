# Стратегия испытаний — Управление документацией

## 1. Цель

Испытания подтверждают бизнес-правила, права, границу предприятия, целостность содержимого, интерфейсы и архитектурные ограничения.

## 2. Обязательные сценарии

| Область | Проверки |
|---|---|
| Нумерация | автоматический код типа `{Numerator:00}`; номер `{DocumentType.Code}-{Numerator:0000}`; ручное изменение; запрет сохранения пустого номера; отсутствие нового номера у новой версии |
| Жизненный цикл | все разрешённые и запрещённые переходы; восстановление в черновик; изменение опубликованной версии только после возврата в черновик |
| Версии и копирование | первая версия без ссылки; последующие ссылаются на первую; копия получает новый номер; новая версия сохраняет номер |
| Содержимое | три вида; неизменяемость после прикрепления; одно основное; отвязка; мягкое удаление после последней связи; сохранение при наличии других связей |
| Файлы | каждый разрешённый класс форматов; запрет `.zip` и `.7z`; 100 МБ; превышение; регистр расширения; частичный результат множественной загрузки |
| Хранилище | создание системного хранилища «База данных» при подключении модуля; назначение его типу документа; обязательное хранилище типа; хранение файла в БД в MVP |
| Связанные записи | существование, предприятие, право просмотра, дубликат, последующая недоступность без раскрытия данных |
| Ответственные | поле «Ответственное подразделение» выбирает внутреннюю производственную единицу; подрядчик исключён |
| Права | три роли; роль «Администратор модуля „Управление документацией“» включает роль «Работа с документами», а та включает роль «Просмотр документов»; повторные серверные проверки |
| Интерфейс | три представления документов; сохранение состояния пользователя; полный набор действий; действия содержимого на панели; пустые состояния и ошибки |
| Программный интерфейс | те же проверки, что в интерфейсе; стабильные коды ошибок; отсутствие обхода обязательности через API |
| Аудит | изменение, переходы, скачивание и ссылка; отсутствие содержимого и секретов в аудите |

## 3. Проверки границ

- запрос и ссылка на данные другого предприятия отклоняются;
- мягко удалённое содержимое не попадает в подбор;
- опубликованный или архивный документ нельзя изменить обычным сохранением;
- недоступное действие нельзя выполнить прямым запросом;
- при конфликте изменения данные второго пользователя не перезаписываются; проверяется `ConcurrencyToken`.

## 4. Нефункциональный профиль

Проверяются согласованные целевые значения: не более 2 секунд для 95% операций с метаданными, не более 3 секунд до начала скачивания, до 1 млн документов на предприятие и 100 одновременных пользователей. Это согласованный стартовый профиль, а не значение из исходных требований.

## 5. Критерий приёмки

Все обязательные сценарии MVP проходят; `DM-Q-008`, пользовательские хранилища и внешнее хранение явно исключены из объёма MVP, а аудит чтения и `ConcurrencyToken` проверены. Критические и высокие дефекты отсутствуют.

## 6. Набор проверок Content Storage

Приёмка должна покрыть File/URL/Text, смешанный результат загрузки, проверки
расширения/MIME/размера, границы предприятия и владельца, payload только с
descriptor, primary, replace/clear, concurrency и файловое поле во встроенной
коллекции. Для UI отдельно проверяются стандартные паттерны: `FileField` для
скалярного свойства `File` в режимах карточки и списка, включая `View`, `Edit`,
`Inline Edit`, `Disabled` и `ReadOnly`; `FileUploadParameter` для параметра
`File` с `Multiple=false/true` в диалоге action, включая drop-зону, ограничения, ошибки по
файлам, повторную попытку, замену и очистку. Приёмка не должна считать
доступность прямого mutation API доказательством работы UI-редактора.

Отдельно проверяется отсутствие зависимости demo от модуля 05.
