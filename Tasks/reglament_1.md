# Постановка задачи: разработка регламента разработки MES-платформы

## 1. Роль

Ты — опытный технический архитектор и руководитель разработки корпоративных программных платформ. Ты обладаешь практическим опытом организации разработки на Java/Spring Boot и React, построения CI/CD на базе GitLab CI и Argo CD, автоматизации тестирования, организации Code Review, управления технической документацией и процессами разработки в Jira.

## 2. Задача

Разработать полноценный внутренний регламент разработки MES-платформы. Регламент должен устанавливать единые обязательные правила для всех участников разработки и быть пригодным для практического применения командой.

Документ охватывает три направления:

1. **Разработка ПО:** организация работы с исходным кодом, ветками, коммитами, Merge Request, Code Review, тестированием и технической документацией.
2. **CI/CD и тестовые окружения:** автоматизация сборки, проверок качества и безопасности, публикации артефактов и доставки изменений на окружения разработки и тестирования.
3. **Управление задачами:** правила постановки задач, декомпозиции, оценки, учёта трудозатрат, контроля выполнения, управления зависимостями и формирования отчётности.

### Ограничение области действия

Регламент заканчивается на этапе интеграции изменений в основную ветку, прохождения обязательных проверок и доставки на окружения разработки и тестирования.

**Не включать в документ:**
- выпуск и развёртывание в продуктивной среде;
- процедуры передачи и выпуска продуктивных релизов;
- согласование продуктивных релизов и управление окнами продуктивного обновления;
- поддержку нескольких выпущенных версий, LTS и исправления для предприятий, использующих старые версии;
- процедуры продуктивного отката, canary-развёртывания и обновления предприятий.

Не создавать разделы об этих процессах даже в сокращённом виде. Если для будущего продуктивного контура необходимо предусмотреть технические предпосылки, явно отделять их от требований настоящего регламента.

## 3. Контекст системы

Разрабатывается распределённая MES-платформа для нескольких промышленных предприятий.

Архитектура предусматривает центральный контур и независимые локальные контуры предприятий.

- Центральный контур обеспечивает корпоративное управление, общие настройки, конфигурацию, управление предприятиями и централизованную обработку данных.
- Локальный контур содержит MES-функциональность предприятия и должен обеспечивать автономное выполнение производственных операций при недоступности центрального контура.
- Обмен между центральным и локальными контурами асинхронный, на базе Kafka.
- Прямой обмен между локальными контурами разных предприятий отсутствует.
- Локальный контур не может использовать версию платформы новее версии центрального контура.
- Платформа предоставляет механизмы для реализации MES-функций, но не содержит всю прикладную бизнес-логику MES непосредственно в своём ядре.

### Функциональные части

| Компонент | Назначение |
|---|---|
| Admin | Управление предприятиями, площадками, пользователями, ролями, правами и настройками |
| Studio | Конфигурирование платформы без изменения исходного кода; не является Low-Code/No-Code-средой |
| Platform Execution | Исполнение объектов, процессов, правил, справочников, событий, аудита и интеграций, используемых MES-модулями |

MES-модули разрабатываются внутри репозиториев Platform Execution в соответствии с установленными границами модулей.

## 4. Технологический стек

Использовать следующие технологии и инструменты:

- Java, Spring Boot — серверная разработка;
- React, TypeScript — клиентская разработка;
- PostgreSQL — реляционная база данных;
- Kafka — асинхронный обмен событиями и синхронизация контуров;
- Keycloak — идентификация и аутентификация;
- Kubernetes — запуск приложений;
- Liquibase — миграции БД;
- GitLab CI — автоматизация сборки, тестирования и проверок;
- Argo CD — доставка приложений на окружения;
- Harbor — хранение Docker-образов;
- Nexus — хранение Maven/npm-артефактов и Helm-чартов;
- SonarQube — статический анализ кода;
- линтеры — проверка исходного кода и конфигураций;
- Vault — хранение секретов.

Допускается предлагать дополнительные инструменты только при наличии обоснованной необходимости. Каждое такое предложение необходимо явно обозначать и объяснять, какую проблему оно решает.

## 6. Модель ветвления

Предложить и формализовать упрощённую модель ветвления, основанную на одной основной ветке `main`.

Не использовать классический Git Flow и не вводить постоянные ветки `develop` и `release/*`.

### Основные правила

1. `main` — единственная постоянная ветка разработки и интеграции.
2. Новая задача сначала регистрируется в трекере.
3. Для каждой задачи создаётся отдельная короткоживущая ветка от актуального состояния `main`.
4. Изменения в `main` попадают только через Merge Request.
5. Merge Request должен пройти обязательные автоматические проверки и Code Review.
6. После успешного слияния запускается предусмотренный CI/CD-процесс.
7. Ветка задачи удаляется после слияния.
8. Прямые коммиты в `main` запрещены.
9. Незавершённая функциональность, которую нельзя включать для всех пользователей, должна оставаться выключенной либо быть изолирована с помощью feature flags.
10. Конфликты с актуальной версией `main` разрешаются до слияния; после разрешения конфликта повторно выполняются обязательные проверки.

### Именование веток

Использовать формат:

`<type>/<issue-id>-<short-description>`

Допустимые типы:

- `feature` — новая функциональность;
- `bugfix` — исправление дефекта;
- `docs` — документация;
- `refactor` — рефакторинг без изменения внешнего поведения;
- `test` — изменения тестов;
- `chore` — технические и вспомогательные изменения.

Идентификатор задачи и описание в имени ветки должны быть в нижнем регистре. Используются латинские буквы, цифры и дефисы. Описание — не более пяти слов.

Примеры:

- `feature/mes-123-equipment-state`
- `bugfix/mes-456-sync-timeout`
- `docs/mes-789-local-setup`
- `refactor/mes-234-object-engine`

Определить правила формирования имени ветки для изменений, затрагивающих несколько репозиториев, и для задач, не имеющих идентификатора в Jira. Если такие сценарии не поддерживаются, это должно быть указано прямо.

### Обязательные вопросы к модели ветвления

Описать:
- как обновлять ветку задачи при изменениях в `main`;
- когда применять merge и когда rebase, если оба механизма допускаются;
- как исправлять ошибки, обнаруженные после слияния;
- как организовать работу нескольких разработчиков над одной задачей;
- как не допускать попадания незавершённой функциональности в общий поток;
- как связывать ветки, коммиты и Merge Request с задачами.

Не добавлять сложные правила только ради полноты формальной схемы. Предпочитать минимальный набор правил, достаточный для безопасной коллективной разработки.

## 7. Процесс разработки

Формализовать единый цикл работы:

**Задача → анализ → проектирование при необходимости → ветка → разработка → тесты → Merge Request → Code Review → CI → слияние в `main` → доставка на `dev` → проверка на тестовом окружении.**

Для каждого этапа указать:
- ответственного;
- входные условия;
- обязательные действия;
- результат;
- критерии завершения;
- действия при неуспешном результате.

Code Review обязателен. Для слияния требуется минимум один положительный approval от другого участника команды. Автор изменений не может утверждать собственный Merge Request.

Указать дополнительные требования к изменениям архитектуры, API, схемы БД, межконтурного взаимодействия, безопасности и инфраструктуры.

Не требовать одновременно ADR, RFC и design doc для каждой задачи. Установить критерии применения каждого документа:
- ADR — фиксация значимого архитектурного решения;
- RFC — обсуждение предложения, затрагивающего несколько компонентов или команд;
- design doc — технический план реализации существенного изменения.

Для небольших локальных изменений отдельный документ не требуется, если отсутствует соответствующий критерий обязательности.

## 8. Коммиты и Merge Request

Использовать Conventional Commits.

Определить допустимые типы коммитов, формат сообщения, правила указания идентификатора задачи и способ автоматической проверки в CI.

Описать:
- минимальный состав Merge Request;
- шаблон описания;
- обязательные критерии приёмки;
- требования к тестам и документации;
- правила назначения ревьюеров;
- действия при отклонении Merge Request;
- условия повторного запуска проверок;
- требования к размеру и области изменений, если они нужны для поддерживаемого Code Review.

Автоматизировать проверки там, где это возможно средствами GitLab CI.

## 9. Тестирование и качество кода

Установить следующие исходные пороги:

- Unit-тесты: покрытие нового кода не менее 70%.
- Unit-тесты: покрытие модуля не менее 60%.
- Integration-тесты: обязательны для интеграций с БД, Kafka и внешними системами.
- Contract-тесты: обязательны для API frontend/backend и межконтурных API.
- E2E-тесты: обязательны для критических пользовательских и производственных сценариев.
- Нагрузочные тесты: обязательны при изменениях, существенно влияющих на производительность, и перед отдельной проверкой готовности платформы к повышенной нагрузке.

Определить инструмент и метод измерения покрытия, правила определения нового кода, область расчёта покрытия и условия блокировки Merge Request.

Описать тестовую пирамиду и разделить:
- быстрые проверки на Merge Request;
- расширенные проверки при интеграции в `main`;
- сквозные проверки на тестовом окружении.

Не считать успешную сборку достаточным подтверждением качества изменений.

## 10. CI/CD и окружения

Определить назначение и правила работы окружений:

| Окружение | Назначение |
|---|---|
| `dev` | Интеграционная проверка изменений и автоматические тесты |
| `test` | Сквозное и приёмочное тестирование согласованного набора изменений |

Не описывать `stage` и `prod` как рабочие окружения в рамках настоящего регламента.

### Проверки Merge Request

Предусмотреть:
- линтеры;
- unit-тесты;
- проверку формата коммитов;
- проверку наличия ссылки на задачу;
- сборку без публикации готовых артефактов;
- дополнительные проверки, необходимые для конкретного типа изменений.

### Проверки после слияния в `main`

Предусмотреть:
- unit-, integration- и contract-тесты;
- статический анализ кода;
- анализ зависимостей и лицензий;
- сборку артефактов;
- публикацию Docker-образов в Harbor и необходимых библиотек в Nexus;
- формирование однозначной связи артефакта с исходным коммитом;
- автоматическую доставку на `dev` через Argo CD;
- health-check и фиксацию результата развёртывания.

### Проверки и доставка на `test`

Определить условия, при которых версия допускается на тестовое окружение. Обеспечить воспроизводимость: на окружении должен проверяться именно тот артефакт, который был собран и прошёл предусмотренные проверки.

Разделить:
- успешное развёртывание;
- успешное выполнение автоматических тестов;
- завершение приёмочного тестирования.

Не считать эти события эквивалентными.

Для каждого пайплайна указать триггер, обязательные шаги, артефакты, критерии успеха и условия блокировки дальнейшего продвижения.

## 11. Безопасность и зависимости

Определить обязательные проверки:
- SAST;
- SCA — анализ уязвимостей и лицензий зависимостей;
- DAST — в пределах тестового контура, если проверка применима к соответствующим приложениям;
- отсутствие секретов в исходном коде и CI-логах;
- использование Vault для секретов;
- проверка Docker-образов и зависимостей;
- фиксация состава программных компонентов и происхождения артефактов.

Исходные требования к срокам устранения уязвимостей:

| Критичность | Максимальный срок устранения |
|---|---:|
| Critical | 24 часа |
| High | 7 дней |
| Medium | 30 дней |
| Low | 90 дней |

Определить ответственного за классификацию уязвимости, регистрацию исключений и контроль срока устранения.

При необходимости применения нормативных требований ФСТЭК/ГОСТ указать, какие исходные данные нужно уточнить для конкретизации обязательных проверок.

Не утверждать, что один инструмент полностью обеспечивает выполнение всех требований безопасности.

## 12. Работа с базой данных

Использовать Liquibase для миграций схемы БД.

Описать:
- хранение и ревью миграций;
- правила именования и организации файлов;
- порядок применения миграций в CI/CD;
- проверку миграций на тестовых данных;
- требования к совместимости приложения и схемы БД;
- порядок исправления ошибочной миграции;
- резервное копирование там, где оно необходимо для безопасного тестирования или восстановления.

Использовать подход expand/contract для изменений, требующих совместимости старой и новой версий приложения в пределах одного процесса обновления.

Не считать автоматический откат схемы БД безопасным по умолчанию. Разделять откат приложения, обратимые изменения схемы и восстановление данных.

## 13. Архитектура и совместимость контуров

Регламент должен учитывать независимость локальных контуров и асинхронное взаимодействие с центральным контуром.

Определить обязательные проверки изменений, влияющих на:
- межконтурные API;
- форматы событий Kafka;
- порядок обработки и повторную доставку событий;
- совместимость конфигураций;
- миграции данных;
- работу при временной потере связи;
- накопление и последующую обработку сообщений;
- восстановление синхронизации после сбоя.

В CI предусмотреть автоматизированные интеграционные проверки взаимодействия центрального и локального контуров. Обязательными сценариями являются потеря связи, накопление сообщений, восстановление связи, доставка конфигурации и соблюдение требований к обработке событий.

Результаты обязательных проверок должны блокировать продвижение изменений, если критерии не выполнены.

## 14. Управление задачами

Использовать иерархию:

**Инициатива → Эпик → Задача/История → Подзадача.**

Для задачи определить обязательные поля:
- краткий заголовок, сформулированный как действие;
- тип;
- эпик;
- описание проблемы и ожидаемого результата;
- критерии приёмки;
- приоритет;
- Story Points;
- компонент;
- связи с другими задачами;
- влияние на совместимость контуров, если применимо.

Определить правила декомпозиции, оценки, назначения исполнителей, управления блокировками и завершения задач.

Предусмотреть состояния задач для обычной разработки и исправления дефектов. Для каждого состояния описать условия входа, выхода и допустимые переходы.

Устранить неоднозначности исходной схемы статусов. Не использовать `Rejected`, `Reopened` и `Needs Explanation` без чёткого определения смысла и правил перехода.

### Оценка и трудозатраты

Разделить назначение Story Points и оценки времени. Не использовать два показателя как взаимозаменяемые оценки.

Если требуется учёт фактических трудозатрат, определить:
- правила ведения Original Estimate, Time Spent и Remaining Estimate;
- периодичность регистрации времени;
- порядок корректировки оставшейся оценки;
- правила формирования отчёта об отклонениях.

Порог уведомления об отклонении от оценки — `Time Spent > Original Estimate × 1.5`.

### Эпики и отчётность

Определить:
- правила расчёта прогресса эпика;
- обработку отменённых задач и задач без оценки;
- условия автоматического закрытия эпика;
- контроль зависимостей и блокировок;
- отчётность по вехам;
- правила определения Green / Amber / Red;
- автоматизацию в Jira Automation в пределах поддерживаемых возможностей.

Предусмотреть дашборды для руководства программы, команды разработки и ответственных за тестирование.

Описать смысл и формулы метрик Velocity, Cycle Time, Lead Time, WIP, Blocked Rate и Estimation Accuracy. Не использовать метрики как самостоятельную оценку производительности конкретного разработчика.

## 15. Роли и ответственность

Описать обязанности и полномочия следующих ролей:
- Product Owner;
- технический архитектор;
- функциональный архитектор или бизнес-архитектор — предварительно определить, являются ли они одной ролью;
- Senior-разработчик;
- разработчик;
- DevOps;
- QA;
- Security Officer;
- руководитель проекта.

Отдельно определить владельцев:
- архитектурных решений;
- технических стандартов;
- качества кода;
- тестовой стратегии;
- CI/CD;
- безопасности;
- структуры и качества задач;
- технической документации.

Не смешивать ответственность за выполнение работы и полномочия на её согласование.

Исходный состав команды: 10 разработчиков, в том числе 4 Senior, 2 DevOps, технический архитектор, бизнес-архитектор, 4 бизнес-аналитика, 3 специалиста внедрения, 2 тестировщика, Product Owner, руководитель проекта, Release Manager и Security Officer. Если роль Release Manager нужна только для процессов, исключённых из настоящего регламента, не наделять её обязанностями по выпуску продуктивных релизов в рамках этого документа.

## 16. Документация

Использовать подход docs-as-code в репозитории `mes-docs`.

Определить:
- перечень обязательных документов;
- критерии необходимости ADR, RFC и design doc;
- правила актуализации документации при изменении кода;
- порядок ревью документации;
- владельцев документов;
- правила хранения инструкций по разработке, тестированию и диагностике.

Документация, необходимая для понимания и проверки изменения, должна обновляться в рамках того же процесса, что и исходный код.

## 17. Корпоративные стандарты и приложения

Предусмотреть шаблоны:
- Merge Request;
- ADR;
- RFC;
- design doc;
- задачи и эпика;
- чек-листа Code Review;
- описания тестового сценария;
- отчёта по вехам;
- инструкции по локальному запуску проекта;
- инструкции по диагностике сбоя на `dev` или `test`.

## 18. Требования к качеству регламента

Документ должен:
- быть написан на русском языке;
- использовать нормативный, однозначный и практический стиль;
- устанавливать проверяемые требования вместо общих рекомендаций;
- назначать ответственного для каждого существенного процесса;
- содержать числовые пороги там, где они необходимы;
- описывать автоматизации достаточно подробно для реализации в GitLab CI, Argo CD, SonarQube, Harbor, Nexus и Jira Automation;
- не дублировать одни и те же правила в нескольких разделах;
- не содержать противоречий между разработкой, тестированием, безопасностью и управлением задачами;
- различать обязательные требования, рекомендуемые практики и предложения;
- не вводить новые инструменты без явного обоснования;
- соответствовать упрощённой модели ветвления с единственной постоянной веткой `main`;
- не включать процессы выпуска в продуктивную среду.

## 19. Формат результата

Подготовь полный документ в Markdown, пригодный для внутреннего согласования.

Для каждого процесса укажи цель, область применения, ответственных, последовательность действий, критерии завершения и автоматические проверки.

Используй таблицы, списки, схемы и готовые шаблоны там, где они делают правила однозначнее.

В конце добавь раздел **«Что осталось уточнить»**. В него включи только вопросы, ответы на которые действительно необходимы для утверждения или практической реализации регламента.

Если исходные данные противоречивы или недостаточны, не останавливай подготовку документа: явно укажи проблему, предложи обоснованное решение и вынеси оставшийся выбор в заключительный раздел.
