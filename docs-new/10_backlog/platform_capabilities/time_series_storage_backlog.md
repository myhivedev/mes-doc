# Backlog будущей capability хранения временных рядов и телеметрии

## 1. Назначение

Документ фиксирует будущую capability хранения временных рядов и телеметрии:

- телеметрию MES/MDC;
- замеры оборудования;
- события и состояния источников;
- аварийные сигналы;
- другие факты, для которых время события является частью смысла данных.

Capability не реализована и пока не является отдельной платформенной областью
в `docs-new/03_platform/`. Этот backlog не устанавливает текущий контракт и не
подменяет решение о владельце.

Audit History, Workflow History и Integration Events/Outbox не являются
хранилищем временных рядов.

## 3. Кандидатные правила для проектирования

Ниже перечислены предложения, которые нужно подтвердить при проектировании
capability. Они не являются действующими требованиями реализованной системы.

- В хранилище временных рядов время хранится в UTC.
- Для SQL Server целевой физический тип времени — `datetime2(7)`.
- Внешние API и интеграционные контракты передают время в ISO-8601 со
  смещением; предпочтительный тип публичного контракта — `DateTimeOffset`.
- Время без часового пояса или смещения не должно молча трактоваться как UTC.
- `OccurredAtUtc` — время факта или замера по часам источника после нормализации
  в UTC.
- `IngestedAtUtc` — время приёма данных DMP.
- Поля жизненного цикла (`CreatedAtUtc`, `ModifiedAtUtc`, `ArchivedAtUtc`,
  `DeletedAtUtc`) не заменяют `OccurredAtUtc`.
- Часовой пояс Tenant используется для отображения и интерпретации
  пользовательских интервалов, но не как основное значение хранения.
- Окна агрегации строятся в UTC.

## 5. Рабочий порядок

### 5.1. Граница capability

Определить один из вариантов:

- `Integration Service -> Time Series Storage`;
- отдельный `Equipment Gateway`;
- комбинированный путь для MVP.

Отдельно зафиксировать, что outbox, Audit History и Workflow History не
используются как хранилище телеметрии.

### 5.2. Минимальная модель данных

Спроектировать кандидатов:

- `TimeSeriesPoint`;
- `TimeSeriesSource` или `SourceCode`;
- `TimeSeriesMetric` или `MetricCode`;
- стратегию типизированных значений или payload значений;
- `QualityCode` и минимальную модель качества данных.

### 5.3. Контракт приёма

Определить правила для:

- входящего времени как ISO-8601 со смещением;
- нормализации в `OccurredAtUtc`;
- заполнения `IngestedAtUtc`;
- `ClockSource`;
- `ClockAccuracyMs`;
- `OriginalOffset`;
- `SequenceNumber`;
- ключа идемпотентности для повторной доставки.

### 5.4. Модель хранения

Спроектировать:

- физический тип времени и индексы;
- индекс по `(TenantId, OccurredAtUtc)`;
- дополнительные индексы по источнику, метрике и окну времени;
- обязательность метаданных часов;
- политику хранения и возможное разбиение таблиц.

### 5.5. Часовые пояса и API

Определить:

- ошибку для входящего времени без смещения, если контракт явно не разрешает
  иное;
- тип времени во внешних DTO;
- использование часового пояса Tenant только для отображения и интерпретации
  интервала запроса;
- правила перехода на летнее или зимнее время через стандартные библиотеки.

### 5.6. Запросы и агрегации

Спроектировать контракт запроса и результата:

- перевод пользовательского интервала в UTC;
- выполнение агрегации в UTC;
- минимальную гранулярность окна, если она будет нужна в MVP;
- отдельный режим чтения исходных высокочастотных данных, если он будет
  принят;
- возврат сведений о часовом поясе или смещении для клиента, если это
  требуется сценарием.

### 5.7. Аномалии времени

Определить обработку следующих случаев:

- большая разница между `IngestedAtUtc` и `OccurredAtUtc`;
- время из будущего;
- чрезмерный jitter;
- отсутствующий или неизвестный `ClockSource`;
- признак `IsTimeAnomaly`;
- диагностический поток или hook для уведомления.

### 5.8. Первый вертикальный срез

Выбрать один payload MES/MDC или оборудования и определить:

- минимальный набор источника и метрики;
- схему хранения;
- путь `ingestion -> normalization -> persistence`;
- запрос по `(TenantId, OccurredAtUtc)`;
- один сценарий чтения или агрегации.

### 5.9. Проверки времени

Подготовить проверки для:

- нормализации UTC из разных смещений;
- отказа на время без смещения;
- преобразования часового пояса и переходов летнего времени;
- стабильности окон агрегации для разных часовых поясов;
- обнаружения искусственного сдвига часов.

### 5.10. Единый источник текущего времени

После определения runtime-контракта проверить генерацию времени в production-
коде и отделить сохраняемые timestamps от технических локальных расчётов.

### 5.11. Обновление документации после решения

После принятия решений или реализации среза обновить только документы
соответствующих владельцев:

- пакет Time Series, если capability получит самостоятельного владельца;
- Integration Capability для Equipment/MDC-среза;
- API и event contracts;
- общую архитектуру;
- документы прикладного модуля, если такой модуль появится.

## 6. Definition of Done первого среза

Первый срез считается спроектированным и реализованным только после того, как:

- утверждена граница Integration Service / Equipment Gateway / Time Series;
- определена модель `TimeSeriesPoint`;
- определён контракт приёма со временем ISO-8601 и нормализацией в UTC;
- запись содержит `OccurredAtUtc`, `IngestedAtUtc` и согласованный набор
  метаданных источника;
- определены индексы и политика хранения;
- есть один сценарий запроса или агрегации с окнами UTC;
- выполнены проверки часовых поясов, переходов времени и аномалий;
- документация обновлена по принятому решению и фактической реализации.
